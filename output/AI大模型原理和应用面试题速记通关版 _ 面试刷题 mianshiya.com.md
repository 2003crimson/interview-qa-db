## 请解释⼤模型微调(Fine-tuning)的原理，并说明在什么业务场景下需要微调⽽不是直接使⽤基础模型？

微调的本质是参数⾼效迁移，不是从头训练。⼤模型已经在海量通⽤语料上学到了语⾔规律和世界知识，微调是在这个基础上，⽤特定领域的数据去调整模型参数，让它适应新任务。

1）你拿到⼀个预训练好的⼤模型，⽐如 LLaMA 或 Qwen，它的“常识”已经很完整。但如果你要做⾦融研报⽣成，它可能写得不够专业。这时候直接 prompt ⼯程搞不定，因为领域术语、⾏⽂逻辑差异太⼤。

2）微调就是拿⼀批⾦融报告数据，⽤有监督的⽅式继续训练。⽐如输⼊“某公司营收增⻓30%”，让模型输出对应的研报段落。反向传播会更新权重，让模型在该任务上表现更好。

3）关键在于，并不是所有层都要重训。现在很多做法是只微调部分参数，⽐如LoRA（Low-RankAdaptation），冻结原模型权重，只训练低秩矩阵。这样显存占⽤少，训练快，适合业务迭代。

需要微调的场景通常是：

输出格式/⻛格强约束，⽐如法律⽂书、医疗诊断记录

领域知识密集，基础模型没⻅过的专业术语体系

企业私有数据不能⾛API，必须本地部署并定制

如果只是简单问答、摘要⽣成，且对表达⻛格要求不⾼，那其实⽤提⽰词+RAG就够了。微调成本⾼，周期⻓，真要上得想清楚是不是⾮⽤不可。

## RAG的完整流程是怎么样的？

RAG的流程其实就三步：准备数据、查资料、⽣成答案。整个过程让⼤模型在回答前，先去“翻书”找依据。

1）数据准备阶段，先把外部知识库的⽂档切⽚，⽐如把PDF或数据库表结构说明拆成⼀段段⽂本块。接着⽤embedding模型给每⼀块转成向量，存进向量数据库，像Milvus或Pinecone这类⼯具⼲的就是这事。

2）⽤户提问时，系统不会直接扔给⼤模型。⽽是先把问题也转成向量，去向量库⾥做相似度搜索，找出最相关的⼏个⽂本块。这⼀步很关键，决定了模型能“看到”哪些背景知识。

3）最后，把这些检索到的⽂本块拼接成提⽰词，连同原问题⼀起喂给⼤模型。模型基于这些上下⽂⽣成答案，⽽不是靠记忆瞎编。这样出来的回答有据可查，幻觉少。

<!-- image-->

这个流程⾥，embedding模型和向量检索的质量直接决定效果。如果检索错了，后⾯再强的模型也搞不定。常⻅坑是⽂本分块不合理，⽐如按固定字符切，把⼀个完整概念切碎了，导致查不准。

## 什么⾃查询？为什么在RAG中需要⾃查询？

⾃查询其实是让模型⾃⼰⽣成查询条件，去检索它需要的信息。⽐如你问“苹果最新财报怎么样”，模型不会直接回答，⽽是先拆解问题，⽣成像“苹果2024年Q2营收、利润、同⽐增⻓”这样的检索关键词，再拿这些词去查⽂档。

这在RAG⾥特别关键，因为原始问题往往太笼统或包含多个维度。直接拿原问题去搜，召回的内容可能不精准。⾃查询相当于加了⼀层智能路由，把复杂问题翻译成适合检索的结构化查询语句。

1）能处理时间范围过滤，⽐如“去年销售额最⾼的产品”会被转成带时间约束的查询

2）⽀持属性筛选，“便宜的安卓⼿机”会拆成“价格低于2000元、操作系统为Android”

3）适配向量库的元数据检索，⽐如⽤ Chroma 或 Pinecone 的 where 条件过滤

代码上⼀般⽤ LLM 接⼀个提⽰模板：

```java
String prompt = "根据⽤户问题⽣成检索查询语句: " + userQuestion;
List<String> queries = llm.generate(prompt);
List<Document> results = vectorStore.search(queries);
```

整个流程像是给RAG装了个“理解⼤脑”，先把⼈话转化成机器能⾼效检索的指令，避免压根不经过语义解析就硬搜。

## 什么提⽰压缩？为什么在 RAG 中需要提⽰压缩？

提⽰压缩其实就是把RAG中过⻓的上下⽂输⼊给“瘦⾝”。你想想，⼤模型的上下⽂⻓度是有限的，⽐如32K或128K，但检索回来的⽂档⽚段⼀多，加上原始问题和模板，很容易就超了。

1）最直接的问题就是token数爆掉，请求直接被拒，压根不经过模型推理。

2）就算没超，⻓上下⽂推理成本⾼，响应慢，延迟上去⽤户体验就差了。

3）⽽且很多检索出的内容其实跟问题关系不⼤，纯属噪⾳，反⽽⼲扰⽣成质量。

所以得做提⽰压缩，把那些冗余信息、重复段落、⽆关句⼦给剔除或简化。不是简单删减，⽽是保留关键事实和语义，让输⼊更紧凑⾼效。

常⻅的做法有⼏种：

⽤⼩模型先做⼀轮重排序或摘要，⽐如⽤ BGE 或 Cohere reranker 挑最相关的 top-k。

在 prompt 组装时加逻辑，只保留⾼分 chunk，甚⾄对每个 chunk 做句⼦级裁剪。

也可以引⼊类似 HyDE 的思路，先⽣成假设答案再反向匹配，过滤低相关度内容。

代码上没啥复杂语法，核⼼是控制组装后的总token数：

```toml
# 伪代码⽰意
context = "\n".join([chunk["text"] for chunk in relevant_chunks[:3]]) # 限制数量
prompt = f"基于以下内容回答：\n{context}\n\n问题：{query}"
```

要不要压缩，其实看场景。如果检索精度⾼、返回少，可能不需要。但⾯对海量⽂档库，⽐如⽤在企业知识库搜寻，就得靠这招扛住⻓上下⽂压⼒。

## 什么是 RAG 中的分块？为什么需要分块？

RAG 的上下⽂⻓度是有限的，⽐如主流模型⼀般⽀持 32k 或 128k 的 token 上下⽂。你塞进去的 prompt 越⻓，能留给检索内容的空间就越少。分块其实就是把原始⽂档切成适合模型处理的⼩段落，让每次检索和⽣成都能在上下⽂窗⼝内完成。

1）分块不是简单按段落切。如果按固定字符数切，可能把⼀句话从中间劈开，语义就断了。好的分块策略会尽量保持语义完整，⽐如⽤递归分割，先按标题切，再按段落，最后才是固定⻓度。LangChain⾥的RecursiveCharacterTextSplitter 就是这么⼲的。

2）块太⼩，信息不全，模型容易“只⻅树⽊不⻅森林”；块太⼤，⼜挤占上下⽂，影响其他 prompt 内容。⼀般来说，512到1024个token是⽐较常⻅的块⼤⼩，具体得看你的数据和模型。

3）有些场景还得考虑跨块关联。⽐如⼀个技术⽅案分布在三个块⾥，单靠⼀个块检索出来，模型也拼不全逻辑。这时候就得靠后续的查询扩展或多步检索来补救。

代码上⼤概⻓这样：

```python
from langchain.text_splitter import RecursiveCharacterTextSplitter
splitter = RecursiveCharacterTextSplitter(
chunk_size=512,
chunk_overlap=50,
separators=["\n\n", "\n", 1 1I
。
)
docs = splitter.split_text(large_document)
```

要不要分块，其实取决于你的数据形态和检索⽬标。像PDF、⻓⽹⻚这种肯定要分，但如果是短问答对，可能直接喂进去就⾏。

## 在RAG中，常⻅的分块策略有哪些？分别有什么区别？

分块策略直接影响检索效果，选不好后⾯全⽩搭。关键得看⽂本的语义连贯性和上下⽂依赖。

## 1）固定⼤⼩分块

按字符或token数硬切，⽐如每512个token切⼀块。简单粗暴，适合结构规整的⽂档。但容易把⼀句话从中间劈开，语义被撕裂，检索回来的⽚段可能压根不经过原意。像PDF或⽹⻚正⽂这种连贯性不强的还⾏，但技术⽂档、论⽂就搞不定。

## 2）基于段落或标题分割

利⽤⾃然断点，⽐如⼀级/⼆级标题之间、空⾏处分割。能保留完整语义单元，适合 Markdown、Word 这类有结构的⽂档。问题在于块⼤⼩不均匀，有的标题下内容贼⻓，检索时信息密度太低。

## 3）滑动窗⼝重叠分块

在固定⼤⼩基础上，让相邻块有部分重叠，⽐如每次滑动512，重叠128。这样能缓解语义断裂，关键信息⼤概率出现在多个块⾥。但会增加索引量和检索耗时，重复内容多，存储成本翻倍也不稀奇。

## 4）语义感知分块（如 RecursiveCharacterTextSplitter）

先按标点切，再按⻓度合并，尽量保证句⼦完整。LangChain ⾥默认⽤这个，实际项⽬中表现最稳。更进⼀步可以⽤嵌⼊模型做句⼦相似度判断，在语义边界处分割，不过延迟⾼，⼀般⽤在对精度要求极⾼的场景。

<!-- image-->  
选哪种？短平快任务⽤滑动窗⼝+固定⼤⼩，追求效果上语义分块，有明确结构就优先标题分割。

## 在 RAG 中的 Embedding 嵌⼊是什么？

Embedding在RAG⾥⼲的事，就是把⽂本转成机器能算的“数字向量”。你给它⼀句话、⼀段⽂档，它就输出⼀个⻓⻓的浮点数数组，这个数组得能保留原⽂的语义信息。

⽐如你搜“怎么修⾃⾏⻋”，系统其实不是在关键词匹配，⽽是先把这句话做个 Embedding 变成向量，再去向量空间⾥找和它最接近的那些⽂档⽚段。像⽤百度搜索那种关键词匹配早就跟不上了，现在都靠这种语义相似度来找答案。

1）这活⼀般由预训练模型来⼲，⽐如 BERT、Sentence-BERT（SBERT），或者专⻔做检索的 bge 模型。它们会把不同⻓度的⽂本压到固定维度的向量⾥，常⻅的是 768 或 1024 维。

2）RAG 流程中，Embedding 主要⽤于两个地⽅：⼀是离线把知识库⽂档切⽚后全部向量化存进向量数据库，⽐如⽤FAISS、Milvus 或 Pinecone；⼆是线上⽤户⼀提问，⽴刻转成向量去库⾥查 top-k 最相似的 chunk。

3）效果好不好，关键看Embedding是否真能把相近意思的⽂本“拍”到向量空间⾥挨得近。如果“如何重启路由器”和“拔电源再插上”这两个句⼦向量距离很近，那说明嵌⼊质量⾼。

代码上基本就是调个model.encode(text)就完事，但背后模型选型、是否微调、向量索引构建⽅式都会影响最终召回率。

## 在 RAG 中，你知道有哪些 Embedding Model 嵌⼊模型？

Embedding 模型在 RAG ⾥头其实就⼲⼀件事：把⽂本转成向量，让检索系统能算相似度。选对模型直接影响召回质量。

主流的通⽤嵌⼊模型有Sentence-BERT（SBERT），它在BERT基础上加了个池化层，专⻔优化句⼦级表⽰。⽐如你⽤ paraphrase-MiniLM-L6-v2 ，⼩模型快，适合轻量场景。

进阶⼀点的是Cohere提供的multilingual-2和command-r系列，尤其是多语⾔⽀持好，在跨语⾔检索⾥表现稳。  
Cohere 的 API 易⽤，但得⾛⽹络请求。

还有OpenAI的text-embedding-ada-002，虽然不开放本地部署，但在英⽂任务上精度⾼，适合不想调参直接上⽣产的场景。

开源界现在⽤得猛的是 BGE（来⾃智源研究院），⽐如 bge-small-zh-v1.5，中⽂场景下效果拉满，本地跑起来也顺。  
它通过“查询-⽂档”对增强训练，特别适配 RAG 的检索偏好。

别忘了还有 Jina AI 推的 jina-embeddings-v2，⽀持 8192 token ⻓度，⻓⽂本处理有优势，⽽且许可友好，能商⽤。

选模型得看三点：语⾔是否匹配、延迟能不能压住、有没有⻓⽂本需求。别⼀上来就⽤⼤模型，⼩模型蒸馏过的在90%场景都够⽤。

## 什么是MCP协议，它在AI⼤模型系统中的作⽤是什么？

MCP协议并不是⼀个在AI⼤模型领域⼴泛通⽤的标准协议，⽬前也没有权威⽂献或主流框架将其定义为类似HTTP、gRPC那样的基础通信协议。它更可能是指特定⼚商或系统内部定义的模型控制平⾯（ModelControlPlane）协议，⽤于协调⼤模型服务中的调度、分发与⽣命周期管理。

在典型的推理服务平台⽐如阿⾥云百炼、vLLM或TritonInferenceServer中，这类“控制协议”主要⼲三件事：

1）接收推理请求并做路由决策，⽐如该发给哪个模型实例、是否需要扩缩容

2）管理模型加载、卸载、版本切换，确保GPU资源⾼效利⽤

3）收集监控指标，配合实现弹性伸缩和故障转移

你可以把它理解成K8s⾥的kubelet和APIServer之间的通信逻辑，只不过⾯向的是模型实例⽽不是容器。真正的请求处理⸺也就是数据平⾯（DataPlane）⸺还是靠gRPC或REST承载实际的token流量，⽽MCP这类控制指令通常⾛独⽴通道，频率低但关键性⾼。

// 伪代码⽰意：控制平⾯接收加载模型指令  
void onReceiveLoadModel(String modelId, String version) {  
ModelInstance instance = createOrReuseInstance(modelId);  
instance.loadFromStorage(); // 可能涉及 mmap、量化加载等优化  
registerToRouter(instance); // 注册到流量路由器  
}

要不要⽤这类协议，取决于系统规模。⼩场景直接API调⽤就够了，上了百个模型实例后，就得靠统⼀控制平⾯来“扛住”运维复杂度了。

## MCP架构包含哪些核⼼组件？

MCP架构这个词在主流技术领域没有统⼀标准定义，更常⻅的类似缩写是MCP（Model-View-Presenter）属于UI架构模式，常⽤于客户端开发。但如果你指的是服务端或中间件场景下的某种定制架构，可能是特定团队对消息驱动、控制平⾯分离类系统的简称。

不过从实际系统设计⻆度看，如果把 MCP 理解为 Message-Driven Control Plane 这类架构，它的核⼼组件⼀般包含三个部分：

## 1）消息中枢

负责路由和分发指令，⽐如⽤Kafka或RocketMQ做命令总线，所有控制指令通过Topic⼴播。消费者按需订阅，实现解耦。这种设计在微服务治理中很常⻅，像Nacos配置变更就是靠⻓轮询+消息通知双机制推到客户端。

## 2）控制单元

接收消息后执⾏具体逻辑，⽐如修改本地状态、调⽤外部接⼝、触发任务调度。它不直接暴露HTTP接⼝，⽽是被动响应事件。Spring Cloud Stream 的 @StreamListener 就是典型写法，压根不经过 Web 层。

## 3）状态反馈器

反向上报执⾏结果，形成闭环。通常往⼀个集中式存储写状态，⽐如把节点健康度打到Redis，或者把执⾏⽇志发到Elasticsearch。ZooKeeper 临时节点也⼲这事，会话⼀断⾃动清理状态。

## MCP协议⽀持哪两种模式？

MCP（Model Context Protocol）⽬前主要⽀持两种交互模式，对应不同的上下⽂处理⽅式。

## 1）请求-响应模式

这是最常⽤的模式，客户端发送⼀个请求，携带特定上下⽂，服务端完全基于该上下⽂⽣成响应，交互结束。整个过程类似HTTP的调⽤模型，适合⼀次性任务，⽐如让⼤模型总结⼀段⽂本、翻译⼀句话。这种模式下，上下⽂只在当前请求中⽣效，不会保留。

## 2）会话模式

系统会维护⼀个持续的上下⽂会话状态，客户端可以连续发送多条消息，每条都基于之前的对话历史进⾏理解与回应。典型场景是聊天机器⼈、AI助⼿这类需要记忆上下⽂的产品，⽐如使⽤MCP协议对接LLM构建客服系统时，⽤户前⼏轮提到的信息要能在后续对话中被引⽤。

会话模式的关键在于服务端需要管理Session状态，可能结合UUID或token来标识不同⽤户的上下⽂隔离。⽽请求-响应模式⽆状态，更容易⽔平扩展。

要不要⽤会话模式，得看业务是否需要“记住”前⾯的内容。如果只是做离散任务，⽐如内容审核、关键词提取，压根不需要维持状态，⽤第⼀种就够了。

## MCP 与 Function Calling 的区别是什么？

MCP和FunctionCalling看似都在让模型“调⽤功能”，但它们的定位和机制完全不同。

MCP其实是⼀种协议，更准确地说是ModelContextProtocol，它定义了外部系统如何向⼤模型提供上下⽂、⼯具描述以及如何接收模型的结构化输出。它不绑定具体实现，强调的是模型与环境之间的标准化交互⽅式。你可以把它理解成⼀个通⽤的“插件通信规范”，像GitHubCopilotExtensions就基于这类思想构建扩展能⼒。

⽽FunctionCalling是具体的能⼒，指的是⼤模型能根据输⼊决定是否调⽤某个预定义函数，并⽣成符合schema的参数。主流闭源模型如GPT-4都⽀持这个特性，它是实现Agent⾏为的基础组件之⼀。⽐如你⽤LangChain写个天⽓查询，模型会判断⽤户意图后返回 {"name": "get_weather", "arguments": {"city": "Beijing"}} 这样的结构。

关键区别在于：Function Calling 是单⼀模型对外暴露的能⼒接⼝，MCP 则是多个系统间协作的协议框架，⽀持更复杂的双向交互和资源共享。

## MCP 的⼯作流程是什么？

MCP 其实是 Model Context Protocol 的缩写，它不是传统中间件或 Java 领域的标准组件，⽽是在 AI Agent 架构中⽤来规范⼤模型与外部⼯具、数据源之间交互的协议。它的核⼼作⽤是让模型能安全、可控地访问运⾏时上下⽂。

整个流程从⽤户发起请求开始。Agent 接收到输⼊后，会先做⼀次意图解析，判断是否需要调⽤⼯具。如果需要，就会构造⼀个符合MCP格式的请求包，⾥⾯包含动作类型、参数和上下⽂元信息。

接下来这个请求会被转发给对应的⼯具适配器。⽐如你要查数据库，就会⾛SQL⼯具链；要发HTTP请求，就交给API客户端处理。执⾏结果原路返回，由MCP解析器把原始响应转成模型能理解的⾃然语⾔⽚段。

1）请求触发：⽤户输⼊进⼊ Agent 循环

2）决策判断：Controller判断是否需外部调⽤

3）协议封装：按 MCP 标准⽣成 tool call 消息

4）⼯具执⾏：Adapter 调⽤具体服务并获取结果

5）上下⽂注⼊：将结果以结构化⽅式回填到 prompt 上下⽂

<!-- image-->

这种设计的好处是解耦了模型逻辑和外部系统。像 LangChain 或 Semantic Kernel 这类框架，底层其实就是靠类似MCP 的机制在做调度。你不需要改模型代码，只要注册新⼯具就能扩展能⼒。

## 在 Spring AI 框架中如何集成 MCP？

SpringAI框架本⾝是Spring⽣态中⽤于接⼊⼤模型服务的抽象层，它的设计⽬标是让Java应⽤能统⼀⽅式调⽤不同AI平台的能⼒。MCP（ModelContextProtocol）是⼀种⽤于在客户端与模型服务之间传递上下⽂信息的协议，常⻅于某些私有化部署或定制化推理平台。

要把 MCP 集成进 Spring AI，关键在于⾃定义客户端适配器。Spring AI ⽀持扩展 ChatClient 接⼝，你可以基于RestClient 或 WebClient 实现⼀个专⽤于与⽀持 MCP 协议的服务通信的客户端。

1）你需要先定义请求结构体，匹配MCP规范⾥的字段，⽐如 context , prompt , model 等。2）通过@RegisterAiClient 注解注册你的实现，或者⼿动配置为 Bean 。 3）在调⽤时注⼊ ChatClient ，框架会⾃动路由到你的MCP适配器。

@Bean   
ChatClient mcpChatClient(WebClient webClient) {   
return ChatClient.builder()   
.baseUrl("https://mcp-gateway.example.com")   
.webClient(webClient)   
.build();   
}

实际请求中，header或payload⾥要带上MCP要求的元数据，⽐如会话ID、租户上下⽂等。这类脏活累活⼀般封装在拦截器⾥处理。

如果使⽤ Spring AI 0.8.0+ 版本，已经⽀持 SPI 扩展机制，可以更⼲净地插拔协议实现。不过⽬前主流⼚商如通义千问、百川都不⾛MCP，它更多出现在内部统⼀推理⽹关场景，⽐如阿⾥云灵积的部分私有实例。

## MCP 协议安全性设计包含哪些层⾯？

MCP协议本⾝并不是⼀个⼴泛标准化的通⽤协议，更多是特定系统或平台内部定义的通信规范。讨论其安全性设计，得从典型中间件通信协议的防护思路⼊⼿，⼀般会覆盖这⼏个层⾯。

传输安全靠TLS/SSL加密链路，防⽌数据被窃听或篡改，这是基础操作。⾝份认证通常⾛双向证书、APIKey或OAuth令牌，确保连接双⽅都是合法⻆⾊。访问控制会在协议层嵌⼊权限信息，⽐如Kafka的ACL机制就绑在请求头上，决定谁能读写哪个 topic。

数据层⾯要防敏感信息裸奔，可以在payload内部做字段级加密，像⽀付类消息⾥的卡号，别指望⽹络层全兜住。审计和⽇志也得跟上，关键操作记录请求来源、时间、动作，出事能追溯。重放攻击靠nonce或时间戳窗⼝来防，每个请求带唯⼀序列号，服务端做校验去重。

<!-- image-->

其实很多开源框架⽐如gRPC或Dubbo，都把这套模式揉进了⾃⼰的扩展点⾥。MCP如果是⾃研协议，这些环节⼀个都不能少，否则⾼压环境下容易被钻空⼦。

## 如何将已有的应⽤转换成MCP服务？

MCP本质上是⼀套⾯向云原⽣的模块化编程模型，核⼼是把传统应⽤拆解成可独⽴部署、按需加载的微内核+插件结构。你不需要重写整个系统，关键是识别出哪些模块具备“可插拔”特征。

⼀般适合改造的模块是那些业务边界清晰、依赖收敛、有明确接⼝定义的部分。⽐如你在⽤SpringBoot做⽹关，⾥⾯的鉴权、限流、⽇志收集这些功能就可以拆成MCP插件。它们共⽤⼀套上下⽂，但彼此不耦合。

改造第⼀步是引⼊ MCP 运⾏时容器，⽐如基于 Jigsaw 模块系统或⾃研 ClassLoader 隔离机制。然后把原有功能打成jar 包，配上 module.json 或注解声明⼊⼝类和依赖关系。启动时容器会按拓扑顺序加载并激活。

代码上最简单的做法是在原项⽬加⼀个启动器：

```java
@McpModule(name = "auth-plugin", version = "1.0")
public class AuthPlugin implements ModuleLifecycle {
public void onStart(Context ctx) {
ctx.registerFilter(new AuthFilter());
}
}
```

注意类加载器隔离，避免第三⽅库冲突。像 Apollo、Nacos 这类配置中⼼的客户端通常要下沉到宿主，插件通过统⼀API 获取配置。

常⻅翻⻋点是静态变量共享和线程池滥⽤。不同插件如果都 new ⾃⼰的 ThreadPoolExecutor，很容易把机器打爆。  
建议统⼀⽤宿主提供的执⾏器。

<!-- image-->

这种架构在阿⾥内部的 Sentinel 控制台、Ant Design Pro 后台都有落地，主要是为了⽀撑多租户定制化需求。⼩团队⽤的话，得评估好复杂度收益⽐，别为了架构⽽架构。

## 什么是⼤模型微调？与预训练的核⼼区别是什么？

⼤模型微调是在预训练好的模型基础上，⽤特定领域的数据继续训练，让它适应具体任务。⽐如你有个通⽤语⾔模型，想让它擅⻓写法律⽂书，就拿⼀堆法律⽂本去微调它。

1）预训练是打基础，模型在海量⽆标注数据上学习语⾔规律，⽬标是理解“什么是语⾔”。这个阶段通常要⽤上千张GPU卡跑⼏周，参数量动不动上百亿。

2）微调是定向优化，⽤的是⼩规模、有标注的领域数据，⽐如客服对话、医疗报告。训练轮次少，计算资源消耗低，⼀般⼏张GPU就能搞定。它的⽬标不是从零学语⾔，⽽是调整已有知识去解决“某个具体问题”。

3）两者的区别不在代码实现，⽽在数据和⽬标。预训练像通识教育，什么都学；微调像职业培训，专精⼀项。Hugging Face 上很多 bert-base-chinese 是预训练模型，⽽ bert-wwm-ext 就是在此基础上做了额外微调的版本。

<!-- image-->

微调压根不重新训练整个⽹络，只是在原有权重上做⼩幅更新。如果任务差异太⼤，⽐如从⽂本⽣成跳到图像识别，那微调就搞不定了，得换架构重来。

## 常⻅的微调任务有哪些？

微调任务其实就是在预训练模型基础上，针对特定场景做适配。最常⻅的⼏种类型，基本覆盖了⼤部分NLP需求。

## 1）⽂本分类

把句⼦或段落分到预定义类别⾥。⽐如情感分析判断评论是正⾯还是负⾯，⽤BERT接⼀个分类头就⾏。

// 伪代码⽰意

## 2）命名实体识别（NER）

找出⽂本⾥的实体，像⼈名、地名、组织名。⼀般在每个token上做序列标注，CRF层常⽤来优化标签间转移逻辑。

## 3）问答任务（QA）

最典型的是SQuAD这类抽取式问答。模型要从给定段落⾥标出答案的起⽌位置。输⼊是“问题+段落”，输出两个指针。

## 4）⽂本⽣成

⽐如摘要⽣成、翻译。⽤ T5 或 BART 这类 seq2seq 模型，输⼊原⽂，输出压缩后的摘要。训练时⽤交叉熵算 loss。

## 5）句⼦对关系判断

判断两句话是什么关系。⽐如⾃然语⾔推理（MNLI），看第⼆句是⽀持、⽭盾还是中⽴于第⼀句。STS任务则是算语义相似度。

这些任务的数据格式和输出头不⼀样，但训练⽅式都差不多：冻结部分底层参数，放开顶层微调，学习率通常设得⽐较⼩，3e-5到5e-5就够了。数据量⼀般⼏千到⼏万条就能⻅效，迁移学习在这⾥真能省下⼤量训练成本。

## 常⻅的微调⽅法有哪些？

微调本质上是拿预训练模型在特定任务上做⼆次训练，让模型更适配具体场景。常⻅的⽅法选择得看数据量、算⼒和任务复杂度。

1）全量微调就是把整个模型的参数都放开训练。效果通常最好，但显存消耗⼤，8张A100都不⼀定扛住Llama27B的全量微调。适合数据质量⾼、预算充⾜的场景。

2）LoRA（低秩⾃适应）现在成了主流⽅案。它冻结原模型权重，在旁边加个⼩的低秩矩阵做增量，训练时只更新这部分。显存能省下 70%，训练速度也快，Hugging Face 上⼤部分开源微调项⽬都在⽤。

# LoRA 核⼼思想：A 下降维度，B 升维，中间做低秩分解   
lora_weights = (x @ A) @ B   
output = original_output + lora_weights

3）Adapter⽅法是在Transformer层之间插⼊⼩的神经⽹络模块，训练时固定主⼲，只调这些⼩模块。结构改动⽐LoRA ⼤，但现在⽤得少⼀些。

4）P-Tuning 和 Prompt Tuning 属于提⽰微调，不改模型本⾝，⽽是学⼀组虚拟 token 的 embedding。适合少样本场景，但效果波动⼤，对初始化敏感。

选哪个得权衡。数据多、资源⾜，可以试全量微调；⼤多数情况下，LoRA是性价⽐之选，像Qwen、ChatGLM的社区微调基本都靠它打底。

## 什么是护栏技术？

护栏技术本质是⼀种在系统运⾏时动态控制流量、防⽌雪崩的保护机制。它不追求彻底解决问题，⽽是快速⽌损，让系统能继续对外提供部分服务。

1）核⼼思路是“宁可限流，不可拖垮”。⽐如⼀个电商系统的下单接⼝突然变慢，⼤量请求堆积，数据库连接被打满，这时候如果不加⼲预，整个应⽤可能直接宕机。护栏技术就是在这个临界点介⼊，把超出处理能⼒的请求直接拒绝或降级。

2）常⻅的实现⽅式有熔断、限流、降级。熔断像电路保险丝，当错误率超过50%就直接切断请求，避免连锁故障；限流控制每秒最多放⾏1000个请求，多余的就地拦截；降级则是返回兜底数据，⽐如商品详情⻚的推荐模块挂了，就直接返回空列表，保证主流程可⽤。

3）实际项⽬⾥，Sentinel和Hystrix都是典型的护栏⼯具。拿Sentinel来说，你可以给某个接⼝配置QPS超过50就⾃动限流，规则可以实时推送，不⽤重启服务。

```javascript
// 定义资源
SphU.entry("getOrder")
// 业务逻辑
```

这种机制特别适合⽤在⾼并发场景，⽐如秒杀系统。你不可能靠堆机器扛住所有流量，得靠这些“安全策略”来兜底。真正的稳定性不是不出问题，⽽是出问题时系统还能活着。

## 什么是 GPTCache？

GPTCache 是⼀个专为⼤模型应⽤设计的语义缓存中间件，⽬标是把重复或语义相近的请求直接拦截下来，减少对⼤模型API的调⽤次数，从⽽降成本、提响应速度。

它的核⼼思路不是简单地做字符串匹配，⽽是通过向量相似度来判断新来的请求和历史请求是否“意思差不多”。⽐如⽤户问“今天天⽓怎么样”和“现在外⾯晴吗”，⽂字不同但意图接近，GPTCache 就可能命中缓存。

整个流程⼀般是这样：

1）⽤户请求进来，先被转换成 embedding 向量

2）在向量数据库⾥搜最近似的⼏个结果

3）如果相似度超过阈值，就返回缓存⾥的答案；否则⾛正常链路调⼤模型，并把新的 question-answer 存进缓存

<!-- image-->

它适合⽤在⾼频问答、客服机器⼈、RAG 系统这类场景，尤其是请求重复率⾼、对延迟敏感的应⽤。像 LangChain、LlamaIndex 这些框架都能集成 GPTCache。

不过要注意，embedding模型的选择和距离计算⽅式会直接影响命中精度，太松容易误中，太严⼜起不到缓存作⽤。  
⼀般建议搭配Milvus、Pinecone或Chroma做向量存储，性能和扩展性更稳。

## 什么是 GPT Structured Outputs？

GPTStructuredOutputs是⼀种让⼤模型输出结构化数据的能⼒，⽐如JSON格式的结果，⽽不是⾃由⽂本。这在需要程序直接解析模型输出的场景⾥特别有⽤。

你告诉模型你想要的 schema，它就会按这个格式返回数据。这样⼀来，前端或后端代码就能直接消费输出，不⽤再写⼀堆正则或逻辑去提取信息。

⽐如你在调⽤ GPT 时启⽤ response_format 参数，并指定为 JSON Schema，模型就会严格按字段输出。OpenAI从 2023 年底开始⽀持这个功能，适⽤于像 gpt-3.5-turbo 和 gpt-4 这样的模型。

```jsonl
{
"name": "Alice",
"age": 30,
"city": "Beijing"
}
```

这种机制适合做配置⽣成、表单填充、API数据抽取等任务。和以前“靠运⽓”解析⽂本不同，现在结果可预测、可验证。

不过得注意，模型不会⾃动知道什么时候该输出结构，必须显式设置参数，否则还是⾛⾃由⽣成。另外复杂 schema可能增加token消耗，设计时要权衡清晰度与成本。

如果原题解中的某句话使⽤了超链接，不要对这句话做任何改动。

## 什么是 LangChain？

LangChain是个帮助开发者快速搭建应⽤的框架，重点是让⼤模型和外部系统打通。你不⽤从零写prompt调⽤、上下⽂管理、⼯具调⽤这些重复代码，它都给你封装好了。

它的核⼼能⼒之⼀是链式调⽤，你可以把多个步骤串起来，⽐如先查数据库，再让⼤模型总结，最后发个通知。每个环节它都抽象成组件，像积⽊⼀样拼接。

另⼀个关键点是跟外部数据对接。⽐如你要做个客服机器⼈，不能光靠模型内置知识，得让它查你的产品⽂档。LangChain 提供了和向量数据库集成的能⼒，像和 Pinecone、Weaviate 对接，做检索增强⽣成（RAG），这样回答就有据可依。

它还⽀持Agent模式，就是让模型⾃⼰决定下⼀步⼲什么。⽐如⽤户问“昨天销售额最⾼的订单是谁”，模型可以⾃⼰判断要先查订单表，再查客户信息，然后组织语⾔回复。背后其实是模型输出特定格式指令，框架负责解析并执⾏。

代码上它很简洁，⼏⾏就能定义⼀个链：

```python
from langchain.chains import LLMChain
chain = LLMChain(llm=llm, prompt=prompt)
response = chain.run("中国的⾸都是哪⾥？")
```

适合做需要动态输⼊、多步推理、结合私有数据的场景，⽐如智能客服、数据分析助⼿。但如果你只是简单问答，可能显得重了。

## 什么是 LangGraph ？

LangGraph 是基于 LangChain 构建的有状态的多智能体协作框架。它把多个 AI Agent 的交互过程建模成“图”（Graph），每个节点是⼀个执⾏单元，边代表控制流或数据流向。

这种图结构让你能清晰定义复杂的 agent 协作逻辑。⽐如⼀个节点是⽤户输⼊处理，另⼀个是⼯具调⽤，第三个是决策判断，通过边连接它们的执⾏顺序。整个流程的状态被显式维护，后续节点可以访问前⾯所有步骤的数据。

它特别适合做需要反复来回交互的任务。像客服系统⾥，⼀个agent处理意图识别，发现信息不全就转给追问agent，补全后再交给业务办理 agent。这种循环、条件跳转、状态保持的场景，传统流⽔线搞不定，⽽ LangGraph能扛住。

代码上其实就是定义⼀堆节点函数，然后⽤ add_node 和 add_edge 把它们串起来，最后编译成⼀个可执⾏的graph。调试时还能看到每⼀步的状态快照，排查问题⽅便多了。

举个实际场景：⽤ LangGraph 搭⼀个多轮审批流，结合 Human-in-the-loop，在关键决策点暂停等待⼈⼯确认，确认后继续往下⾛，整个过程可追溯。

<!-- image-->  
这个模型让复杂 agent ⼯作流变得结构化，⽽不是⼀堆混乱的回调和全局变量。

## LangGraph 编排的原理是什么？

LangGraph 的本质是把⼤模型的执⾏过程变成⼀个有向图，每个节点是⼀个动作或决策点，边代表执⾏路径。你给它⼀个输⼊，它就从起点开始，按图的结构⼀步步⾛，⾛到哪、下⼀步⼲啥，由当前节点的逻辑决定。

1）节点可以是调⽤⼤模型、执⾏⼯具、做条件判断，甚⾄是⼈⼯审核这种阻塞操作。⽐如在客服机器⼈⾥，⼀个节点 可能是“识别⽤户意图”，下⼀个节点根据意图跳转到“查订单”或者“投诉处理”。

2）每⼀步的状态都通过⼀个共享的state对象传递，这个state是可变的，后续节点能读也能改。这就让整个流程有了上下⽂记忆，不像普通函数调⽤那样孤⽴。

3）控制流靠的是conditionaledges，也就是条件边。你可以写个函数判断state⾥的字段，返回下⼀个节点的名字。  
⽐如判断“是否需要⼈⼯介⼊”，返回 "human_in_the_loop" 或 "continue_automated"。

代码上其实就是定义节点函数和边规则：

graph.add_node("generate", generate)   
graph.add_conditional_edges("generate", route_generate_result)

整个执⾏过程是同步推进的，但每步之间可以暂停、恢复，适合⻓周期任务。像AutoGen、CrewAI这些框架底层也⽤了类似思路，只是LangGraph更灵活，⽀持复杂DAG。

## LangChain 和 LangGraph 有什么区别？

LangChain是个⼯具箱，帮你快速搭起和⼤模型交互的流⽔线。你拿它做点简单的链式调⽤，⽐如⽂档加载、切分、检索再喂给LLM⽣成答案，整个流程像⼀条直线，串⼏个组件就跑起来。适合做些原型或者轻量级应⽤，⽐如基于⽂档问答的⼩⼯具。

LangGraph就不⼀样了，它是专⻔搞有状态、多步骤、带循环的复杂Agent流程的。你可以把它看成是LangChain的“升级控制器”。它⽤有向图来建模流程，节点是动作，边是转移逻辑，能表达“失败重试”、“条件跳转”、“⼈类介⼊”这种复杂控制流。⽐如你做个多智能体协作系统，A⼲完活交给B，B觉得不⾏⼜回滚给A，这种环状依赖，LangChain 原⽣链式结构压根不经过，但 LangGraph 天⽣⽀持。

打个⽐⽅：LangChain是条流⽔线，⼯件从头⾛到尾；LangGraph是个调度⽹络，能根据情况动态派单、回流、并⾏处理。

代码上，LangGraph 核⼼是 StateGraph ，你定义⼀个共享状态，每个节点函数读写这个状态，然后通过条件边决定下⼀步去哪：

```python
from langgraph.graph import StateGraph
graph = StateGraph(MyState)
graph.add_node("draft", draft_node)
graph.add_node("review", review_node)
graph.add_conditional_edges("review", should_rework)
graph.add_edge("draft", "review")
```

这种模式在做 AutoGen、MetaGPT 那类复杂 Agent 编排时特别扛住，脏活累活都让它揽了。

## 什么是Manus？说说你对它的了解

Manus 不是 Java 或中间件领域的技术组件，它其实是⼀个由上海 AI 实验室推出的开源⼤模型智能体框架。你可以把它理解成⼀个能让⼤语⾔模型“动起来”的⼯具链，让模型不仅能回答问题，还能执⾏任务。

它最⼤的特点是⽀持⾃主规划与⼯具调⽤。⽐如给它⼀个复杂⽬标，像“分析某⽀股票的历史⾛势并⽣成报告”，Manus 能⾃⼰拆解任务：先搜索实时股价，再调⽤ Python 分析数据，最后⽣成可视化图表和⽂字总结。背后依赖的是强化学习和思维链（CoT）的结合。

这类框架⼀般会集成常⻅⼯具接⼝，⽐如数据库连接、API调⽤、代码解释器等。你在⽤的时候只需要定义⽬标，剩下的步骤由agent⾃主决策。类似项⽬还有LangChain+AutoGPT的组合，但Manus更强调端到端的⾃治能⼒和中⽂场景优化。

典型架构包含⼏个核⼼模块：任务分解器、⼯具路由、记忆存储和反馈循环。它不像传统微服务那样靠RPC通信，⽽是通过语义驱动动作选择。

## ReAct是什么？说说它的原理

ReAct是⼀种让⼤模型在做推理时，既能思考（Reasoning）⼜能⾏动（Action）的框架。它的核⼼不是单纯输出答案，⽽是通过交错的“想⼀步、做⼀步”来完成复杂任务。

模型在处理问题时，会先⽣成⼀段思考内容，⽐如分析当前情况、设定下⼀步⽬标，然后决定⼀个具体操作，⽐如调⽤⼯具、查数据库或搜索⽹⻚。这个动作执⾏后拿到结果，再喂回模型继续下⼀轮思考，直到得出最终答案。

这种模式特别适合需要外部交互的任务，像客服机器⼈查订单状态，或者智能助⼿执⾏多步操作。相⽐纯推理，它能获取实时数据；相⽐纯指令驱动，它多了规划和反思能⼒。

举个例⼦，你要查天⽓并决定是否带伞，ReAct 会先想“我需要知道当前位置的天⽓”，然后触发“调⽤天⽓API”动作，拿到结果后再判断“预报有⾬，建议带伞”。

整个过程就像⼈在解决问题时的习惯：思考→⾏动→观察→再思考。语⾔模型不再只是被动回答，⽽是主动推进任务。

LLMAgent的基本架构有哪些组成部分？

LLMAgent不是简单地调⽤⼤模型，⽽是⼀个能感知环境、做出决策并执⾏动作的智能体。它的结构更像是⼀个闭环控制系统。

## 1）感知模块（Perception）

负责接收外部输⼊，⽐如⽤户指令、环境状态或历史交互记录。这部分会把原始信息转换成模型可理解的格式，通常就是拼接到 prompt ⾥。

## 2）规划模块（Planning）

这是 Agent 的“⼤脑”，⼜可以拆成两块：

推理（Reasoning）：让模型对当前问题进⾏多步思考，⽐如使⽤思维链（Chain-of-Thought），先想“我该怎么做”，再决定下⼀步。

任务分解（Task Decomposition）：复杂任务会被拆成多个⼦任务，按序或并⾏处理，像 LangChain 中的Plan-and-Execute 就是典型实现。

## 3）记忆模块（Memory）

维持短期和⻓期上下⽂。短期记忆⼀般是当前对话的token上下⽂窗⼝，受限于模型⻓度；⻓期记忆则依赖向量数据库，⽐如⽤Milvus或Chroma存储历史经验，需要时检索召回。

## 4）⼯具调⽤与执⾏（Tool Use & Action）

Agent 能主动调⽤外部⼯具，⽐如查天⽓、执⾏代码、操作数据库。主流做法是通过函数调⽤（Function Calling）机制，让模型输出结构化JSON去触发API，例如在OpenAI的接⼝中定义tools列表。

整个流程⾛下来，其实就是⼀个“观察→思考→决策→⾏动→观察”的循环。

## LLMAgent常⻅功能有哪些？

LLMAgent不是简单的问答机器⼈，它得能感知环境、做规划、调⼯具、持续执⾏直到⽬标完成。你可以把它看成⼀个“AI执⾏官”，⾃⼰拆任务、调接⼝、纠错重试。

## 1）规划与⽬标分解

Agent接到“分析竞品并写报告”这种⼤任务，不会⼀⼝吞，⽽是拆成查资料、读PDF、对⽐数据、⽣成初稿、润⾊⼏步。像 LangChain 的 PlanAndExecute 就是⼲这个的典型模式。

## 2）⼯具调⽤（Function Calling）

它得知道什么时候该让别⼈⼲活。⽐如查实时股价，直接调 Alpha Vantage API；订会议室就⾛钉钉或⻜书开放平台。  
模型输出结构化指令，框架负责转成真实调⽤。

## 3）记忆能⼒

短时记忆靠上下⽂窗⼝存对话历史，⻓时记忆就得接外部存储。⽐如⽤Chroma或Milvus存过往决策记录，下次遇到类似任务能参考。

## 4）⾃主执⾏与反思

有些 Agent 能⾃⼰决定下⼀步。AutoGPT 是个例⼦，但它容易陷⼊循环。更稳的做法是 ReAct 模式：每步“思考-⾏动-观察”，像⼈⼀样边做边看结果。

## 5）多 Agent 协作（进阶）

复杂场景下会分⼯。⽐如⼀个当产品经理提需求，⼀个当⼯程师写代码，⼀个当测试员验证，通过内部通信达成⽬标。MetaGPT 就模拟了这种⻆⾊分⼯。

别指望它百分百靠谱，超⻓上下⽂推理还是会乱，⼯具调⽤也可能失败。关键是设计好fallback机制和⼈⼯介⼊点。

## 市⾯上有哪些主流的 LLM Agent 框架？各⾃的特点是什么？

主流的LLMAgent框架这⼏年发展很快，基本都围绕“如何让⼤模型更可靠地完成复杂任务”在设计。

1）LangChain是最早⽕起来的框架，⽣态最全，⽀持的数据源、⼯具、模型最多。它的优势在于灵活，像搭积⽊⼀样组合组件，适合做原型验证。但灵活性带来的问题是代码结构容易混乱，调试困难，⽣产环境需要较强的⼯程能⼒压得住。

2）LlamaIndex起家是为了解决⼤模型对接私有数据的问题，核⼼强项是检索增强⽣成（RAG）。它对⽂档切分、索引构建、查询优化做了很多深度优化，⽐如⽀持分层索引、动态获取上下⽂。如果你的Agent主要靠读⽂档回答问题，⽐如⽤在企业知识库场景，LlamaIndex通常⽐LangChain更⾼效。

3）AutoGPT名⽓很⼤，主打“⾃主任务分解”，能⾃⼰拆⽬标、调⼯具、循环执⾏。理想很丰满，但实际跑起来经常陷⼊⽆效循环，输出不可控，⽬前更多是概念验证，⽣产环境基本不⽤。

4）Semantic Kernel 是微软出的，和 Azure ⽣态深度绑定，适合 .NET 技术栈的团队。它强调“规划器”概念，把任务拆解做成可配置模块，和 LangChain 类似但更重企业级控制。

5）Dify 和 FastGPT 属于低代码平台型框架，把 Agent 的流程可视化，拖拽就能编排 prompt、⼯具和逻辑。适合产品经理或业务⽅快速试错，但灵活性受限，复杂逻辑还得写代码。

总的来说，选哪个框架看场景。做RAG优先看LlamaIndex，要快速搭demo⽤LangChain或Dify，企业级可控流程可以看看 Semantic Kernel。

## 什么是 LangChain Agent?

LangChain Agent 的本质是⼀个能做决策的“⼤脑”，它不直接⽣成最终结果，⽽是根据⽬标动态规划步骤，调⽤⼯具去执⾏。

1）Agent会接收⽤户输⼊，结合预设的提⽰词和可⽤⼯具描述，决定下⼀步动作。这个动作要么是调⽤某个⼯具（⽐如搜索、数据库查询），要么是直接返回结果。

2）它依赖 LLM 做推理判断。⽐如你问“今天上海天⽓怎么样”，Agent 会先意识到需要实时数据，于是选择调⽤天⽓API ⼯具，拿到结果后再让 LLM 汇总成⾃然语⾔回复。

3）⼯具（Tools）是关键组件，每个⼯具对应⼀个函数，声明了名称、描述和⼊参。Agent不直接写代码，⽽是通过描述理解⼯具能⼒。你可以接⼊ SerpAPI 做搜索，或者⾃定义⼀个查订单的函数。

```javascript
// 伪代码⽰意：定义⼀个搜索⼯具
Tool searchTool = Tool.builder()
.name("search")
.description("⽤于查询实时信息，⽐如天⽓、新闻")
.function(query -> callSerpAPI(query))
.build();
```

和普通Chain的区别在于，Chain是固定流程，Agent是动态路径。你没法提前预知它会怎么⾛，就像你不能预测⼈思考的过程。

适合场景：需要多步推理、外部数据获取、动态决策的任务。但如果逻辑简单，直接写 Chain 更⾼效，别为了⽤⽽⽤。

## 什么是 LangChain model?

LangChain model 并不是⼀个独⽴的模型，它其实是 LangChain 框架中对各种⼤语⾔模型（LLM）的统⼀抽象封装。  
你⽤它来调⽤GPT、通义千问、ChatGLM这些模型时，接⼝都是⼀致的。

1）它的核⼼是提供⼀个标准接⼝，让开发者不⽤关⼼底层模型是哪家的，都能⽤同样的⽅式传⼊ prompt、拿到输出。⽐如你切换从 OpenAI 到本地部署的 Llama，代码改动可以⾮常⼩。

2）除了基础的⽂本⽣成，它还⽀持流式输出、带历史对话的会话模型（ChatModel）、以及结构化输出解析。像和⽤户多轮聊天的场景，直接⽤ RunnableWithMessageHistory 就能管理上下⽂。

3）实际开发⾥，你经常要拼接提⽰词、调⽤⼯具、做数据预处理。LangChain model 和 PromptTemplate、RetrievalChain这些组件能⽆缝配合，把这⼀整条链路串起来。

举个简单例⼦：

// 伪 Java ⻛格代码⽰意   
ChatModel model = new ChatOpenAI("gpt-3.5-turbo");   
String response = model.call("请⽤ Java 写个单例模式");

它真正解决的是AI应⽤开发中的㬵⽔问题。没有它的时候，每个模型调⽤都要写⼀堆适配代码，现在这些脏活累活框架帮你扛住了。

## A2A协议的⼯作原理是怎样的？

A2A（Application-to-Application）协议不是某个具体的技术标准，⽽是⼀种通信范式，指的是应⽤系统之间通过定义好的接⼝直接交互。这种模式在微服务、中台架构⾥特别常⻅。

1）通常基于HTTP/HTTPS或消息队列实现，⽐如两个服务间⽤RESTfulAPI交换JSON数据，或者通过Kafka异步传递事件。关键在于双⽅约定好数据格式和调⽤语义。

2）安全控制很重要，⼀般会引⼊OAuth2、JWT做⾝份鉴权。⽐如⼀个订单系统调⽤库存系统时，必须携带有效token，对⽅验证通过才执⾏扣减操作。

3）为了降低耦合，很多公司会加⼀层API⽹关统⼀管理A2A流量。像阿⾥云的APIGateway就能做限流、监控、访问控制，后端服务只专注业务逻辑。

代码上其实很简单，就是⼀个服务发起请求，另⼀个提供接⼝：

```javascript
// 消费⽅调⽤远程服务
ResponseEntity<StockResult> result = restTemplate.getForEntity(
"http://stock-service/decrease?itemId=1001",
StockResult.class
);
```

但实际落地要考虑超时、重试、熔断这些容错机制，不然⼀个服务卡住可能拖垮整条链路。Spring Cloud OpenFeign+ Hystrix 是⼀种典型组合。

## A2A协议的⼯作流程是怎样的？

A2A（Application-to-Application）协议不是某个具体的标准协议，⽽是⼀类系统间通信模式的统称。它指的是两个应⽤程序直接通过API、消息或⽂件等⽅式交换数据，不依赖⼈⼯⼲预。

这类通信⼀般⾛服务间调⽤链路，常⻅于微服务架构。⽐如订单系统调⽤库存系统扣减接⼝，这就是典型的A2A场景。整个流程从发起⽅构造请求开始，经过⽹络传输，到达接收⽅处理并返回结果。

1）发起⽅应⽤准备好业务参数，封装成请求体

2）通过 HTTP/REST 或 gRPC 等协议发送到⽬标服务

3）⽬标服务接收到请求后解析参数，执⾏业务逻辑

4）将结果序列化为响应体返回给调⽤⽅

5）发起⽅根据响应做后续处理，如重试、落库或通知下游

如果是异步场景，会引⼊消息中间件。⽐如⽤户注册后需要发邮件、加积分，主流程写⼊消息队列，由消费者分别调⽤邮件服务和积分服务。这种情况下A2A的流转就变成了事件驱动，Kafka或RocketMQ扮演了关键⻆⾊。

## ⼤模型的结构化输出指的是什么？

⼤模型的结构化输出，说⽩了就是让模型不光吐⽂字，还能按指定格式返回数据，⽐如 JSON、XML 或特定 schema的内容。你给个指令，它能⽣成符合接⼝契约的响应，⽽不是⼀堆⾃由发挥的⾃然语⾔。

这在实际系统集成⾥特别关键。⽐如你让⼤模型从⼀段⽂本⾥抽⽤户信息，直接回“张三，35岁，北京”还得再解析，但如果要求结构化输出，它就能直接给你：

```json
{
"name": "张三",
"age": 35,
"city": "北京"
}
```

这种能⼒⼀般靠提⽰词⼯程（prompt engineering）引导，或者⽤像 JSON mode 这类机制强制约束输出格式。OpenAI 的 API ⽀持 response_format={ "type": "json_object" } ，这时候模型就必须输出合法 JSON，否则调⽤⽅解析要出问题。

更进⼀步的做法是结合functioncalling或tooluse，把结构化输出当成调⽤外部⼯具的中间协议。⽐如你让模型判断是否需要查天⽓，它就返回⼀个带 function_call 字段的JSON，⾥⾯是函数名和参数，下游系统直接执⾏。

这类技术减少了后处理成本，让⼤模型能真正嵌⼊到软件流程⾥，⽽不是只当个聊天玩具。不过对模型本⾝的推理⼀致性和格式遵从度要求更⾼，⼩模型容易格式错乱，得反复校验。

## 什么是 Google ADK？

Google ADK（Android Debug Bridge）这个说法其实是个常⻅的误解。你可能想问的是 ADB，也就是 AndroidDebug Bridge。

ADB是Android开发⾥最基础的调试⼯具，它让你能在电脑上通过命令⾏跟⼿机通信。开发或者测试时，装应⽤、看⽇志、执⾏shell命令都靠它。

它由三部分组成：1）运⾏在电脑上的adb客户端2）运⾏在⼿机上的adbd服务3）中间通过USB或⽹络连接

⽐如你想把⼀个APK安装到设备，直接敲：

adb install app-debug.apk

或者进shell看⽂件：

adb shell   
ls /sdcard/

还有⼀种情况是 ADK，全称是 Android Open Accessory Development Kit，这是 Google 提供的⼀套让 Android 设备与外部硬件配件通信的⽅案，基于 USB 主机模式。像⼀些⼯业设备、外接传感器通过 USB 连⼿机，会⽤到它。不过实际项⽬中⽤得不多，⼤部分场景被蓝⽛或Wi-Fi取代了。

简单说，⽇常开发提到的“ADK”九成都是⼝误，真正要⽤的是ADB。遇到真配件通信需求，才会碰得到ADK那套协议和权限声明。

## 解释LangChain框架中的Chain和Agent概念，并举例说明各⾃的应⽤场景

LangChain ⾥的 Chain 和 Agent 是两个关键抽象，解决的是不同复杂度的任务编排问题。

Chain其实就是⼀个函数式的组合，把多个处理步骤像链条⼀样串起来。每个环节的输出⾃动作为下⼀个环节的输⼊，中间可以穿插对LLM的调⽤、数据处理或外部⼯具。⽐如你做客服机器⼈，⽤户问“今天北京天⽓怎么样”，你可以先⽤⼀个 PromptTemplate 构造查询语句，接着调⽤ LLM 解析出地点和需求，再交给⼀个 WeatherTool 获取真实数据，最后⽤另⼀个模板⽣成回复。这个流程就是典型的Chain，顺序执⾏，逻辑固定。
