## Redis通常应⽤于哪些场景？

缓存是最常⻅的⽤途，把热点数据放在Redis⾥，查询能从⼏⼗毫秒降到亚毫秒级。⽐如电商商品详情⻚，⽤Redis能扛住每秒⼏⼗万的并发请求。

1）Session 存储也常⽤它，像 Spring Session + Redis 可以实现分布式会话，在集群环境下⽤户登录状态不丢失。

2）分布式锁基于SETNX或RedLock实现，多个服务节点协调执⾏，避免资源冲突。注意锁过期时间设置要合理，不然可能误删别⼈的锁。

3）排⾏榜或计数场景特别适合，ZSet⽀持按分数排序，微博热搜、游戏积分榜基本都这么⼲。

4）消息队列也能凑合⽤，通过 List 结构做简单的⽣产消费，但功能⽐不上 RocketMQ、Kafka 这种专业中间件，复杂场景还是得换。

5）限流经常结合Lua脚本做原⼦操作，⽐如统计1分钟内接⼝调⽤次数，超过阈值就拒绝请求，保护后端服务不被搞崩。

持久化场景要谨慎，RDB和AOF都有性能损耗，⼀般不拿它当主数据库⽤。临时数据、⾼频读写、需要快速响应的场景才是它的主战场。

## Redis中常⻅的数据类型有哪些？

Redis⽀持⼏种核⼼数据结构，每种都有明确的使⽤场景。

字符串（String）是最基础的类型，能存⽂本、序列化对象，也常⽤来做计数器。⽐如⽤ INCR 实现接⼝调⽤次数统计，简单⾼效。

列表（List）底层是双向链表，⽀持从头尾插⼊删除，适合做消息队列。但随机访问慢，⼀般不推荐当数组⽤。  
LPOP/RPOP 配合 LPUSH/RPUSH 能实现简单的⽣产消费模型。

集合（Set）是⽆序不重复的字符串集合，底层⽤哈希表实现，所以增删查都是 O(1)。可以⽤在⽤户标签管理、社交关系去重这些需要快速判断成员存在的场景。

有序集合（SortedSet）在Set基础上加了score排序，⽐如排⾏榜类需求，ZADD加数据，ZRANGE按排名取，性能很好。score可重复，member才是唯⼀键。

哈希（Hash）适合存储对象字段，⽐如⽤户信息，field对应属性名，value存值。相⽐直接序列化整个对象，可以单独更新某个field，省带宽也省内存。

## Redis Zset 的实现原理是什么？

Redis 的 Zset 为了适应不同场景，在底层⽤了两种编码实现，完全基于元素数量和⼤⼩动态切换。

当数据量⼩、成员⻓度短时，⽤ ziplist 存储。它把score和member连续存放在⼀段内存⾥，节省空间，插⼊删除快。⼀旦元素超过 zset-max-ziplist-entries （默认 128），或者任⼀ member 字符串⻓度超过 zset-max-ziplist-value （默认 64 字节），就转成 跳表（skiplist） 加哈希表的组合。

跳表是核⼼，解决有序问题。它有多层链表，最底层按score升序存所有元素，上层是索引，每次查询像“电梯式”快速下落，时间复杂度稳定O(logN)。Redis的skiplist是单向后指针，但带反向遍历能⼒，⽀持ZREVRANGE 。

哈希表也不能少，它保存member到score的映射，确保 ZSCORE 查询是O(1)，避免在跳表⾥线性查找。

所以最终结构是：⼀个 zset 对象同时包含⼀个跳表和⼀个哈希表，空间换时间。⽐如你在做排⾏榜， ZADDuser:ranking 100 u1 ，member 和 score 会同时写⼊这两个结构。

这种设计在性能和内存间做了折中，⼩数据⽤ziplist省内存，⼤数据⽤skiplist保效率。你⼀般不⽤关⼼切换过程，Redis ⾃动完成。

## 你在项⽬中使⽤的Redis客户端是什么？

项⽬⾥⽤ Redis 客户端，⼀般⾸选 Lettuce，尤其是 Spring Boot 2.0 之后的项⽬。它基于 Netty 实现，⽀持响应式编程，连接是⻓连接，多个线程可以共享⼀个连接，资源利⽤率⾼。

Jedis也⽤过，早期项⽬常⻅，但它默认是同步阻塞的，每个操作都独占⼀个连接，⾼并发下连接数容易打满。除⾮是特别轻量的场景，不然现在基本不选它了。

Lettuce 和 Spring Data Redis 配合起来特别顺⼿，配置简单，API 也清晰。⽐如⽤ ReactiveRedisTemplate 做响应式缓存，或者普通 RedisTemplate 操作字符串、哈希都没问题。

@Bean   
public RedisConnectionFactory redisConnectionFactory() {   
return new LettuceConnectionFactory(new   
RedisStandaloneConfiguration("localhost", 6379));   
}

遇到过⼀次连接泄漏，是因为⽤了Lettuce的异步API但没处理好Future回调，导致Netty线程堆积。后来统⼀⽤RedisTemplate 封装，避免直接操作底层连接。

1）⽣产环境⼀定要配连接池，Lettuce 虽然原⽣⽆连接池，但可以通过 LettucePoolingClientConfiguration启⽤。2）⼤key或频繁批量操作要控制粒度，避免阻塞主线程。3）开启SSL和设置超时时间是上线前的必备动作。

## Redis字符串类型的最⼤值⼤⼩是多少？

Redis的字符串类型最⼤能存512MB。

这个限制是硬编码在Redis源码⾥的，不是随便定的。你往⼀个key⾥塞超过512MB的数据，Redis直接拒绝，返回错误。这么做主要是为了防⽌单个value太⼤，把内存打爆，或者在⽹络传输时卡住整个实例。毕竟Redis是单线程处理命令的，⼀个超⼤value的读写可能让其他请求全部排队，延迟飙升。

⼀般情况下，我们也不会⽤ Redis 存这么⼤的数据。⽐如缓存⽹⻚内容、JSON 数据，通常都在⼏ KB 到⼏⼗ KB。真要存⼤⽂件，⽐如图⽚、视频，通常做法是把⽂件放在对象存储（⽐如 S3、MinIO），Redis 只存个 URL 或索引。

如果你看到有⼈把序列化后的⼤型对象塞进⼀个 key，那基本是设计问题。拆分结构、⽤哈希或者换存储更合适。

需要特别注意的是，虽然最⼤⽀持 512 MB，但⽣产环境建议单个 value 控制在 10 KB 以内。超过 100 KB 就算⼤ key了，容易引发慢查询和内存不均。

## 如何在Redis中实现队列和栈数据结构？

Redis本⾝不直接提供队列和栈的类型，但它的List结构天⽣适合做这个事。你⽤ LPUSH 和 RPOP 就能实现⼀个先进先出的队列，反过来 LPUSH 和 LPOP 就是栈的后进先出。

1）实现队列时，⽣产者⽤ LPUSH 往左边塞数据，消费者⽤ RPOP 从右边取。这样最早进的数据在链表尾部，最先被消费。如果担⼼ RPOP 在没数据的时候卡住，可以换成 BRPOP ，设置个超时时间，⽐如 BRPOP queue_key5 ，最多等 5 秒。

2）实现栈就更简单了， LPUSH 和 LPOP 都操作头节点，压栈和弹栈都在同⼀边，天然符合栈的⾏为。

不过实际项⽬⾥，光靠这两个命令可能搞不定复杂场景。⽐如消息丢了怎么办？这时候就得上RedisStreams，这是Redis5.0加的功能，专⻔⽤来做消息流处理。Kafka是重量级选⼿，如果你系统⾥已经⽤了Redis，那Streams基本就是⾸选，轻量⼜⽀持持久化、回溯、消费者组。

<!-- image-->

注意⼀点，List做队列时别⽤ LRANGE ⾃⼰轮询，太耗资源。让客户端阻塞等待才是正道。还有，如果需要确保消息不丢，记得配持久化策略，不然重启就没了。

## Redis String 类型的底层实现是什么？（SDS）

Redis⾥的String类型底层其实⽤的不是C语⾔原⽣的char数组，⽽是⾃⼰搞了⼀套叫SDS（SimpleDynamicString）的数据结构。这么做主要是为了解决C字符串在实际使⽤中的痛点，⽐如获取⻓度得遍历、没法安全拼接、容易缓冲区溢出这些。

SDS的结构很简单，核⼼就三个字段： len 记当前⽤了多少字节， free 记后⾯还剩多少空闲空间， buf[] 是真正的字符数组。因为存了 len ，所以 strlen 这种操作是 O(1) 的，压根不经过遍历。拼接字符串前它会先看free 够不够，不够就扩容，避免了溢出问题。

还有个关键点是 SDS 在修改时会做空间预分配和惰性释放。⽐如你追加内容，它不会刚好分配你需要的⼤⼩，⽽是多分⼀点，下次再改就能省掉⼀次内存调整。删数据时也不⽴刻 free ，留着 free 字段⾥，⽅便后续复⽤。

代码⻓这样：

struct sdshdr {   
int len;   
int free;   
char buf[];   
};

像Redis做RDB写⼊或⽹络传输时，经常要⼆进制安全地处理数据，SDS不依赖 \0 结尾，能存任意字节，这也是⽐C字符串强的地⽅。

## 如何使⽤Redis快速实现排⾏榜？

⽤ Redis 做排⾏榜，核⼼是利⽤ Sorted Set 这个数据结构。它天然⽀持按分数排序，增删改查都是 O(log N)，性能完全够⽤。

1）每个玩家的得分⽤ ZADD leaderboard {score} {player} 写⼊。后续更新直接覆盖同名 member，Redis会⾃动按新分排序。

2）查 Top 10 直接 ZRANGE leaderboard 0 9 WITHSCORES ，从⾼到低取前 10。如果要倒序（⽐如末尾排名），⽤ ZREVRANGE 。

3）想查某个玩家的排名， ZSCORE leaderboard player 拿分数，再⽤ ZRANK leaderboard player 拿正序 名次，或 ZREVRANK 拿倒序。

实际场景⾥，像游戏积分榜、直播热度榜、电商销量排⾏，基本都这么⼲。Redis的SortedSet在内存⾥维护跳跃表，查询快得⻜起，写⼊也⾼效。

代码⽰例：

// 添加或更新分数   
jedis.zadd("leaderboard", 95.5, "player1")   
// 获取 Top 10   
Set<Tuple> top10 = jedis.zrevrangeWithScores("leaderboard", 0, 9);

注意点：数据量特别⼤时，⽐如千万级⽤户，单个zset可能撑不住。可以按维度拆，⽐如分服排⾏榜，或者⽤zset+分⻚缓存组合⽅案。另外别忘了设过期时间，避免数据堆积。

## 如何使⽤Redis快速实现布隆过滤器？

布隆过滤器的核⼼是⽤多个哈希函数和位数组判断元素是否存在，Redis本⾝不直接⽀持位操作的复合结构，但可以⽤HyperLogLog 或 Bitmap 搭配外部逻辑来实现。实际项⽬⾥更常⻅的是⽤ Redis Module，⽐如 RedisBloom。

1）先说原理。布隆过滤器往⾥加数据时，会算出多个哈希值，对应到位数组的不同位置，把这些位设为1。查的时候看这些位是不是都是1，有⼀个是0就说明肯定不存在，全是1则⼤概率存在（有误判率）。

2）在Redis⾥搞这个，最省事的是加载RedisBloom模块。它提供了 BF.ADD 、 BF.EXISTS 这种命令，直接就能⽤。⽐如：

```elixir
BF.ADD user:exists "user123"
BF.EXISTS user:exists "user456"
```

背后 RedisBloom ⾃⼰管理位数组和哈希函数，你不⽤操⼼细节。

3）如果不允许装模块，就得⾃⼰⽤ setbit 和 getbit 模拟。⽐如⽤ key + offset 表⽰某个哈希位置，⾃⼰写逻辑算 n 个哈希值。但要注意控制 key 的粒度，别让单个 key 太⼤，不然搞不定。

典型场景是缓存穿透防护。像商品详情⻚查DB前，先过⼀遍布隆过滤器，99%的⽆效ID被挡掉，数据库压⼒直接降下来。

如何使⽤Redis统计⼤量⽤户唯⼀访问量（UV）？

⽤Redis做海量⽤户UV统计，直接存⽤户ID肯定搞不定，内存撑不住。⽐如1亿⽤户，每个ID存成字符串也得上百MB到GB级别，更别说重复访问还得去重。

这时候就得上 HyperLogLog。它是⼀种概率数据结构，专⻔⽤来做基数估算⸺也就是“不精确但误差可控”的去重统计。它的神奇之处在于，不管你是10万还是1亿⽤户，Redis⾥只占12KB内存。

底层原理是通过哈希函数把元素映射成⼆进制串，利⽤“前⾯连续零的个数”来估算整体分布，再⽤调和平均减少误差。官⽅说标准误差是0.81%，对⼤多数业务完全够⽤，⽐如活动⻚⾯、⼴告曝光这些场景。

代码⽤起来也简单：

```javascript
// pfadd key element
redisTemplate.opsForHyperLogLog().add("uv:page1", "user123");
// pfcount key
long uv = redisTemplate.opsForHyperLogLog().size("uv:page1");
```

还能合并多个统计值：

```javascript
// pfmerge destkey sourcekey [sourcekey ...]
redisTemplate.opsForHyperLogLog().union("uv:total", "uv:page1", "uv:page2");
```

注意点：HyperLogLog 不⽀持取出具体元素，也不能获取实时精确值。如果⾮要精确去重，还是得靠布隆过滤器 +Set或者下沉到Flink实时计算。

对于⽇活这种量级，单个HLL12KB，⼀天⼀个key，⼀年也就4MB左右，⾮常轻量。

## Redis中的Geo数据结构是什么？

Redis的Geo结构本质上是基于SortedSet实现的，⽤zset来存地理位置的坐标，把经纬度编码成⼀个score，查的时候靠范围查询搞定。

1）存的是某个地点的经度、纬度，以及⼀个名称（⽐如“北京西站”），实际存储时会把经纬度⽤Geohash编码转成⼀个 52 位整数作为 zset 的 score。

2）⽀持的核⼼命令有 GEOADD 、 GEODIST 、 GEORADIUS 等。⽐如 GEORADIUS city 116.4 39.9 10 km就是查坐标附近10公⾥内的所有点。

3）底层其实是 zset，所以可以⽤ ZRANGE 或 ZREM 直接操作，但⼀般不建议绕过 geo 命令。

适合做附近的打卡店、共享充电宝、⽹约⻋这些场景，像美团、滴滴早期都拿RedisGeo做过就近匹配。

有个坑要注意：经纬度不能超范围，经度-180180，纬度-85.051185.0511，超出会报错。另外精度问题也得注意，Geohash本⾝有边界误差，跨格⼦可能漏点。

## 代码⽰例：

GEOADD cities:geo 116.405285 39.904989 "beijing" GEORADIUS cities:geo 116.4 39.9 100 km WITHDIST

整个结构没单独的数据类型，压根不经过特殊编码，就是zset+geohash算法组合拳，脏活累活都让zset⼲了。

## Redis性能瓶颈时如何处理？

Redis 出现性能瓶颈，⼀般先看是 CPU、内存、⽹络还是磁盘成了短板。⼤多数情况瓶颈在单线程模型处理⼤量请求时的吞吐上限。

1）先⽤ INFO stats 和 redis-cli --latency 观察指标。如果 QPS 上不去但 CPU 没到顶，可能是⼤ key 或慢查询拖累。像 KEYS 这种阻塞命令得禁⽤，改⽤ SCAN 。

2）⼤ key 拆分是常⻅优化⼿段。⽐如⼀个包含 10 万元素的 hash，读写都慢。可以按业务维度拆成多个⼩ hash，或者⽤ Redis Hash 的 slot 机制分散。

3）数据结构选型也很关键。⽐如⽤ ZSET 做时间排序队列没问题，但如果频繁修改分数，O(logN)的复杂度在百万级数据下就明显了。这时候可以考虑降级为 LIST + 外部索引 ，或者引⼊RedisStreams，它更适合⾼吞吐的消息场景。

4）真扛不住就横向扩展。Redis Cluster 能⾃动分⽚，数据按 key 分布到 16384 个 slot，跨节点访问会重定向。不过multi-key 操作必须在同⼀个 slot，可以⽤ hash tag 强制路由，⽐如 user:{1000}:profile 和 user:{1000}:orders 。

5）极端场景下，本地缓存加⼀层 Caffeine 或 Guava Cache，把最热的数据挡在 Redis 前⾯。⽐如⽤户登录信息，  
99%请求集中在10%的key上，本地缓存能减少80%以上的远程调⽤。

## Redis 中原⽣批处理命令（MSET、MGET）与 Pipeline 的区别是什么？

原⽣批处理像把多个命令打包成⼀个请求发给Redis，MSET和MGET就是这种。Redis收到后可以⼀次性执⾏，⽹络来回只有1次，指令还是原⼦的，顺序执⾏不被打断。

Pipeline不⼀样，它不是命令，⽽是⼀种通信优化⼿段。客户端把⼀堆命令连续发出去，不⽤等每个响应。Redis还是⼀个个处理，但省掉了反复的⽹络等待时间。⽐如发100条GET，RTT是1ms，传统⽅式要100ms，Pipeline可能只要2ms（1次发送+1次回程）。

关键区别在于原⼦性和实现层级。MSET/MGET是服务端⽀持的单命令多操作，天然原⼦。Pipeline是客户端攒请求、批量发，服务端压根不经过“原⼦执⾏”这层逻辑，中间可能穿插别的客户端命令。

举个例⼦：⽤ Jedis 做 Pipeline，你写：

```java
Pipeline p = jedis.pipelined();
p.get("k1");
p.get("k2");
List<Object> resp = p.syncAndReturnAll(); // 批量获取结果
```

这期间其他客户端照样能写数据，没法保证这⼀组读的原⼦视图。

再⽐如，MSET最多⽀持1024个键，超了得拆；Pipeline理论上可以塞⼏千条不同命令，但得⾃⼰控制缓冲区⼤⼩，别把内存搞爆。

所以，要原⼦性批量读写⼩数据，⽤MGET/MSET。要是追求吞吐，操作之间不要求原⼦，⽐如缓存预热加载1w条数据，Pipeline 更合适。

## Redis主从复制的常⻅拓扑结构有哪些？

Redis主从复制的拓扑结构其实就那么⼏种常⻅模式，不同的场景下选择合适的结构能更好地扛住流量和保证可⽤性。

## 1）⼀主⼀从或者⼀主多从

这是最简单的部署⽅式。主节点负责写，从节点负责读，读写分离可以分担主库的压⼒。⽐如在电商⼤促时，⽤多个从库来应对爆发的查询请求。但主节点要是挂了，整个集群就写不了了，得靠 Redis Sentinel 或者⼿动切换。

## 2）树状主从（级联复制）

从节点下⾯再挂更下游的从节点，形成树形结构。这种适合跨机房部署，⽐如北京主节点同步到上海的中继节点，上

海再往下同步给多个本地从库，减少跨机房带宽压⼒。不过层级多了，数据延迟会逐层累积。

## 3）主-从-从（中间节点既是 slave 也是 master）

中间节点开启 replica-serve-stale-data 并允许被其他节点复制。它从上游同步数据，同时给下游提供同步服务。这种结构在⼤规模读场景⾥很实⽤，⽐如⽤Redis做缓存集群，前端业务直接连末端从库。

要注意的是，所有这些结构⾥，主节点始终是唯⼀的写⼊点，复制都是单向的。故障转移需要外部⼲预，除⾮你搭了Sentinel 或者 Cluster 模式。

## Redis List 类型的常⻅操作命令有哪些？

Redis 的 List 类型底层⽤双端链表或压缩列表实现，适合做消息队列、最新消息排⾏这类功能。

## 1）插⼊类命令

往列表头部或尾部塞数据。 LPUSH key value [value ...] 从左边加元素， RPUSH key value [value...] 从右边加。⽐如⽤ LPUSH news:latest "breaking" 把突发新闻推到列表头。

## 2）弹出和读取类命令

拿数据但不删⽤ LINDEX key index ，按位置查。想删并返回就⽤ LPOP key 或 RPOP key ，分别从左右两端取出。常配合 LPUSH + RPOP 做先进先出队列。

## 3）阻塞操作

怕消费者空转可以加个等待时间。 BLPOP key [key ...] timeout 在指定 key 上阻塞式取值，超时⾃动返回，避免客户端频繁轮询。

## 4）范围与⻓度控制

看⼀段内容⽤ LRANGE key start stop ，⽐如 LRANGE news:latest 0 9 拿前⼗条。设最⼤⻓度可以⽤LTRIM key start stop ，防⽌列表⽆限膨胀。

有个坑得注意：虽然⽀持随机访问，但越靠后性能越差，毕竟底层不是数组。⾼频随机读的场景别硬扛，换 SortedSet 更合适。

## Redis中如何保证缓存与数据库的数据⼀致性？

缓存与数据库的⼀致性问题，本质上是在写操作发⽣时，如何让缓存和DB的状态保持同步。现实中没有完美⽅案，只有权衡。

## 1）先更新DB，再删除缓存（推荐）

这是CacheAsidePattern的标准做法。写请求来临时，先更新数据库，然后把缓存删掉。下次读请求会触发⼀次缓存重建。这种策略下，缓存不⼀致的时间窗⼝很短，且在⾼并发场景下相对安全。⽐如⽤户信息更新，先改 MySQL，再删 Redis ⾥的 user:1001。

## 2）先删缓存，再更新DB（有⻛险）

如果删完缓存后，还没来得及更新DB，这时⼀个读请求进来，就会把旧数据从DB加载到缓存，导致脏数据。这种情况在⾼并发下可能持续⼏毫秒，但确实存在。

## 3）延迟双删（缓解⽅案）

针对上⾯的问题，可以在更新 DB 前先删⼀次缓存，更新完 DB 后再 sleep ⼏百毫秒，再次删除缓存。虽然能降低脏数据概率，但sleep时间难控制，⼀般只在强⼀致性要求⾼且数据变更频繁的场景⽤，⽐如库存系统。

## 4）通过 Binlog 异步处理（解耦）

像阿⾥开源的 Canal 可以监听 MySQL 的 Binlog，把数据变更事件发到 MQ，由消费者去清理或更新缓存。这种⽅式完全解耦，适合复杂系统，⽐如订单状态变更同步到缓存。

<!-- image-->

最终建议：优先⽤“先更新DB，再删缓存”，配合缓存过期时间兜底。真要强⼀致，就得上分布式锁或者版本号机制，但性能代价⼤，多数业务没必要。

## Redis 中的 Ziplist 和 Quicklist 数据结构的特点是什么？

Ziplist是Redis早期⽤来存储⼩对象的⼀种紧凑内存结构，它把数据连续存储在⼀块内存⾥，没有指针节点开销。这种设计省空间，但插⼊删除要移动元素，平均 O(n) 时间成本。当 list 或 hash 的元素少、值⼩的时候，Redis 会⽤ziplist 来编码，⽐如 list-max-ziplist-size 控制节点数或⼤⼩。

后来发现ziplist扩容缩容容易触发连锁更新，性能不稳定，尤其在⼤列表场景下压根不经过修改就可能引发内存重排。所以 Redis 3.2 开始⽤ Quicklist 替代 ziplist 实现 list 类型。

Quicklist本质是个双向链表，每个节点存的是ziplist。相当于把⼀个⼤的ziplist拆成多个⼩段，每段独⽴维护。这样既能保留ziplist内存紧凑的优点，⼜把修改操作控制在局部，避免整体搬移。你可以通过 list-max-ziplist-size 调整每个节点的 ziplist ⼤⼩，还能⽤ list-compress-depth 对两端节点做 LZF 压缩，节省内存。

1）Quicklist 减少了单次操作的影响范围，插⼊删除只影响当前 ziplist ⽚段

2）⽀持压缩，冷数据可以进⼀步降低内存占⽤

3）相⽐纯ziplist，稳定性更好，适合⽣产环境⻓期运⾏

<!-- image-->  
现在 hash、zset 等类型的⼩对象也倾向⽤ ziplist 编码，但 list 类型已经统⼀⾛ Quicklist 了。

## Redis复制延迟的常⻅原因有哪些？

Redis 复制延迟其实是主从架构⾥挺常⻅的问题，⼀旦出现可能影响数据⼀致性和故障切换。排查的时候⼀般从这⼏个层⾯来看。

⽹络带宽跑满是最直接的原因，主节点写⼊量⼤时，RDB快照或命令流同步会占⽤⼤量带宽，从节点拉取数据就跟不上了。⽐如主库每秒写10MB，但跨机房的链路只有20Mbps，压根不经过计算就肯定积压。

主节点CPU或磁盘压⼒⼤也会拖慢复制。像执⾏ SAVE 或后台 bgsave ⽣成RDB时，⼦进程和主进程争抢CPU和磁盘IO，导致主线程处理客户端请求和发送复制流变慢。同样，AOF⽇志刷盘策略设成 everysec 或always ，磁盘写不过来也会影响整体响应。

从节点本⾝性能不⾜同样会成为瓶颈。⽐如它的CPU不够强，解析RDB或处理命令流的速度跟不上主节点⽣成的速度，或者内存不⾜触发swap，访问速度断崖式下跌。

还有就是单线程复制的问题。Redis主从复制是单主从链路，即使主节点能发得快，从节点处理慢就会形成堆积。如果拓扑是级联的，中间节点延迟会逐层放⼤。Kafka的消费者组能并⾏消费，但Redis从节点只能单线程replay命令，这个阻塞模型是根本限制之⼀。

1）检查主节点写⼊QPS和数据变更量

2）观察⽹络监控是否达到上限

3）排查主从节点的 CPU、内存、磁盘 IO 使⽤率

4）查看 Redis ⽇志是否有 Sync failed 或 repl backlog 相关警告

Redis事务与关系型数据库事务的主要区别是什么？

Redis的事务和MySQL这类关系型数据库的事务，看着名字差不多，其实差别挺⼤的。最根本的⼀点是，Redis不⽀持回滚。

你把⼏个命令塞进 MULTI 和 EXEC 之间，Redis会按顺序把它们排队，等 EXEC ⼀发，就⼀股脑执⾏下去。哪怕中间某个命令出错了，⽐如对⼀个字符串类型执⾏ HGETALL ，前⾯已经执⾏的命令也不会撤掉，后⾯的命令照样继续跑。这跟MySQL⾥ BEGIN 和 COMMIT 包住的操作完全不同，MySQL出错可以 ROLLBACK ，所有变更都能撤销。

另⼀个关键区别是隔离性。Redis 是单线程处理命令的，所以事务⼀旦开始执⾏，就不存在并发⼲扰的问题。它靠这个实现了“串⾏化”调度，压根不经过锁机制。⽽ MySQL 要靠 MVCC 或锁来保证不同事务之间的隔离级别。

再就是原⼦性理解不⼀样。Redis的原⼦性指的是事务⾥的命令要么都排队成功、要么都不执⾏（⽐如 EXEC 前断了），但不保证每个命令逻辑上正确。MySQL的原⼦性是在存储引擎层做的，配合⽇志机制确保数据可恢复。

如果你需要类似“回滚”的能⼒，得靠 WATCH 监视键的变化，在提交前检测有没有被其他客户端改过，有变动就放弃执⾏。这其实是乐观锁的思路，像⽤Redis做库存扣减时就得这么搞。

<!-- image-->

简单说，Redis事务更像是“打包执⾏+有限⼀致性保障”，脏活累活都靠应⽤层兜底。

## Redis Cluster 模式与 Sentinel 模式的区别是什么？

Redis 的⾼可⽤⽅案⾥，Cluster 和 Sentinel 是两种常⻅模式，解决的问题有重叠但定位完全不同。

Sentinel本质是做⾼可⽤监控与故障转移。它不负责数据分⽚，所有主从节点存的是⼀份数据。当主节点挂了，Sentinel 集群会选举出⼀个新主，客户端通过监听通知切换地址。整个过程对应⽤有⼀定感知，⽐如连接闪断、短暂只读。典型部署是3个Sentinel节点+1主1从或更多从，像Codis就依赖这种架构做代理层后端。

Cluster则是原⽣的分布式⽅案，核⼼是数据分⽚和去中⼼化。16384个哈希槽把数据分散到多个主节点，每个主可以带从节点做⾼可⽤。请求先根据 key 计算 slot，再路由到对应节点。客户端要么直连，要么通过 smart 客户端⾃动重定向。扩容缩容靠迁移slot实现，⽐如RedisShake可辅助迁移。

两者最⼤区别在于是否分⽚。Sentinel模式下数据全量复制，容量受限于单机；Cluster能横向扩展，扛住⼏⼗GB到TB级数据。但Cluster运维复杂，跨slot的事务和批量操作受限；Sentinel架构简单，适合中⼩规模场景。

选型上，数据量⼤、需要⽔平扩展直接上Cluster；追求稳定简单，数据量不⼤，⽤Sentinel搭配客户端或代理更省⼼。

## Redis 的 ListPack 数据结构是什么？

从 Redis 7.0 开始，ListPack 成为了 Hash 和 ZSet 内部结构的默认编码之⼀，⽤来替代逐渐暴露短板的 ZipList。

它本质是⼀个紧凑的、连续内存存储的序列化结构，把多个⼩元素挨着存，省去了指针开销。每个元素直接存⾃⼰的内容和⻓度，读的时候按格式⼀步步解析出来。这种设计让内存利⽤率特别⾼，适合存短字符串或整数这类⼩数据。

相⽐⽼将ZipList，ListPack做了关键改进。ZipList在修改中间元素时可能触发连锁更新，⼀个改动态⻓字段的操作可能波及后⾯所有节点，性能不可控。⽽ListPack每个元素头⾥记录的是⾃⼰占⽤的总字节⻓度，修改只影响当前项，不会扩散，稳定性强得多。

不过它也有硬伤，就是所有操作都是O(n)的。查第5个元素？只能从头开始⼀个个跳。所以官⽅⽤它也是有前提的只在元素个数少于 512 个，且每个值⼤⼩不超过 64 字节时启⽤，超出就切到 Hash Table 或 SkipList。

代码层⾯你看不到直接操作ListPack的API，它是完全内部的。但你可以通过配置控制切换阈值：

listpack-max-listpack-size 512   
listpack-max-listpack-entries 64

实际场景中，像⽤ZSet做滑动窗⼝限流，或者Hash存⽤户会话的⼩属性，只要数据够⼩，Redis就会⾃动⽤ListPack编码，内存能省下30%以上。

<!-- image-->

整个结构每次变更都要重新分配内存，所以不适合频繁修改的⼤列表。它的定位很明确：⼩数据、⾼密度、低频修改的冷热数据混合场景下的内存优化利器。

## Redis中的内存碎⽚化是什么？如何进⾏优化？

内存碎⽚化指的是Redis分配的内存中，存在⼤量不连续的⼩块空闲内存，导致⽆法有效利⽤。即使总空闲内存⾜够，也可能因为没有连续的⼤块内存⽽⽆法分配给新数据。

Redis 使⽤ jemalloc 作为默认内存分配器，它会按不同⼤⼩的块进⾏内存管理。随着数据频繁增删改，⼩块内存被释放后可能散布各处，形成碎⽚。内存碎⽚率通过 mem_fragmentation_ratio 指标体现，计算⽅式是：

used_memory_rss / used_memory

接近1.0：理想状态

⼤于1.5：可能存在严重碎⽚

⼩于 1.0：说明部分内存被交换到磁盘，性能已受损

## 优化⼿段主要有三种：

1）启⽤ 内存碎⽚⾃动回收。从 Redis 4.0 开始⽀持 activedefrag yes 配置，配合 active-defrag-ignore-bytes 和 active-defrag-threshold-lower 等参数，在运⾏时逐步整理碎⽚，但会消耗额外 CPU。

2）应⽤层控制键值⼤⼩⼀致性。避免频繁创建和删除⼤对象，尤其是⼏KB到⼏⼗KB的中间尺⼨对象，这类最易造成 jemalloc 分配失衡。

3）极端情况下采⽤重启重建。通过RDB或AOF⽂件恢复数据，重新加载时内存布局更紧凑。⽐如使⽤主从切换或集群迁移实现⽆感重启。

代码层⾯注意批量操作，减少频繁⼩写⼊：

```javascript
// 批量插⼊⽐单条循环⾼效得多
for (int i = 0; i < keys.length; i++) {
pipeline.set(keys[i], values[i]);
}
pipeline.sync();
```

## 在Redis集群中，如何根据键定位到对应的节点？

Redis 集群通过 ⼀致性哈希的变种算法来定位键所在的节点，但不是传统的⼀致性哈希，⽽是⽤了“哈希槽”（hashslot）机制。

1）Redis集群总共定义了16384个哈希槽。每个键通过CRC16算出⼀个0到65535的哈希值，再对16384取模，确定属于哪个槽。

2） 每个主节点负责⼀部分哈希槽。⽐如有 3 个主节点，槽可能是这样分配：节点 A 负责 05500，B 负责  
550111000，C 负责 11001\~16383。

3） 定位过程是客户端直接计算的。客户端拿到 key 后，算出 hash slot，然后查本地缓存的 slot -> node 映射表，就知道该发给哪个节点。

如果映射关系变了，⽐如扩容或缩容，节点会返回 MOVED 重定向，告诉客户端新位置。客户端更新本地映射后，后续请求就直接⾛新路由。

这种设计让集群具备去中⼼化特性，路由逻辑压根不经过中间代理，全靠客户端+重定向同步元数据。

要注意的是，涉及多个 key 的操作必须在同⼀个 slot，否则会报错。可以⽤哈希标签强制多个 key 落在同⼀ slot，⽐如 {user1000}.profile 和 {user1000}.orders 。

## 说说 Redisson 分布式锁的原理?

Redisson的分布式锁核⼼是基于Redis的 Lua 脚本和 Redis 单线程特性来保证原⼦性，同时⽀持可重⼊、锁续期等⾼级功能。

客户端加锁时，会通过⼀段Lua脚本向Redis写⼊⼀个hash结构，key是锁名，field是当前线程的唯⼀标识（⽐如UUID+threadId），value是重⼊次数。如果key不存在，就设置过期时间防⽌死锁；如果已存在且field匹配，就将value 加⼀，实现可重⼊。

解锁同样是Lua脚本操作，先校验threadId是否匹配，不匹配直接返回失败；匹配则将重⼊数减⼀，减到0就删除key 并释放锁。

最关键是锁续期机制，也就是看⻔狗（Watchdog）。当客户端拿到锁后，会启动⼀个后台任务，每过1/3过期时间就检查锁是否还被持有，如果还在⽤就⾃动延⻓TTL，避免业务还没执⾏完锁就过期了。

这种设计让客户端不需要⼿动管理超时，只要线程活着就能保住锁。像 RLock rlock = redisson.getLock("order");  
rlock.lock(); 这样简单调⽤背后其实已经包含了⽹络通信、脚本执⾏和定时任务调度这些脏活累活。

使⽤场景上，适合订单扣减、库存超卖这类强⼀致性要求的场景，但要注意⽹络分区下可能丢失锁的问题，极端场景建议结合RedLock模式，不过⼀般单Redis实例配合合理超时也能扛住⼤部分情况。

## 为什么RedisZset⽤跳表实现⽽不是红⿊树？B+树？

Redis的Zset选择跳表（SkipList）实现，主要是在读写性能、实现复杂度和范围查询之间找了个好平衡。

1）跳表在平均情况下，插⼊、删除、查找都是O(logn)，虽然最坏情况可能退化⼀点，但随机层数设计让它⼤概率保持均衡，不像红⿊树那样需要频繁旋转维持平衡。你想想，每次插⼊都要左旋右旋，写放⼤严重，对Redis这种⾼并发场景来说，脏活累活越少越好。

2）范围查询是硬需求，⽐如 ZRANGEBYSCORE 。跳表天然⽀持双向链表+多层索引，指针直接串着，遍历效率⾼。红⿊树做中序遍历也可以，但得靠额外数据结构辅助，代码复杂。B+树倒是擅⻓范围扫描，但它是为磁盘IO设计的，⼀个节点对应⼀⻚，内存⾥⽤反⽽有额外指针开销，没必要。

3）跳表代码实现简单，调试容易。Redis强调稳定和可维护，不⽤搞复杂的树平衡逻辑，开发成本低。⽽且实测性能不输红⿊树，甚⾄在并发插⼊时表现更好。

<!-- image-->

你看这个结构，⼀层层往下筛，查得快，删增也⽅便，指针⼀改就⾏。Redis要的就是这种“够快、够稳、别太复杂”的⽅案。

## Redisson 看⻔狗（watch dog）机制了解吗？

Redisson的看⻔狗机制是解决分布式锁⾃动续期的关键设计，主要针对业务执⾏时间不确定的场景。

你拿到锁之后，如果业务还没处理完，锁就过期了，那其他线程就能进来，这显然不⾏。Redisson会在后台起⼀个Watch Dog 线程，默认每 10 秒检查⼀次，只要线程还持有这个锁，它就会⾃动把锁的过期时间延⻓到 30 秒（基于默认的 lockWatchdogTimeout 配置）。这个动作完全由客户端⾃⼰触发，压根不经过业务逻辑⼲预。

这个机制只在没给锁设置超时时间的时候⽣效。⽐如你⽤的是 lock() ⽽不是 tryLock(10,TimeUnit.SECONDS) 。⼀旦指定了超时时间，就靠你⾃⼰控制节奏了，看⻔狗不会介⼊。

实际使⽤中，像 RLock rLock = redisson.getLock("order"); rLock.lock(); 这样调⽤后，续期就是透明的。但要注意，如果 Redisson 实例宕了，Watch Dog 也跟着挂，所以依赖的是客户端的存活状态。

常⻅问题是在集群故障转移时可能出现多个客户端认为⾃⼰持有锁的情况，这时候就得靠RedLock或者更严格的fencing token 机制来兜底。

## 如何解决 Redis 中的热点 key 问题？

热点 key 问题说⽩了就是某个 key 被疯狂访问，QPS 可能上⼗万，直接把 Redis 实例的 CPU 或⽹卡打满，甚⾄拖垮整个服务。

1）先定位。⼀般通过 redis-cli --hotkeys 或监控系统（⽐如⽤ Prometheus + Grafana）看 key 的访问频率。  
⽣产环境建议在 proxy 层（⽐如 TendisProxy 或 Codis）埋点统计 top N 热 key。

2）解决思路不是单⼀的，得组合拳。

本地缓存是第⼀道防线。应⽤节点⽤Caffeine或GuavaCache把热key缓⼀份，设置短过期时间（⽐如1\~2秒），这样⼤部分请求就压根不经过⽹络到Redis。注意缓存穿透问题，可以⽤布隆过滤器兜底。

3）拆分key也是常⽤⼿段。⽐如原来⼀个key存全量数据，改成key_1、key_2分⽚存储，访问时随机或轮询拉取，把压⼒分散。适⽤于静态资源类场景，⽐如⾸⻚ banner。

4）Redis 侧可以做多副本。⽐如给这个 key 单独起⼀个只读副本集群，或者利⽤ Redis Cluster 的 replica 只读节点分流读请求。

5）极端情况，写扩散。⽐如把热 key 的值推送到所有客户端内存⾥，靠消息中间件（⽐如 Kafka）通知更新。这招重运维，搞不定⼀致性别轻易上。

## Redis为什么这么快？

Redis快不是单⼀原因造就的，是多个设计选择叠加的结果。很多⼈第⼀反应是“因为内存”，但这只是基础，真正关键的是它怎么利⽤这个基础。

⾸先，数据存在内存⾥确实让访问速度上了个台阶，读写都在纳秒到微秒级。但光这样还不够，⽐如你⽤Java写个Map 存数据，也快，但扛不住并发请求。Redis 的多路复⽤ I/O 模型才是让它能同时处理⼏万连接的核⼼。

它⽤epoll（Linux）这类机制，⼀个线程就能监听⼤量socket连接，有数据才处理，压根不经过阻塞等待。像Tomcat那种每个请求起个线程的⽅式，在⾼并发下线程切换开销直接搞垮性能，⽽Redis单线程处理命令，避免了上下⽂切换和锁竞争，脏活累活都省了。

当然，单线程也有前提：命令执⾏必须⾜够快。所以你得注意别⽤ KEYS \* 这种慢操作，⼀执⾏全库卡住。官⽅推荐⽤ SCAN 代替。

数据结构上，Redis 直接基于 C 语⾔实现紧凑结构，⽐如 SDS 字符串⽐普通字符串少内存拷⻉，哈希表查找接近O(1)，这些细节累积起来也让响应更快。

再往后看，像Pipeline批量发命令、主从复制异步同步、RDB快照fork⼦进程由操作系统做写时复制，都是围绕“减少阻塞”做的权衡。

<!-- image-->

总结⼀句：内存 + I/O 多路复⽤ + 单线程 + 精简数据结构，这套组合拳打下来，才让 Redis 能轻松扛住 10w+ QPS。

## 为什么Redis设计为单线程？6.0版本为何引⼊多线程？

Redis的单线程模型其实指的是它的核⼼⽹络I/O和命令执⾏流程由⼀个线程串⾏处理。这么设计最直接的原因是，避免锁竞争带来的复杂性和性能损耗。内存操作本⾝极快，如果命令处理再⽤多线程加锁，上下⽂切换和同步开销反⽽可能压倒收益。

尤其是在10Gbps⽹络下，Redis处理简单命令的瓶颈通常不在CPU，⽽在于⽹络读写。所以早期版本选择⽤I/O多路复⽤+单线程事件循环，像Redis这种以微秒级响应为⽬标的系统，逻辑越简单越可控。

但问题出在⾼并发场景下，⽹络 I/O 成了新瓶颈。⽐如同时有上万连接发来请求，单线程读取 socket 缓冲区就成了串⾏步骤，CPU压根没被充分利⽤。

从Redis6.0开始，它引⼊了多线程来分担这部分脏活累活。具体做法是：主线程继续处理命令调度和执⾏，但把⽹络数据的读写拆给 I/O 线程池。你可以通过 io-threads 配置开启，⽐如设为 4，那么读请求就由 4 个线程并⾏从socket读数据，解析完再交回主线程统⼀执⾏。

// redis.conf 关键配置   
io-threads 4   
io-threads-do-reads yes

注意，命令执⾏依然在主线程，保证了原⼦性。多线程只解决“数据搬⼊搬出”的问题。实测在多核机器上，开启4线程能提升吞吐近⼀倍。

1）单线程为规避锁开销，依赖内存速度和I/O多路复⽤

2）6.0多线程仅⽤于⽹络I/O，不碰命令执⾏

3）适合⾼并发、多核环境，⼩并发开多线程反⽽增加切换成本

## Redis 的 hash 是什么？

Redis 的 hash 本质上就是⼀个字段和值的映射表，类似 Java ⾥的 Map<String, String> 或 Map<String,Object> ，但它是存放在⼀个 key 下的结构。你可以⽤它来存储对象，⽐如⽤户信息，不⽤把整个对象序列化成⼀个字符串。

1）你往⼀个 hash ⾥塞数据，⽤的是 HSET user:1001 name "Tom" age "25" 这种命令，读的时候⽤ HGETuser:1001 name 。这样改某个字段特别⽅便，不⽤动整个对象。

2）底层实现上，Redis 会根据数据量⾃动切换两种编码⽅式。⼩的 hash ⽤ ziplist（压缩列表），内存紧凑，所有字段和值挨着存；当字段多了或单个值太⼤，⽐如超过64字节，或者字段数超过512个，就会转成hashtable，也就是真正的哈希表，读写都是 O(1)。

3）适⽤场景很明显，⽐如缓存⼀个商品信息，字段多但更新独⽴，⽤hash就很合适。像在电商系统⾥⽤Redis存商品详情，字段如price、stock、title各⾃更新互不影响。但如果你每次都读整个对象，直接⽤string存JSON反⽽更简单。

4）注意别滥⽤嵌套，Redis 不⽀持 hash 套 hash。你要存复杂结构，得⾃⼰拼 key，⽐如⽤ user:1001:profile 和 user:1001:settings 分开存。
