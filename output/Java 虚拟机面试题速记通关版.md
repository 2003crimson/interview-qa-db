## JVM⽅法区是否会出现内存溢出?

⽅法区在JVM⾥主要存类的元数据、常量池、字段⽅法信息这些。以前永久代（PermGen）时代，这地⽅确实会OOM，尤其是动态⽣成类的场景，⽐如早期⽤CGLIB做字节码增强时，加载太多类就容易把永久代打满。

JDK8开始，元空间（Metaspace）替代了永久代，这块内存挪到了堆外，直接⽤的是系统内存。默认情况下，元空间可以动态扩容，上限是系统可⽤内存。但如果你显式通过 -XX:MaxMetaspaceSize 设了个上限，那⼀旦加载的类太多超过这个值，照样会 OutOfMemoryError。

所以答案是：会溢出。尤其在以下场景：1）⼤量动态⽣成类，⽐如某些框架频繁做ASM字节码操作2）部署很多应⽤的服务器上，每个应⽤都有⼀堆类，⽐如上百个微服务模块热部署3）存在类加载器泄漏，⽼的ClassLoader卸不掉，对应的类元数据也回收不了

代码上没啥特别⽰例，但调优时注意这两个参数：

-XX:MaxMetaspaceSize=256m -XX:MetaspaceSize=128m

监控的时候关注 CommittedMBC 和 UsedMBC 这两个指标，突然涨得快就得查是不是有类加载⻛暴。

分析JVM性能，关键得看场景。如果是线上突发问题，Arthas是⾸选，不⽤重启应⽤就能直接连上去看堆栈、内存、线程，特别适合定位死锁或CPU突增。

## 什么条件会触发 Java 的 young GC？

年轻代空间不⾜时就会触发 young GC，这是最直接的条件。JVM 的堆被分成年轻代和⽼年代，对象优先在年轻代的Eden 区分配，当 Eden 区快满的时候，系统会进⾏⼀次 minor GC，也就是 young GC。

1）Eden区满了是主要触发时机。⽐如默认情况下Eden和两个Survivor区的⽐例是8:1:1，⼀旦Eden被填满，不管⽼年代还有多少空间，都会触发⼀次回收。

2）⼤对象直接进⼊⽼年代的情况也可能间接影响，但不会直接触发 young GC。如果频繁分配⼤对象导致⽼年代压⼒⼤，可能会加快 Full GC 的到来，但这不是 young GC 的触发条件。

3）代码⾥其实没法主动“控制”什么时候发⽣，只能通过对象分配⾏为影响。⽐如连续创建⼤量临时对象：

```javascript
for (int i = 0; i < 100000; i++) {
byte[] data = new byte[1024]; // 每次分配 1KB 对象
}
```

这种写法很快就能把 Eden 塞满，从⽽观察到 young GC 的⽇志。

young GC 的核⼼⽬标是清理掉那些朝⽣⼣死的对象，把还活着的对象挪到 Survivor 区或者晋升到⽼年代。整个过程采⽤的是复制算法，效率⽐较⾼，暂停时间短，所以设计上允许它频繁发⽣。

## JVM 的 TLAB（Thread-Local Allocation Buffer）是什么？

每个线程在堆上分配对象时，如果每次都去竞争共享的Eden区，那效率会很低。JVM为了减少锁争⽤，给每个线程单独划了⼀⼩块私有内存区域，这就是 TLAB。

它本质是Eden区⾥的⼀段缓存，线程可以快速在⾃⼰的TLAB中分配对象，不⽤加锁。只有当TLAB空间不⾜时，才会重新申请新的TLAB，这时候才需要同步。

1）TLAB 默认是开启的，由 -XX:+UseTLAB 控制

2）⼤⼩不是固定的，通过 -XX:TLABSize 可设置初始⼤⼩，JVM 也会动态调整

3）如果对象太⼤，直接在共享区分配，避免浪费TLAB剩余空间

代码层⾯你看不到直接操作TLAB的API，它是JVM⾃动管理的。但你可以通过GC⽇志观察它的使⽤情况：

-XX:+PrintGCDetails -XX:+PrintTLAB

⽇志⾥会输出每个线程的TLAB分配速率、浪费空间等信息，⽤来调优。

有个关键点：TLAB回收不是垃圾回收做的，⽽是随着线程结束或TLAB被填满后，整个归还给Eden区统⼀管理。所以它不解决对象存活问题，只解决分配时的并发冲突这个脏活累活。

<!-- image-->

TLAB在⾼并发创建对象的场景下特别有⽤，⽐如Dubbo这种RPC框架处理⼤量请求时，临时对象多，有TLAB能明显降低分配开销。

## 什么是 Java 的 PLAB？

PLAB 是 JVM 在多线程环境下为对象分配内存时⽤到的本地缓冲区，主要发⽣在新⽣代的 Eden 区。

多线程同时触发MinorGC时，每个线程都需要在Eden区分配对象空间。如果直接操作共享的Eden区，会因为竞争锁带来⼤量开销。JVM 为每个线程分配⼀块私有的⼩内存区域，也就是 PLAB（Thread Local Allocation Buffer），让线程先在⾃⼰的缓冲区⾥分配对象，这样就不需要频繁加锁了。

每个PLAB⼤⼩不固定，⼀般在⼏KB到⼏⼗KB之间，由JVM⾃动调整。当线程的PLAB⽤完后，会申请新的PLAB，旧的被回收或归还。如果对象太⼤，直接在共享区域分配，或者触发TLAB填充失败处理逻辑。

这种机制能显著减少多线程分配时的竞争，提升吞吐量。但也会带来⼀点内存浪费，⽐如PLAB剩余空间不够分配下⼀个对象，这块碎⽚就闲置了。JVM会控制这个浪费⽐例，默认不超过1%。

代码上我们⽆法直接操作PLAB，但可以通过参数调优：

-XX:+UseTLAB

// 开启 TLAB（默认开启）

// 设置初始⼤⼩

-XX:+PrintTLAB

// 打印 TLAB 使⽤情况，⽤于诊断

1）GC 线程也会有⾃⼰的 PLAB

2）PLAB仅⽤于对象分配，不⽤于晋升或⽼年代分配

3）所有⾏为由JVM⾃动管理，应⽤层⽆感知

## 为什么 Java 中某些新⽣代和⽼年代的垃圾收集器不能组合使⽤？⽐如 ParNew 和 Parallel Old

不同垃圾收集器之间能不能组合使⽤，关键看它们的 设计架构 和 并发模型 是否兼容。JVM 的 GC 实现不是随便拼凑的，每个收集器都有⼀套⾃⼰的⼯作⽅式，尤其是跨代引⽤处理和停顿控制这块。

1）新⽣代和⽼年代的收集器要能配合，得共享⼀套 GC 根扫描机制和线程协作模型。⽐如 CMS 和 ParNew 能搭，是因为 ParNew 专⻔加了对 CMS 的⽀持代码，两者都考虑到了并发阶段如何安全地处理跨代指针。

2）Parallel Scavenge 和 Parallel Old 是⼀对，它们共⽤⼀套⾃动调优策略和并⾏控制逻辑，追求的是最⼤吞吐量，压根不打算⽀持CMS或G1这类并发型⽼年代收集器。

3）ParNew虽然是并⾏的新⽣代收集器，但它只服务于CMS模式下的⽼年代回收。你没法⽤它配ParallelOld，因为后者完全没实现跟 ParNew 协作的接⼝，连触发机制都不⼀样⸺Parallel Old 是 STW 全堆回收，⽽ CMS 是并发标记。

4）从 JDK 8 开始，官⽅推荐直接⽤ G1，它把整个堆统⼀管理，不再分这种 tight-coupled 的组合。像 ZGC、Shenandoah更是彻底去掉分代概念的趋势。

JVM新⽣代垃圾回收如何避免全堆扫描？

新⽣代回收能⾼效运⾏，关键在于它压根不碰⽼年代的对象。JVM⽤了⼀种叫分代收集的设计，把堆分成新⽣代和⽼年代，⼤部分对象朝⽣⼣死，集中在新⽣代。

1）新⽣代回收采⽤复制算法，只扫描新⽣代区域。它从GCRoots出发，但有个前提：如果⽼年代对象引⽤了新⽣代对象，这个引⽤关系必须被记录下来，否则就会漏掉存活对象。

2）CardTable（卡表）就是⼲这事的。它把⽼年代内存划成512字节⼀⻚，⽤⼀个字节标记⻚是否“脏”。只要⽼年代对象修改了对新⽣代的引⽤，对应卡⽚就被标为 dirty。

3）YGC 时，除了常规的 GC Roots，还会把 dirty 的卡⽚对应的区域也作为 Roots 扫描，确保跨代引⽤不被遗漏。这样既不⽤全堆扫描，⼜不会误删存活对象。

像CMS、G1都依赖这套机制。G1虽然⾃⼰有RememberedSet，但原理类似，只是粒度更细。

整个过程新⽣代单独完成，停顿时间控制在10\~50ms级别，靠的就是这种隔离+增量更新的策略。

## 什么是 Java 中的 logging write barrier？

Java 中的 logging write barrier 其实是垃圾回收过程中⽤来追踪对象引⽤变化的⼀种机制，主要⽤在像 G1 或 ZGC 这类关注并发标记的收集器⾥。

它不直接“记录⽇志”到⽂件，⽽是把对象引⽤的修改，⽐如 obj.field = newRef ，这种写操作记下来。因为并发标记阶段⽤户线程还在跑，对象图可能随时变，writebarrier就是在每次引⽤字段被修改时插⼀段逻辑，把这次变更记录到⼀个队列⾥。

这些记录后续会被并发标记线程消费，确保新引⽤的对象不会被漏标，从⽽保证标记的准确性。你可以把它看作是GC对“谁改了引⽤”这件事的监控探针。

1）写屏障代码通常由JVM⾃动⽣成，不需要开发者⼲预

2）它带来的开销很⼩，但⾼频调⽤场景下仍会有⼀定性能影响

3）G1 使⽤ post-write barrier 来记录 card table，ZGC 则⽤ load barrier 配合指针着⾊

举个简单例⼦，G1 ⾥⼀旦发现某个 region 的引⽤被更新，就会通过 write barrier 标记对应 card，让后续 Remark 阶段能快速扫描脏卡。

<!-- image-->

这机制说⽩了就是为了解决“⼀边⼲活⼀边记账”的⼀致性问题，让GC能在不停顿的情况下安全完成标记。

## JVM垃圾回收调优的主要⽬标是什么？

JVM垃圾回收调优不是为了把GC时间压到零，那不现实。⽬标很实际：在应⽤的吞吐量、延迟和内存占⽤之间找到平衡点。

1）吞吐量优先的场景，⽐如离线计算任务，像Spark批处理这种，可以选G1或ParallelGC，⽬标是让⽤户代码跑得更久，GC停顿少打断。

2） 低延迟是关键的应⽤，⽐如交易平台下单链路，每次 GC 停顿必须控制在 100ms 内，这时候 ZGC 或 Shenandoah就更合适，它们能把STW（Stop-The-World）拆成⼩段，压根不经过⻓时间卡顿。

3）内存footprint⼩也很重要，特别是在容器化环境，K8s⾥跑着⼏百个Java实例，⽤ZGC虽然停顿短，但内存开销⼤，可能反⽽不如G1稳定。

调的时候常⻅翻⻋点是堆设太⼤，结果⽼年代回收拖不动，⼀次 Full GC ⼏秒直接超时。⼀般来说，新⽣代别超 4G，避免 Minor GC 时间过⻓。

重点盯住 GC ⽇志⾥的 Pause Time 和 Frequency，配合监控看 P99 延迟有没有⽑刺。调优到最后，其实是业务容忍度和硬件成本的权衡。

## 如何对Java的垃圾回收进⾏调优？

调优垃圾回收不是上来就调参数，⽽是先搞清楚应⽤的GC⾏为。⼤部分问题其实出在对象创建太猛，⽽不是GC本⾝不⾏。

1）先⽤ jstat -gc 或 jcmd <pid> GC.run_finalization 观察频率和耗时。如果 Young GC 超过 50ms 或频繁到⼏⼗毫秒⼀次，说明对象分配速率太⾼，得查代码⾥有没有短⽣命周期⼤对象。

2）⽼年代增⻓快？可能是内存泄漏，也可能是晋升太快。打开 -XX:+PrintGCDetails 看对象从Eden到Old的晋升⽇志。可以加 -XX:MaxTenuringThreshold=1 强制提前晋升测试是否扛得住。

3）停顿时间敏感的应⽤，⽐如接⼝响应要求200ms内，CMS已经过时了，直接上ZGC或Shenandoah。它们的暂停时间基本稳定在10ms以内，哪怕堆到32GB也压不垮。

// 启动参数⽰例：⽤ ZGC，堆设 8G

-XX:+UseZGC -Xmx8g -XX:+UnlockExperimentalVMOptions

4）别迷信“最⼤吞吐量”。吞吐型服务可以⽤ G1，但记得设置 -XX:MaxGCPauseMillis=200 ⽬标停顿，JVM 会⾃动调整分区回收数量。

真正要动⼿调的，⼀般就三个⽅向：控制对象分配速率、减少晋升压⼒、选对收集器。⼯具链推荐配合 Arthas 的vm.gc 命令做线上诊断，⽐ jstat 更直观。

## 常⽤的JVM配置参数有哪些？

JVM参数选对了，服务能少掉⼀半链路。先分三类来看，最常⽤的是内存相关。

堆内存⼀般⽤ -Xms 和 -Xmx 设成⼀样，避免动态扩容开销，⽐如 -Xms2g -Xmx2g。年轻代⼤⼩⽤ -Xmn，通常设为堆的1/3到1/2。如果对象多，可以调⼤⼀点。

垃圾回收器得看场景。响应优先⽤ G1，加 -XX:+UseG1GC 就⾏，再配 -XX:MaxGCPauseMillis=200 控制停顿时间。吞吐优先就上 ParallelGC，-XX:+UseParallelGC，适合后台批处理。ZGC 现在⽤得多，-XX:+UseZGC 能把 STW 压到10ms 内，但得 JDK 15+。

⽇志参数不能少。-Xlog:gc\* 开启 GC ⽇志，最好加上 time,uptime,level,tags 打全信息。线上出问题靠这个定位。

还有⼏个关键开关。-XX:+HeapDumpOnOutOfMemoryError ⾃动导出堆 dump，配合 -XX:HeapDumpPath=/path存⽂件。-XX:+PrintCommandLineFlags 启动时打印实际⽣效的参数，排查配置有没有被覆盖。

别乱调-XX:MaxMetaspaceSize，除⾮你真遇到元空间爆了。多数时候让它⾃动扩就⾏。

代码⽰例：

```batch
java -Xms4g -Xmx4g -Xmn2g -XX:+UseG1GC -XX:MaxGCPauseMillis=200 \
-Xlog:gc*:gc.log:time,uptime:filecount=5,filesize=100m \
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dump MyApp
```

## 编译执⾏与解释执⾏的区别是什么？JVM使⽤哪种⽅式？

Java代码的执⾏混合了编译和解释两种⽅式，得从整个流程来看。

1）源代码先由 javac 编译成字节码（.class⽂件），这个阶段是编译执⾏的⼀部分。但这⾥的“编译”不是直接⽣成机器码，⽽是⽣成⼀种中间形态的字节码，平台⽆关。

2）运⾏时JVM读取字节码，再通过解释器逐⾏解释成机器指令执⾏。这就是解释执⾏，启动快，但执⾏慢，因为每次都要翻译。

3）为了提升性能，JVM 还引⼊了 JIT（Just-In-Time）编译器。它会在运⾏时把热点代码（频繁执⾏的⽅法）直接编译成机器码缓存起来，下次调⽤就不⽤解释了，直接执⾏本地代码。

所以JVM实际上是“解释+编译”的混合模式。早期HotSpotVM就是靠这种策略兼顾了启动速度和运⾏效率。

<!-- image-->

像SpringBoot应⽤刚启动时接⼝响应慢，过⼀会⼉变快，就和JIT的预热过程有关。GraalVM提供的AOT（提前编译）可以进⼀步优化这个问题，把部分⼯作提前到构建阶段。

## 如何在Java中进⾏内存泄漏分析？

内存泄漏分析其实分两步⾛，先定位现象，再找根因。

应⽤跑着跑着 Full GC 频繁，⽼年代使⽤率蹭蹭往上涨，基本就能怀疑内存泄漏了。这时候得抓堆转储⽂件，⽤ jmap命令就⾏，⽐如 jmap -dump:format=b,file=heap.hprof <pid> ，拿到 .hprof ⽂件后丢给分析⼯具。

主流⼯具就两个，MAT和JVisualVM。MAT对泄漏感知更强，能⾃动给出"LeakSuspects"报告，直接告诉你哪些对象占得多、谁在强引⽤它们。⽐如你看到⼀堆HashMap\$Entry挂着成千上万的业务对象，⽽GCRoots是某个静态缓存，那问题⼋成出在缓存没设上限或者没做清理策略。

常⻅泄漏场景也就那⼏类。静态集合类持有对象不放，⽐如publicstaticList缓存数据但不清空；监听器和回调注册后不注销，Spring⾥EventListener注解⽤多了容易踩这坑；还有线程池创建线程时，ThreadLocal没清理，堆栈⾥Thread 数量持续增⻓，最后 OOM。

代码层⾯要防泄漏，核⼼是控制⽣命周期。集合类记得考虑 WeakHashMap 或 Guava Cache 这种带回收策略的；⽤try-with-resources 确保流关闭；⾃定义线程池别瞎 new Thread，⽤ ThreadPoolExecutor 显式管理资源。

<!-- image-->

说到底，内存泄漏不是JVM的锅，是代码⾥那些“忘了释放”的引⽤在搞事。

## JVM由哪些部分组成？

JVM 主要由类加载⼦系统、运⾏时数据区、执⾏引擎和本地库接⼝组成。

1）类加载⼦系统负责把 .class ⽂件加载到内存。它包含加载、验证、准备、解析和初始化五个阶段。⽐如 SpringBoot 应⽤启动时，就是靠它把成千上万个类读进 JVM。

2）运⾏时数据区是核⼼内存布局，分为⽅法区、堆、虚拟机栈、本地⽅法栈和程序计数器。其中堆是最⼤的⼀块，存放对象实例和数组，GC主要就在这⾥⼲活。⽅法区存常量、静态变量、类信息，JDK8后⽤元空间实现，直接扔到了本地内存⾥。

3）执⾏引擎负责执⾏字节码。解释执⾏逐条翻译，JIT 编译则把热点代码编译成机器码缓存起来，像 HotSpot 就靠这个提升性能。GC线程也属于执⾏引擎的⼀部分，专⻔处理垃圾回收的脏活累活。

4）本地库接⼝（JNI）让Java调⽤C/C++代码。⽐如你⽤NIO操作⽂件，底层其实是通过JNI调⽤了操作系统API。

<!-- image-->

整个流程串起来：类加载器把字节码载⼊内存，执⾏引擎读取并运⾏，需要本地功能时通过JNI跳出去。堆和栈的划分决定了对象⽣命周期和线程隔离⽅式，这块搞不定，线上OOM问题基本扛不住。

## JVM有那⼏种情况会产⽣OOM（内存溢出）？

JVM产⽣OOM的情况主要集中在⼏个内存区域，每个区域的溢出都有特定场景和表现。

1）堆内存溢出是最常⻅的，对象持续创建但⽆法回收，最终超过 -Xmx 设置的上限。⽐如缓存没加过期策略，或者⼀次加载⼏百万条数据到 List ，很容易把堆撑爆。

2）虚拟机栈溢出⼀般由线程请求深度超过限制引起，典型就是递归太深或死循环。每个线程默认栈⼤⼩是1MB左右（取决于系统），线程数太多也会耗尽内存，这种情况其实是栈内存不⾜⽽不是堆问题。

3）⽅法区（元空间）溢出在Java8后主要是永久代被移除，改⽤本地内存存储类信息。如果动态⽣成⼤量类，⽐如CGLIB做字节码增强时没控制，元空间不断扩张⼜不卸载，就会OOM。

4）直接内存溢出发⽣在使⽤ ByteBuffer.allocateDirect() 时，这部分内存不受GC控制，也不算在堆内，靠-XX:MaxDirectMemorySize 限制。NIO使⽤不当，频繁分配直接内存且迟迟不释放，就可能触发。

代码⽰例：

// 直接内存溢出模拟  
for (;;) {  
ByteBuffer.allocateDirect(1024 \* 1024); // 每次分配 1MB  
}

这类问题线上排查得看 OutOfMemoryError 后⾯的提⽰，⽐如 "Java heap space"、"Metaspace"、"Direct buffermemory" 都能直接定位区域。

<!-- image-->

Java⾥的对象在虚拟机⾥⾯是怎么存储的？

Java对象在虚拟机⾥的存储，得从内存布局说起。对象创建后主要分布在堆上，⽽它的内存结构可以拆成三块：对象头、实例数据和对⻬填充。

对象头⾥存了两样东西，⼀个是MarkWord，⽤来放哈希码、GC分代年龄、锁状态这些信息；另⼀个是指向类元数据的指针，JVM靠它确定这个对象是哪个类的实例。如果是数组，这⾥还会多出⼀个记录⻓度的字段。

接下来是实例数据，这部分最实在，就是你定义的那些成员变量，按声明顺序排列，⽗类的变量也会包含进来。JVM会按 long/double、int、short/char、byte/boolean 这样的顺序重新排序，⽬的是为了内存对⻬，减少空间浪费。

最后是对⻬填充，不是必须的。因为 JVM 要求对象⼤⼩必须是 8 字节的整数倍，不够就得补上。

<!-- image-->

这种布局⽅式直接影响 GC 和并发性能。⽐如 synchronized 锁升级过程就会修改 Mark Word 的内容，从⽆锁到偏向锁、轻量级锁再到重量级锁，都是在这块做⽂章。理解这块结构，对排查竞争激烈时的性能问题很有帮助。

## JIT编译后的代码存在哪？

JIT编译后的代码存在代码缓存区（CodeCache），这是JVM堆外的⼀块内存区域，专⻔⽤来存放动态⽣成的本地机器码。

Java程序启动时解释器逐条执⾏字节码，热点⽅法被JIT识别并编译成机器码。这些机器码不是放在堆⾥，也不是⽅法区，⽽是直接刷进 Code Cache。下次调⽤这个⽅法，虚拟机就直接跳过去执⾏这段本地代码，压根不经过解释器，性能提升明显。

不同JVM实现对CodeCache的管理策略不⼀样。HotSpot默认⼤⼩⼏MB到上百MB不等，可以通过 -XX:ReservedCodeCacheSize 调整。⼀旦填满，JIT 编译就会停掉，后续⽅法只能解释执⾏，应⽤峰值性能会掉⼀截。

1）Client Compiler（C1）⽣成的代码相对简单，体积⼩，适合短⽣命周期的⽅法

2）Server Compiler（C2）或 Graal 编译出的优化程度⾼，代码更⻓，更容易撑满缓存

常⻅于⾼并发服务如 Dubbo 或 Spring Boot 应⽤跑久了出现 "CodeCache is full" ⽇志，这时候得看是不是编译策略不合理，或者缓存设太⼩。

## 说说Java的执⾏流程?

Java 程序跑起来其实就四步：写代码、编译、加载、执⾏。

你写的 .java ⽂件，先⽤ javac 编译成 .class 字节码。这⼀步不⽣成机器码，只⽣成⼀套能在任何平台跑的中间指令，保证了“⼀次编写，到处运⾏”。

字节码⽂件扔给JVM后，类加载器把它们按需加载进⽅法区。加载完，JVM启动main线程，程序计数器和虚拟机栈跟着初始化。每个⽅法调⽤对应⼀个栈帧，压到线程的栈上。

真正执⾏靠解释器和即时编译器（JIT）配合。解释器逐⾏读字节码解释执⾏，启动快但慢。JIT发现某些⽅法被频繁调⽤（⽐如循环⾥），就把它编译成机器码缓存起来，下次直接执⾏本地代码，这就是热点代码优化。

<!-- image-->

GC负责堆内存回收，线程私有的部分⽐如栈，随线程消亡⾃动释放。整个过程由JVM统⼀管控，开发者不⽤⼿动管内存布局和指令调度。

注意，JDK 8 之后元空间取代永久代，⽤的是本地内存，不再受 -XX:MaxPermSize 限制。

## JavaG1相对于CMS有哪些进步的地⽅?

G1出来就是为了解决CMS在⼤堆场景下停顿时间不可控的问题。CMS虽然能实现⼤部分并发回收，但停顿时间没法保证，G1 的⽬标是让你能指定 -XX:MaxGCPauseMillis=200，它就尽量在 200ms 内搞定⼀次 GC。

G1把整个堆拆成多个⼤⼩相等的Region，不再有固定的年轻代和⽼年代内存块，代可以动态伸缩。回收的时候优先挑垃圾最多的Region先清，这就是“Garbage-First”名字的由来。这样能在有限时间内尽可能多回收空间，做到可预测的停顿。

1）不再⽤ CMS 的 mark-sweep 算法，避免碎⽚问题。G1 在回收阶段会做部分整理，合并存活对象，减少后续 FullGC ⻛险。

2）Card Table 换成了 Remembered Set（RSet），每个 Region ⾃⼰维护谁引⽤了我。跨 Region 引⽤写屏障记录，避免扫描整个⽼年代。

3）并发标记阶段和 CMS 类似，但 G1 多了个“并发转移”阶段，真正回收时只选⼏个 Region 做 evacuation，复制到其他 Region，顺便整理内存。

4）CMS ⼀旦发⽣ Concurrent Mode Failure 就会退化成 Serial Old，整个应⽤卡死很久。G1 设计上更稳，配合Humongous Region 处理⼤对象，降低 Full GC 概率。

代码上基本不⽤调，G1 ⾃⼰根据停顿⽬标⾃适应调整回收策略。像 RocketMQ、Kafka 这些⼤堆服务现在基本都⽤ G1或 ZGC。

<!-- image-->

简单说，G1 ⽤ Region + RSet + 可预测停顿模型，把 GC 从“尽⼒⽽为”变成了“有承诺的服务”。

## Java是如何实现跨平台的？

Java的跨平台能⼒，关键在于JVM和字节码的设计。你写的是Java代码，但跑在不同系统上的不是它，⽽是编译后的 .class ⽂件。

1）Java源⽂件通过 javac 编译成字节码（.class），这玩意是中间指令，不依赖任何具体操作系统或CPU架构。

2）每个平台（Windows、Linux、macOS）都有对应的 JVM 实现。JVM 负责把字节码翻译成当前系统的机器指令，这个过程可以是解释执⾏，也可以通过JIT编译成本地代码来提速。

3）所以⼀次编写，到处运⾏⸺只要⽬标机器装了对应版本的 JVM，你的程序就能跑，底层差异全被 JVM 挡住了。

⽐如你在Mac上写的SpringBoot应⽤打包成jar，在Linux服务器上照样能⽤ java -jar 启动，压根不经过重新编译。

```java
// 编译后⽣成 Test.class
public class Test {
public static void main(String[] args) {
System.out.println("Hello, JVM");
}
}
```

不同⼚商的JVM实现⽐如HotSpot（Oracle）、OpenJ9（IBM），它们对字节码的优化策略不同，但都遵循同⼀个规范，保证⾏为⼀致性。

## JVM 的内存区域是如何划分的？

JVM内存区域划分，其实是为了⾼效管理程序运⾏时的数据。不同数据⽣命周期不⼀样，⽐如⽅法执⾏的局部变量和整个类的结构信息，肯定不能混着放。

线程私有的部分包括程序计数器、虚拟机栈和本地⽅法栈。程序计数器记录当前线程执⾏到哪条字节码指令了，线程切换回来能接着执⾏。每个⽅法调⽤时都会创建⼀个栈帧压⼊虚拟机栈，⾥⾯存了局部变量表、操作数栈、动态链接这些，⽅法执⾏完就弹出。本地⽅法栈则是为native⽅法服务的。

线程共享的区域主要是堆和⽅法区。堆是最⼤的⼀块，⼏乎所有对象实例都在这⾥分配内存。GC主要就是管这块区域，像G1、ZGC这些垃圾回收器优化的也是它。⽅法区存放类信息、常量、静态变量等，JDK8以后⽤元空间实现，放在本地内存⾥，避免永久代时代因加载类过多导致 OOM。

<!-- image-->

直接内存虽然不在JVM规范⾥定义，但NIO的ByteBuffer分配会⽤到，得⼩⼼OutOfMemoryError，毕竟不受堆⼤⼩限制。

## Java中有哪些垃圾回收算法？

Java的垃圾回收算法主要围绕怎么找垃圾、怎么清理垃圾展开。不同算法适合不同场景，⼀般CMS、G1这些收集器会组合使⽤多种算法。

## 1）标记-清除（Mark-Sweep）

先标记所有存活对象，然后统⼀回收未被标记的垃圾。最⼤的问题是会产⽣内存碎⽚，⽐如⽼年代⽤Serial收集器时就⽤这个算法，⻓时间运⾏后可能因为碎⽚触发 Full GC。

## 2）复制（Copying）

把内存分成两块，每次只⽤其中⼀块。当这⼀块满了，就把存活对象复制到另⼀块，然后清空原来的那块。效率⾼，不会产⽣碎⽚，但可⽤内存直接砍半。年轻代的 Minor GC 基本都⽤这个思路，⽐如 ParNew 和 G1 在年轻代阶段。

## 3）标记-整理（Mark-Compact）

标记过程和“标记-清除”⼀样，但后续不是直接清理，⽽是把存活对象往⼀端滑动，再清理边界外的内存。适合⽼年代这种对象多、回收少的场景，避免碎⽚问题。CMS 在并发失败降级后就会⽤这个算法做 Full GC。

## 4）分代收集（Generational Collection）

这不是具体算法，⽽是策略。基于对象⽣命周期分布：90%对象朝⽣⼣死。年轻代⽤复制算法，回收快；⽼年代⽤标记-清除或标记-整理。G1和ZGC都是基于分代思想演进出来的。

<!-- image-->

像 G1 会把堆拆成多个 Region，逻辑上保留分代，回收时优先选垃圾多的区域，实现“增量整理”。ZGC 和Shenandoah更激进，主打并发整理，停顿时间控制在10ms以内。

## Java中堆和栈的区别是什么？

Java ⾥堆和栈是两种不同的内存区域，分⼯明确。

栈主要⽤来存⽅法的局部变量、⽅法参数和返回地址。每个线程有⾃⼰独⽴的栈，⽣命周期和线程⼀致。基本数据类型（如int、char）和对象引⽤通常存在栈上，访问速度快，但空间⼩，⼀般就⼏MB。

堆则是所有线程共享的⼀块区域，⽤来存放对象实例。⽐如你 new 出来的对象，都分配在堆上。堆的⼤⼩可以很⼤，通常是⼏百MB到⼏个GB，由JVM参数控制。垃圾回收器主要管理的就是堆内存。

举个例⼦：

void method() {  
int a = 10; // a 在栈上  
Object obj = new Object(); // obj 引⽤在栈上，new Object() 实例在堆上  
}

⽅法执⾏完，栈帧弹出，a和obj这两个变量就没了，但堆⾥的对象能不能回收，得看有没有其他引⽤指向它。

栈不会发⽣GC，只有堆才会被垃圾回收。如果栈深度太深（⽐如递归没出⼝），会报StackOverflowError；如果堆内存不⾜，则抛 OutOfMemoryError。

简单说，栈管“临时变量”，堆管“对象本⾝”。⼀个⽅法调⽤的过程，其实是栈帧不断压⼊弹出的过程，⽽对象创建全靠堆撑着。

<!-- image-->

## 为什么Java新⽣代被划分为S0、S1和Eden区？

新⽣代这么划分，主要是为了⾼效处理对象的⽣命周期差异，⽤复制算法实现垃圾回收。

⼤多数对象朝⽣⼣死，刚创建就变成垃圾。Eden 区就是专⻔⽤来分配新对象的地⽅。当 Eden 满了，触发 MinorGC，把还活着的对象复制到S0或S1中的⼀个。

S0 和 S1 互为 From 和 To，每次 GC 时，存活对象从⼀个 Survivor 区（From）复制到另⼀个（To），同时年龄加 1。  
下⼀次 GC 时⻆⾊翻转。这样设计的好处是能⾃动整理内存，避免碎⽚。

对象在Survivor区每经历⼀次GC，年龄+1，达到阈值（默认15）就晋升到⽼年代。如果某次需要复制的对象太多，Survivor放不下，也会提前晋升。

这种分法让GC只在⼩范围内运⾏，速度很快。像CMS、G1这些收集器底层也借鉴了这个思路。

<!-- image-->

要是没有S0/S1的双缓冲机制，光靠Eden和⼀个Survivor，要么没法运作，要么效率低下。这两个区看着浪费空间，其实是为复制算法服务的关键设计。

## 什么是Java中的常量池？

Java⾥的常量池主要管两件事：类加载时的字⾯量和符号引⽤，还有运⾏时⽣成的字符串复⽤。

类⽂件⾥有个常量池，存着编译期确定的字⾯量，⽐如 "hello" 这种字符串，还有类名、⽅法名这些符号信息。  
JVM加载类的时候会把这部分搬到⽅法区，叫运⾏时常量池，属于元空间的⼀部分。

真正影响性能的是字符串常量池。它本质是个 HashMap<String, String> ，专⻔存字符串对象的引⽤，确保内容相同的字符串只保留⼀份。⽐如你写 "abc" ，JVM先去池⼦⾥找有没有，有就直接返回，没有就放进去再返回。这个池⼦从JDK7开始挪到了堆内存，⽅便GC管理。

通过 intern() ⽅法可以⼿动把字符串对象加⼊池中。⽐如 new String("abc").intern() ，如果池⾥没有"abc" ，就会把堆⾥这个对象的引⽤存进池⼦。

String a = "abc"; // 直接从常量池拿   
String b = new String("abc"); // 堆⾥新建对象   
String c = b.intern(); // 把 b 对应的值⼊池，返回池引⽤   
System.out.println(a == c); // true，a 和 c 都指向池中同⼀个

常量池能省内存，减少重复字符串创建，但intern操作本⾝有哈希计算和同步开销，频繁调⽤可能拖慢性能。

## 什么是 Java 中的 JIT（Just-In-Time）?

JIT其实就是Java虚拟机在程序运⾏时，把热点的字节码动态编译成机器码的过程。你写的Java代码先被javac编译成字节码，然后由JVM解释执⾏。但解释执⾏慢啊，所以JIT就来了。

它会监控哪些⽅法被频繁调⽤，也就是所谓的“热点代码”。⼀旦发现，就⽴⻢把这些字节码编译成当前CPU架构直接能跑的机器码，下次调⽤就直接执⾏本地代码，速度⻜起。

1）触发条件⼀般是⽅法被调⽤⼀定次数，⽐如默认是 10000 次（Client VM），这个叫热点探测

2）编译后的机器码缓存起来，但可能因为继承、类加载等变化⽽失效，需要重新编译

3）不同JVM实现有差异，HotSpot就⽤了分层编译：C1编译快但优化弱，C2优化强但耗时⻓，结合使⽤

long result = 0;   
for (int i = 0; i < n; i++) {   
result += i;   
}

不⽤JIT的话，Java性能压根没法跟C++这种静态编译语⾔⽐。有了它，很多场景下性能差距⼤幅缩⼩，尤其是⻓期运⾏的服务，⽐如 Tomcat、Spring Boot 应⽤。

不过JIT也有代价，编译过程本⾝要消耗CPU和内存，启动阶段还感受不到，这就是为什么有些服务有“预热”过程。

## 什么是 Java 的 AOT（Ahead-Of-Time）？

AOT指在程序运⾏前就把字节码编译成机器码，和传统的JIT（运⾏时编译）反过来。Java⻓期依赖JVM的即时编译，启动慢、内存占⽤⾼，尤其在云原⽣场景下成了短板。

GraalVM提供了native-image⼯具实现AOT编译，能把Java程序打成⼀个独⽴的可执⾏⽂件。这个过程会做静态分析，把⽤到的类、⽅法、反射信息全提前编译进去。结果是启动速度从秒级压到⼏⼗毫秒，内存占⽤也直接砍掉⼀⼤半。

但代价不⼩。⾸先，所有动态特性得⼿动配置，⽐如反射、动态代理、资源加载，都得通过配置⽂件告诉编译器。其次，不⽀持 Class.forName 这种运⾏时加载类的操作，连 java.lang.Thread 的某些 API 都受限。Spring Boot 早期版本完全跑不起来，直到推出SpringNative才逐步适配。

适合⽤AOT的场景很明确：短⽣命周期、⾼并发拉起的服务，⽐如Serverless函数。FaaS平台要求百毫秒内启动，传统 JVM 压根扛不住，这时候 native image 就能派上⽤场。但常规的⻓驻 Web 服务，JIT 的热点优化能⼒还是更强，AOT反⽽可能跑不过。

## 为什么Java的垃圾收集器将堆分为⽼年代和新⽣代？

Java 的堆内存分代设计不是凭空来的，是基于⼤量观测数据做出的⼯程妥协。你得先知道⼀个现象：绝⼤多数对象都是朝⽣⼣死的，研究发现98%以上的对象在创建后很快就会变成垃圾。

1）新⽣代专⻔放这些短命对象。它⼜分成Eden区和两个Survivor区（S0/S1）。⼤多数对象直接在Eden分配，GC时活下来的复制到 S 区，熬过⼏次 GC 还活着的，就升级去⽼年代。这种复制算法在存活对象少的时候效率很⾼。

2）⽼年代的对象都⽐较“⻓寿”，可能是⼀些缓存、静态变量引⽤的对象。这⾥空间⼤，⽤标记-整理或标记-清除这类适合⾼存活率场景的算法更合适。

不分代的话，每次扫描整个堆，GC 停顿时间根本扛不住。分代之后，Minor GC 只扫新⽣代，频率⾼但速度快，⼀般⼏⼗到⼏百毫秒。FullGC才扫⽼年代，虽然慢但触发少。

## Java中的强引⽤、软引⽤、弱引⽤和虚引⽤分别是什么？

Java的引⽤类型不⽌⼀种，除了我们天天⽤的普通引⽤，还有⼏种特殊引⽤，它们的区别主要体现在垃圾回收器对它们的处理策略上。

1）强引⽤就是平时最常⻅的，⽐如 Object obj = new Object() ，只要这⾏代码还挂着，哪怕内存快满了，对象也不会被回收。这是最硬的关联。

2）软引⽤在内存充⾜时不会被清理，⼀旦系统快撑不住了，JVM才会把它标记的对象⼲掉。适合做缓存，⽐如你⽤SoftReference<byte[]> 来缓⼀个⼤⽂件内容，内存不够⾃动释放，够⽤就留着。GuavaCache内部就⽤到了这个特性。

3）弱引⽤⽐软引⽤更短命，只要发⽣GC，不管内存够不够，直接回收。典型场景是 ThreadLocal ⾥的Entry ，⽤的是 WeakReference<ThreadLocal> ，防⽌内存泄漏。但注意，只是 key 被弱引⽤，value 不是，所以还得⼿动清理。

4）虚引⽤最特别，它⼏乎不控制对象⽣命周期，唯⼀作⽤就是能在这个对象被回收时收到⼀个系统通知。必须配合ReferenceQueue 使⽤，⼀般⽤于追踪 GC ⾏为，像 NIO 中的直接内存管理就靠它触发清理。

## Java中常⻅的垃圾收集器有哪些？

Java的垃圾收集器得按年代来看，不同年代⽤的策略和实现不⼀样。早期CMS主要解决⽼年代回收停顿时间⻓的问题，⽤标记-清除算法，并发收集，但容易产⽣碎⽚，搞不定的时候还得靠SerialOld收尾。

G1 收集器是 JDK 9 默认的，主打“低延迟”，把堆拆成多个 Region，优先回收垃圾最多的区域，⽤写屏障维护RememberedSet来追踪跨区引⽤，避免全局扫描。它在⼤部分场景下能控制STW时间在⽬标范围内，适合⼤堆、多核机器。

到了JDK11+，ZGC和Shenandoah是新主⼒。它们都追求亚毫秒级停顿，⽀持⼏⼗GB甚⾄TB级堆。ZGC⽤着⾊指针+读屏障，在标记和转移阶段⼏乎不暂停应⽤线程，停顿基本压在1ms以内。Shenandoah类似，但它不依赖着⾊指针，⽽是额外加了个转发指针。

2）CMS 已经被废弃，ZGC 在⽣产环境越来越常⻅，尤其对延迟敏感的系统⽐如交易、实时计算
