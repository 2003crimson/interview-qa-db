## 什么是命令模式？⼀般⽤在什么场景？

命令模式把“请求”封装成⼀个对象，这样就能让⽅法参数化。⽐如你调⽤⼀个⽅法，传进去的不是⼀个值，⽽是⼀个命令对象，它知道要执⾏什么动作、由谁来执⾏。

这样⼀来，调⽤⽅和执⾏⽅就彻底解耦了。调⽤⽅只管触发 execute()，压根不经过具体业务逻辑，后⾯的Receiver⾃⼰处理。常⻅的像JDK⾥的Runnable就是典型例⼦，你把任务提交给线程池，⾄于怎么执⾏，调⽤者不⽤管。

1）⽀持撤销和重做。命令对象可以记录执⾏前的状态，undo() 时恢复回去。⽐如⽂本编辑器⾥的 Ctrl+Z，每个操作都是⼀个命令。

2）实现命令队列。接收⽅处理不过来时，可以把命令先存起来，慢慢消费。像MQ削峰其实也是这个思路，只不过更复杂。

3）远程调⽤场景。⽐如⽤命令对象序列化后通过⽹络发送，在另⼀端反序列化执⾏。JavaRMI或早期的EJB远程调⽤就有这种味道。

代码上关键就是四个⻆⾊：Command 接⼝定义 execute 和 undo，ConcreteCommand 持有 Receiver 引⽤并实现具体逻辑，Invoker触发命令，Client负责组装。

其实 Swing 的 Action 事件处理、Spring JMS Template 发送消息，底层都⽤了这套路。但注意别滥⽤，不是所有封装都要搞成命令，太简单的直接调⽤更清晰。

## 什么是合成复⽤原则？

合成复⽤原则简单说，就是优先⽤对象组合，⽽不是靠继承来复⽤代码。继承虽然能复⽤⽗类功能，但耦合太紧，⼦类依赖⽗类的实现细节，⼀旦⽗类变动，⼦类就容易出问题。

⽤组合的话，把功能拆成独⽴的组件，通过成员变量持有并委托调⽤，灵活性⾼得多。⽐如你有个数据库操作逻辑，别让业务类去继承⼀个 BaseDao ，⽽是定义个 DatabaseService ，业务类⾥直接引⽤它。

1）组合关系在运⾏时可以动态替换，⽐如换个数据源实现2）避免继承导致的类爆炸，像JavaAWT那种Button 、 TextField 都继承⾃ Component ，层次⼀深就搞不定3）符合开闭原则，新增功能靠加组件，⽽不是改继承树

## 什么是单⼀职责原则？

单⼀职责原则讲的是，⼀个类或者模块应该有且只有⼀个引起它变化的原因。换句话说，你得让⼀个类只负责⼀块功能，别啥都往⾥塞。

⽐如你写个⽤户管理类，它负责处理⽤户信息的校验、存储，甚⾄还要⽣成报表、发邮件。这时候只要报表格式⼀变，或者邮件模板改了，你都得动这个类。时间⼀⻓，这个类就会变得⼜⼤⼜难维护，测试也搞不定。

1）如果职责混杂，修改时容易牵⼀发⽽动全⾝

2）拆开之后，每个类专注⼀件事，复⽤性和可测试性都更强

3）团队协作也更顺畅，不同⼈改不同模块互不影响

举个实际例⼦，在Spring项⽬⾥，你不会把Controller⾥的业务逻辑和数据库操作全塞进⼀个Service类。通常会拆成 UserService 负责业务流程，UserRepository 负责数据存取，各⾃独⽴演化。

代码上其实很简单，就是做好边界划分：

class UserValidator {   
boolean isValid(User user) { ... }   
}   
class UserRepository {   
void save(User user) { ... }   
}

这两个类各⼲各的，以后加加密逻辑也好，换数据库也好，影响范围都很清楚。很多⼈刚开始写代码总想“图省事”，结果后期维护成本翻倍，这就是没守住这条原则。

## 请⽤⼀句话概括，什么是设计模式？为什么要⽤？

设计模式是前⼈总结的、针对特定软件设计问题的经典解决⽅案模板，它让开发者能快速复⽤经过验证的设计思路，避免重复造轮⼦。

⽐如你写⼀个数据库连接池，直接上⼿搞可能线程安全、资源回收都容易出问题。但如果你⽤了单例模式保证实例唯⼀，配合对象池模式管理连接⽣命周期，代码结构清晰，稳定性也⾼得多。

这些模式在 Spring、Netty 这些主流框架⾥到处都是。像 Spring 的 Bean 默认就是单例模式，Netty 的事件循环组也是典型的对象池实现。

⽤模式不是为了炫技，⽽是为了解决“类之间怎么协作”、“对象怎么创建”、“状态怎么管理”这类⾼频难题。不⽤的话，⼩项⽬还能靠经验顶⼀顶，项⽬⼀复杂就容易架构混乱，后期维护成本翻倍。

1）创建型模式解决对象怎么⽣出来，⽐如⼯⼚模式把创建逻辑封装掉

2）结构型模式解决类和对象怎么组合，⽐如代理模式可以在不改原逻辑的前提下加⽇志、事务

3）⾏为型模式解决对象间怎么通信，⽐如观察者模式解耦事件发布与监听

## 什么是迪⽶特法则？

迪⽶特法则，也叫最少知道原则，说⽩了就是⼀个类应该尽量少了解其他类的内部细节，只和直接的朋友打交道。

1）每个对象都有朋友类，⽐如成员变量、⽅法参数、⽅法返回值⾥的类型，这些是允许通信的。但你不能去调⽤朋友的“朋友”，否则依赖就太深了。

⽐如你在⼀个服务类⾥拿到⼀个⽤户对象，可以调它的getName()，但如果还要通过⽤户对象再去getAccount().getBalance()，那你就依赖了 Account 类，违反了法则。正确的做法是让⽤户类⾃⼰提供 getBalance()⽅法，把细节封装住。

2）过度遵守也可能带来问题。⽐如在 Spring 项⽬⾥，Service 层调⽤ Mapper 返回实体，再转成 DTO 返回给Controller，这种链式调⽤很常⻅。如果硬拆，反⽽会让代码啰嗦。所以实际开发中要权衡，⾼内聚和松耦合才是⽬标。

3）典型应⽤场景是在模块划分时。像订单系统对外只暴露OrderService，别的模块不需要知道OrderItem、OrderLog 这些底层实现。哪怕内部结构变了，只要接⼝不变，外部就不受影响。

```java
// 好的做法：封装内部细节
public class Order {
private List<OrderItem> items;
public BigDecimal getTotal() {
return items.stream().map(Item::getPrice).sum();
}
}
// 外部只需要调⽤ getTotal，不⽤关⼼ item 列表
order.getTotal();
```

别把它当成铁律，⽽是设计思维的引导。降低耦合度是⽬的，不是为了少写⼏个点号。

## 什么是装饰器模式？⼀般⽤在什么场景？

装饰器模式就是在不改变原有对象的基础上，动态地给它添加新功能。这种设计属于结构型模式，关键在于装饰类和被装饰的类实现同⼀个接⼝，这样外部调⽤者完全感知不到内部是原始对象还是被包装过的。

1）假设你有⼀个 InputStream ，想让它具备缓冲能⼒，Java ⾥的 BufferedInputStream 就是典型例⼦。它接收⼀个 InputStream 实例，然后在读取时加了⼀层缓冲逻辑，但对外暴露的⽅法还是标准的 read() ，这就是装饰器的实际应⽤。

2）再⽐如写⽇志或监控埋点，你可以封装⼀个装饰类，在每次⽅法调⽤前后打印⽇志，⽽不⽤去改原来的业务代码。  
SpringAOP的某些实现思路也借鉴了这个模式。

```java
interface Service {
void handle();
}
class RealService implements Service {
public void handle() { System.out.println("处理请求"); }
}
```

```java
class LogDecorator implements Service {
private final Service target;
public LogDecorator(Service target) { this.target = target; }
public void handle() {
System.out.println("开始记录⽇志");
target.handle();
System.out.println("⽇志记录完成");
}
}
```

这种⽅式⽐继承更灵活。继承是在编译期静态扩展，装饰器是运⾏时动态叠加，想要“带缓存的功能”、“带认证的功能”，可以⼀层套⼀层地包装，拆卸也⽅便。

不过要注意别滥⽤，包装层次太多会增加调试难度，⽐如最终执⾏链路可能要穿过四五层装饰器，排查问题就⽐较麻烦。

## 什么是接⼝隔离原则？

接⼝隔离原则说⽩了就是让接⼝尽量⼩⽽专，别搞成⼤⽽全的“胖接⼝”。你想想，如果⼀个接⼝定义了⼀堆⽅法，但某些实现类只⽤其中⼀两个，那其他⽅法就成了摆设，还强迫实现类去写⼀堆空⽅法，这就很别扭。

1）接⼝应该只为它的使⽤者提供它真正需要的⽅法，别的都别塞进来。⽐如有个 Machine 接⼝，既有 print()⼜有 scan() ，结果你有个类只负责打印，那它还得实现 scan() ，返回个不⽀持操作异常，这不⾃找麻烦嘛。

2）更合理的做法是拆开，搞个 Printer 接⼝和 Scanner 接⼝，让不同的设备去按需实现。像富⼠通的多功能⼀体机可以同时实现两个，⽽普通打印机就只实现 Printer 就⾏了。

3）这样拆的好处是解耦更彻底，代码维护起来也轻松。新增⼀个扫描功能，不影响原有的打印模块，测试范围也⼩。

```java
public interface Printer {
void print();
}
public interface Scanner {
void scan();
}
public class OfficePrinter implements Printer {
public void print() {
System.out.println("Printing...");
}
}
```

客户端依赖的接⼝越具体，系统的灵活性和可维护性就越⾼。⼀个类不应该被强迫依赖它不⽤的⽅法，这是设计上的洁癖，也是⻓期演进的保障。

## 什么是⾥⽒替换原则？

⾥⽒替换原则讲的是⼦类应该能够替换它的⽗类，程序的⾏为不会因此出错。你⽤⽗类定义的地⽅，换成⼦类对象，系统照样能正常跑。

1）关键在于⾏为⼀致性。⼦类可以扩展功能，但不能改变⽗类原有的正确⾏为。⽐如⽗类的某个⽅法约定返回正数，⼦类重写后就不能返回负数，这会破坏调⽤⽅的预期。

2）常⻅违反场景是重写⽅法时抛出意外异常，或者对输⼊输出做不合理限制。像集合框架⾥ ArrayList 和 Vector 都继承⾃AbstractList，它们都能替换抽象⽗类出现在参数、变量中，这就是遵循了该原则。

3）它和多态有关联但不是⼀回事。多态是语⾔机制，允许运⾏时决定调⽤哪个⽅法；⽽⾥⽒替换是⼀种设计约束，确保这种替换是安全的。搞不定这点，继承体系就会变得脆弱，上游⼀改，下游全挂。

这个原则压根不关⼼你⽤了多少继承层次，只关⼼替换后逻辑是否成⽴。⽤的时候记住⼀点：别让⼦类“背叛”⽗类承诺。

## 什么是开闭原则？

开闭原则讲的是软件实体应该对扩展开放，对修改关闭。意思是说，当需求变化时，你应该通过添加新代码来实现功能变更，⽽不是去改已经写好的、正在运⾏的代码。

⽐如你有个订单处理逻辑，现在要⽀持新的⽀付⽅式，理想的做法不是在原有代码⾥加if-else判断，⽽是通过抽象出Payment接⼝，让每种⽀付⽅式⾃⼰实现，新增时只加新类，不动旧逻辑。

这样做的好处很明显，⽼功能不会因为改代码⽽引⼊ bug，系统也更容易维护和测试。实际开发中，像 Spring 的拦截器链、Dubbo的扩展点机制，都是靠这种设计⽀撑起来的。

1）先定义抽象，⽐如接⼝或抽象类

2）具体⾏为由⼦类或实现类完成

3）新增功能时只增加新实现，不碰原有分⽀

这个模式⽤得好的话，核⼼流程稳定，新功能靠插件式接⼊。其实很多设计模式，像策略、装饰器、模板⽅法，本质上都在帮我们满⾜这条原则。

什么是备忘录模式，⼀般⽤在什么场景？

备忘录模式解决的是对象状态的保存和恢复问题，不破坏原封装性。它通过⼀个中间⻆⾊把对象的内部状态抽出来存到外部，需要时再塞回去。

1）核⼼是三个⻆⾊：原发器（Originator）是那个有状态要保存的对象，⽐如⼀个⽂本编辑器。负责⼈（Caretaker）负责管理备忘录，但不能看内容。备忘录（Memento）就是个数据容器，存原发器的状态快照。

2）典型场景是撤销操作。⽐如你⽤记事本写东西，Ctrl+Z撤销上⼀步，背后其实就是把之前存的备忘录拿回来覆盖当前状态。游戏存档也是类似逻辑，打不过关卡就读档重来。

3）另⼀个常⻅⽤途是事务回滚。像Spring的 @Transactional 注解，万⼀事务失败，可以通过保存的旧状态来回滚。虽然Spring不⼀定直接⽤备忘录模式实现，但思想是⼀致的。

代码上很简单，原发器提供 save() 和 restore(Memento m) ⽅法，备忘录类通常设计成原发器的内部类，这样能访问私有成员。

```java
class Editor {
private String conten t;
public Memento save() {
return new Memento(content);
}
public void restore(Memento m) {
content = m.getContent();
}
public static class Memento {
private final String content;
private Memento(String content) { this.content = content; }
private String getContent() { return content; }
}
}
```

这个模式的好处是隔离了状态存储逻辑，原发器不⽤关⼼怎么存，负责⼈也不⽤知道存了啥。但频繁创建备忘录会吃内存，尤其是状态⼤⼜频繁操作的场景，得考虑做快照间隔或者序列化压缩。

## 什么是访问者模式？⼀般⽤在什么场景？

访问者模式解决的是数据结构和操作逻辑解耦的问题。当⼀个数据结构包含多种类型对象，⽽你需要对这些对象执⾏不同的操作，并且这些操作可能会频繁增减时，直接在类⾥加⽅法会让代码越来越臃肿。

它把操作“外移”，让外部逻辑通过访问者的⽅式来处理各个元素。元素负责接受访问者，调⽤其对应的⽅法，反过来触发具体⾏为。

1） 元素接⼝定义 accept(Visitor) ⽅法

2） 每个具体元素实现 accept ，传⼊⾃⾝引⽤调⽤访问者的 visit(this)

3） 访问者接⼝声明多个 visit 重载⽅法，对应不同元素类型

4）具体访问者实现这些⽅法，封装实际逻辑

⽐如编译器AST（抽象语法树）遍历，不同节点（变量、循环、函数）需要做类型检查、代码⽣成、优化等操作。如果每个节点都内置这些⽅法，维护成本极⾼。⽤访问者模式，每种功能写⼀个访问者类，新增优化策略也不⽤动节点代码。

另⼀个典型场景是报表⽣成，⽐如SpringDataJPA中的查询树处理，或者Jackson反序列化时的节点遍历逻辑。

这种模式适合稳定的数据结构+多变的操作。但⼀旦元素类型变了，所有访问者都要改，反⽽更麻烦。所以前提是结构相对固定。

## 什么是责任链模式？⼀般⽤在什么场景？

责任链模式就是把多个处理器串成⼀条链，请求沿着链往下传，直到某个处理器处理它为⽌。每个节点只关⼼⾃⼰能不能处理，能就办了，不能就丢给下⼀个，调⽤者不⽤管背后是谁⼲的。

这种模式的关键在于解耦。你往链上加新处理器，完全不⽤动原来的代码，符合开闭原则。⽐如在Web开发⾥，过滤器（Filter）就是典型的责任链，像 Spring Security 的安全过滤器链，⼀堆 Filter 依次执⾏，有的做认证，有的做授权，漏掉⼀个都不⾏。

再⽐如电商场景下的审批流，报销申请先由直属领导审，然后财务审，⾦额超过1万还得总监过⼀遍。每层只判断⾃⼰该不该拦，不⽤知道前后是谁。

写法上⼀般让处理器实现同⼀个接⼝，⾥⾯有个next引⽤指向下⼀个处理器，处理⽅法⾥先判断⾃⼰是否处理，否则调⽤ next.handle()。

```java
public abstract class Handler {
protected Handler next;
public void setNext(Handler next) { this.next = next; }
public abstract void handle(Request request);
}
public class Level1Handler extends Handler {
public void handle(Request request) {
if (request.getType() == "type1") {
System.out.println("Level1 处理");
} else if (next != null) {
next.handle(request);
}
}
}
```

注意别搞成死循环，还有要考虑是否要⽀持多路径或并⾏处理，原⽣责任链是线性的。有些框架像 Netty 的ChannelPipeline，也是责任链，但更复杂，⽀持⼊站出站双向传播。

## 什么是策略模式？⼀般⽤在什么场景？

策略模式解决的是“⼀堆if-else或switch分⽀⾥塞不同算法”的问题。你想啊，⽐如做⽀付功能，微信⽀付、⽀付宝、银联，每种逻辑完全不同，要是全写在⼀个⽅法⾥，代码⽴⻢爆炸，维护起来根本搞不定。

它的核⼼是把每个算法封装成独⽴的类，都实现同⼀个接⼝。运⾏时根据条件选⼀个具体实现来⽤。这样新增⽀付⽅式不⽤改⽼代码，符合开闭原则。

⼀般在这些场景特别好使：1）有明显的⾏为分⽀，⽐如计算运费，按城市、重量、会员等级有不同算价规则2）需要动态切换算法，像导出报表⽀持CSV、Excel、PDF三种格式3）避免重复的条件判断，像促销活动满减、打折、返券

举个例⼦，Spring 的 Resource 接⼝就是典型， ClassPathResource 、 FileSystemResource 、UrlResource 各⾃处理不同路径类型的资源加载，调⽤⽅压根不经过具体实现。

```java

}
public class Context {

public void setStrategy(Strategy strategy) {
this.strategy = strategy;
}
public void run() {
strategy.execute();
}
}
```

实际项⽬⾥，配合Spring的IoC，直接把所有策略实现注⼊进来，⽤map存好，key是策略名，取的时候strategies.get("alipay").execute() 就⾏，⼲净利落。

## 什么是状态模式？⼀般⽤在什么场景？

状态模式本质上是把对象的⾏为包装在不同状态类⾥，让对象在运⾏时通过切换状态类来改变⾏为。你不⽤写⼀堆if-else判断当前状态再执⾏对应逻辑，⽽是让“状态”⾃⼰决定该⼲什么。

1）每个状态都实现统⼀接⼝，⽐如 handle() ⽅法，具体⾏为由⼦类实现

2）上下⽂（Context）持有⼀个状态实例，所有请求都委托给当前状态处理

3）状态之间可以互相转换，⽐如订单从“待⽀付”变成“已发货”

这种模式特别适合状态多、状态转换复杂、每个状态⾏为差异⼤的场景。举个例⼦，电商系统的订单状态机⸺待⽀付、已⽀付、已发货、已完成、已取消，如果全⽤if-else堆在⼀起，改⼀个状态跳转就得动整个⽅法，后期根本搞不定。⽤状态模式，每个状态独⽴封装，新增状态或修改流转只影响对应类。

游戏开发⾥也常⻅，⽐如⻆⾊有“ idle ”、“running”、“attacking”状态，不同状态下按键响应完全不同，⽤状态模式就很清晰。

interface OrderState {

}

状态模式真正发⼒的点在于它让状态变更和⾏为扩展变得可控。你不再是在⼀个⼤类⾥修修补补，⽽是⽤多态代替条件判断，代码结构更稳定。

## 什么是设计模式？请简述其作⽤。

设计模式不是语法也不是框架，它是前⼈总结出的、针对特定问题的可复⽤解决⽅案模板。本质上是代码结构和组织⽅式的经验结晶。

## 1）解决重复出现的设计问题

⽐如对象创建太散乱，就⽤⼯⼚模式统⼀出⼝；系统耦合太紧，就引⼊观察者模式解耦。Spring ⾥的 BeanFactory 就是简单⼯⼚的体现，MyBatis的插件机制⽤了责任链。

## 2）提升代码可维护性和扩展性

以策略模式为例，不同算法独⽴封装，新增逻辑不⽤改原有if-else。电商项⽬⾥计算运费、优惠规则基本都这么⼲。

## 3）提供通⽤语⾔

团队沟通时说“这⾥⽤模板⽅法”，⽐解释“⽗类定流程⼦类重步骤”更⾼效。就像说“MVC”⼤家⽴刻明⽩分层结构。

## 什么是模板⽅法模式？⼀般⽤在什么场景？

模板⽅法模式说⽩了就是把⼀个算法的流程固定下来，把不变的部分在抽象类⾥写死，变的部分交给⼦类去实现。⽗类控制整体步骤，⼦类只负责具体细节。

1） 定义了⼀个算法⻣架，⽐如处理请求的流程是：校验 -> 处理 -> 记录⽇志。这个流程不能改。

2）把校验、处理这些步骤声明成抽象⽅法，⼦类根据业务实现⾃⼰的逻辑。⽐如⽀付流程⾥，微信⽀付和⽀付宝⽀付的处理⽅式不同，但整体流程⼀致。

3）钩⼦⽅法可以⽤来做条件分⽀，⽗类通过 isDebug() 这样的默认返回值控制是否打印⽇志，⼦类可选择性覆盖。

这种模式在框架设计⾥特别常⻅。Spring的 JdbcTemplate 就是个典型例⼦，你写SQL，它帮你搞定连接管理、异常转换、资源释放这些脏活累活。还有像 AbstractList ⾥的 addAll ⽅法，底层调⽤ add ，⽽ add 是抽象的，留给具体集合实现。

## 什么是观察者模式？⼀般⽤在什么场景？

观察者模式解决的是⼀对多依赖关系，当⼀个对象状态改变，所有依赖它的对象都能⾃动收到通知。这种模式在事件驱动系统⾥特别常⻅。

1）被观察的对象叫主题（Subject），它维护⼀个观察者列表。状态变更时，遍历列表调⽤每个观察者的更新⽅法。

2）观察者实现统⼀接⼝，只需定义如何响应变化，不需要主动去拉数据。

这种设计把通知逻辑收拢到主题内部，避免散落在各处。像Spring的 ApplicationEvent 机制就是典型应⽤，发布⼀个事件，多个监听器⾃动触发。Swing的按钮点击、前端框架的事件绑定也都是这个思路。

代码上其实很简单：

```java
interface Observer {
void update(String message);
}
class Subject {
private List<Observer> observers = new ArrayList<>();
private String state;
public void setState(String state) {
this.state = state;
notifyObservers();
}
observers.forEach(o -> o.update(state));
}
}
```

适合⽤在业务解耦的场景，⽐如订单创建后要发短信、更新库存、记录⽇志。把这些操作做成观察者，主流程只管发事件，不⽤硬编码后续动作。但要注意别滥⽤，观察者太多会搞不清执⾏链路，调试起来头疼。

## 请解释什么是单例模式，并给出⼀个使⽤场景

单例模式保证⼀个类在整个应⽤中只有⼀个实例，并提供⼀个全局访问点。这种模式属于创建型设计模式，核⼼是控制实例的创建时机和数量。

实现上通常把构造函数私有化，通过静态⽅法获取唯⼀实例。重点在于线程安全和防⽌反射破坏，⽐如饿汉式在类加载时就创建，简单但可能浪费资源；懒汉式延迟加载，但得加锁。

1）饿汉式写法最稳妥，JVM 保证线程安全

```java
public class Singleton {
private static final Singleton INSTANCE = new Singleton();
private Singleton() {}
public static Singleton getInstance() {
return INSTANCE;
}
}
```

## 2）懒加载推荐使⽤静态内部类，既延迟⼜安全

```java
public class Singleton {
private Singleton() {}
private static class Holder {
static final Singleton INSTANCE = new Singleton();
}
public static Singleton getInstance() {
return Holder.INSTANCE;
}
}
```

常⻅场景是配置管理器或线程池。像 java.lang.Runtime 就是个典型例⼦，每个 JVM 进程只需要⼀个运⾏时环境，通过 getRuntime() 获取唯⼀实例来执⾏系统级操作。

注意序列化和反射可能破坏单例，如果类实现了 Serializable ，要重写 readResolve() ⽅法返回同⼀实例。

## 请描述简单⼯⼚模式的⼯作原理。

简单⼯⼚模式的核⼼是把对象的创建过程集中到⼀个“⼯⼚”类⾥，客户端不⽤关⼼具体怎么创建实例，只要告诉⼯⼚想要什么类型就⾏。

1） ⼯⼚类内部通常有⼀个静态⽅法，接收⼀个参数⽐如类型标识，通过 if-else 或 switch 判断该返回哪个具体实现。  
⽐如传⼊ "mysql" 就返回 MySqlDriver ，传⼊ "redis" 就返回 RedisClient 。

2）客户端代码只需要依赖抽象接⼝或⽗类，不直接调⽤new。这样新增产品时，理论上只需修改⼯⼚逻辑，⽽不必改动所有使⽤⽅。

3）这种模式其实违背了开闭原则，每加⼀种新产品就得改⼯⼚⽅法。所以适合产品种类固定、变化少的场景，⽐如配置解析器，⽀持JSON和XML两种格式就够了。

代码⽰例如下：

```java
public class ParserFactory {
public static Parser create(String type) {
if ("json".equals(type)) return new JsonParser();
if ("xml".equals(type)) return new XmlParser();
throw new IllegalArgumentException("Unknown type");
}
}
```

说⽩了，它就是个封装了new的⼯具类，让调⽤⽅更⼲净，但扩展性有限。真要搞灵活，还是得上⼯⼚⽅法模式或抽象⼯⼚。

## 什么是建造者模式？⼀般⽤在什么场景？

建造者模式解决的是复杂对象构建过程的封装问题，尤其当构造函数参数太多、对象创建需要多个步骤时特别有⽤。  
你肯定遇到过那种⼀串new的时候传七⼋个参数，还分不清哪个是哪个，这时候就该上建造者了。

1）它把对象的构建逻辑从构造中剥离出来，通过链式调⽤⼀步步设置属性，最后build⼀下⽣成最终对象。代码可读性直接提升⼀个档次。

2）典型的使⽤场景就是像 HTTP 请求构建、数据库连接配置、DTO 转换这类需要灵活组合字段的地⽅。⽐如 OkHttp的 Request 就⽤了建造者，你可以先 setUrl，再 addHeader，最后 build 出请求对象，每步都清晰明了。

3）和⼯⼚模式不同，建造者关注的是同⼀个产品族内部的复杂构建流程，⽽不是创建哪种类型的产品。⼯⼚决定“⽣产什么”，建造者决定“怎么组装”。

代码⻓这样：

User user = User.builder(   
.name("zhangsan")   
.age(25)   
.email("zhangsan@example.com")   
.build();

你看这⽐ new User(null, "zhangsan", 25, null, "zhangsan@example.com", ...) 强太多了，参数多了也不会搞不定。  
⽽且可以设置默认值，某些必填字段还能在 build 阶段做校验，不满⾜直接抛异常。

Spring Boot 的 RestTemplate、Jackson 的 ObjectMapper 配置也都⽤了类似思路。这种模式在构建不可变对象（Immutable）时尤其有价值，因为所有字段都是 final 的，只能靠 builder ⼀次性赋值。

## 什么是原型模式？⼀般⽤在什么场景？

原型模式就是通过拷⻉⼀个已有对象来创建新对象，⽽不是⾛构造函数那套流程。关键在于实现 Cloneable 接⼝并重写 clone() ⽅法，让对象能⾃⼰复制⾃⼰。

1）当你发现创建对象的过程特别重，⽐如要查数据库、读⽂件、⽹络请求，这时候⽤原型模式缓存⼀个“样板”对象，后续直接克隆，性能提升⾮常明显。像 Spring 框架⾥的 prototype 作⽤域，每次 getBean() 都返回⼀个新实例，底层就是靠克隆机制实现的。

## 什么是适配器模式？⼀般⽤在什么场景？

适配器模式解决的是接⼝不兼容问题，你⼿⾥的类和系统期望的接⼝对不上，⼜不能改源码，这时候就需要⼀个中间层来做转换。

## 什么是桥接模式？⼀般⽤在什么场景？

桥接模式的关键是把抽象和实现解耦，让它们能独⽴变化。⽐如你有个图形类，既要⽀持不同形状（圆形、⽅形），⼜要⽀持不同渲染⽅式（Windows、Linux）。如果⽤继承硬写，组合爆炸，8个类都搞不定。

1）把变化维度拆开。形状作为抽象层，渲染作为实现层，两者通过组合连接。2）抽象层持有⼀个实现层的接⼝引⽤，运⾏时动态绑定具体实现。3）新增形状或新渲染器，都不⽤动对⽅代码，符合开闭原则。

典型场景是跨平台 GUI 库。Swing ⾥的 Component 和 LookAndFeel 就是桥接⸺同⼀个按钮，在 Windows 和macOS 上外观不同，但⾏为⼀致。还有 JDBC 驱动， Connection 接⼝是抽象，MySQL、Oracle 驱动是具体实现，切换数据库不改业务代码。

## 什么是组合模式？⼀般⽤在什么场景？

组合模式解决的是树形结构的统⼀处理问题。你有⼀堆对象，它们之间是⽗⼦关系，形成⼀个树，你想让客户端不管是操作根节点、分⽀还是叶⼦，都⽤同⼀套接⼝。

1）它把对象组织成树形结构，每个节点要么是容器（组合节点），要么是叶⼦节点。关键是，容器和叶⼦都实现同⼀个抽象接⼝，这样上层调⽤者就不需要关⼼当前操作的是不是还有⼦节点。

2）典型场景⽐如⽂件系统，⽬录可以包含⽂件和其他⽬录，但你可以对它们统⼀调⽤ getSize() 或delete() 。再⽐如UI组件，窗⼝包含⾯板，⾯板包含按钮，但所有组件都能响应 draw() 调⽤。

3）另⼀个常⻅例⼦是菜单系统。像Swing或JavaFX中的菜单项和⼦菜单，都可以被点击或渲染，组合模式让遍历和操作变得简单。

代码核⼼就是⼀个 Component 接⼝，定义通⽤⾏为，然后 Composite ⾥维护⼀个 List<Component> ⼦节点 列表，调⽤时递归下去。

<!-- image-->

这种模式的好处是扩展性强，加新类型的节点不影响原有逻辑。但缺点也很明显，如果节点类型差异⼤，强⾏统⼀接⼝会让很多⽅法在某些⼦类⾥空实现，有点别扭。⽤的时候得看场景是否真的具备树形 + 统⼀操作的特征。

## 什么是外观模式？⼀般⽤在什么场景？

外观模式本质是给复杂⼦系统加⼀层统⼀的⻔⾯，让外部调⽤更简单。你不⽤关⼼背后⼀堆模块怎么协作，只通过⼀个外观类就能搞定。

1）假设你的系统⾥下单要⾛订单、库存、⽀付、通知四个服务，每个都有⾃⼰的API和调⽤顺序。如果每个业务都⾃⼰拼这些逻辑，代码会散落各处，改⼀个流程就得动好⼏处。

2）这时候搞个 OrderFacade ，它内部封装了完整的下单流程，暴露⼀个 placeOrder() ⽅法。上层应⽤只需要调这个⽅法，压根不经过底层那堆服务。

3）这种模式特别适合中台服务或者通⽤能⼒平台。⽐如你在公司做了⼀个统⼀的消息⽹关，对接了短信、邮件、钉钉、企业微信多个渠道，业务⽅不需要知道每个渠道的细节，调⼀个 sendMessage() 就⾏，背后由外观类去路由和处理。

## 代码上看很简单：

class OrderFacade {   
public void placeOrder(Order order) {   
inventoryService.reduce(order);   
paymentService.pay(order);

notificationService.send(order);   
orderService.save(order);   
}   
}

常⻅于重构⽼旧系统时引⼊，把混乱的调⽤关系收拢。也常⽤于 API 层对内隐藏微服务细节，⽐如⽤ Spring CloudGateway 或者⾃定义 Facade 服务对外暴露简洁接⼝。

注意它不是代理，不控制访问过程，也不做增强，就是单纯地简化调⽤。要是你发现某个功能需要组合多个服务才能完成，⽽且这个组合逻辑重复出现，那就是外观模式的典型场景。

## 什么是迭代器模式？⼀般⽤在什么场景？

迭代器模式说⽩了就是把集合内部的遍历逻辑封装起来，让调⽤者不⽤关⼼底层是数组、链表还是树，统⼀⽤next() 、 hasNext() 这⼀套⽅式去访问元素。

1）它最核⼼的价值在于解耦。⽐如你写了个ArrayList，别⼈⽤的时候如果直接操作内部数组，那以后你换成链表结构，他的代码就全得改。但⽤了迭代器，接⼝不变，底层爱怎么变怎么变。

2）Java ⾥的 Collection 框架全靠它撑着。List、Set、Map 的遍历，像 for (String s : list) 这种增强for 循环，背后都是 Iterator 在⼲活。你⽤ LinkedList 或 HashSet，表⾯写法完全⼀样。

3）适⽤场景很明确：只要你在设计⼀个容器类，或者需要对外提供遍历功能，就应该考虑返回⼀个迭代器。典型例⼦像 MyBatis 查询结果的 ResultSet 遍历，或者 Kafka Consumer 拉取的消息集合，都⽤了类似思想。
