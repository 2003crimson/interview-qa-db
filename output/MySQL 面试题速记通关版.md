## MySQL 的 Doublewrite Buffer 是什么？它有什么作⽤？

MySQL的DoublewriteBuffer是个防⽌数据⻚写⼊过程中出现“部分写”问题的机制。InnoDB每次刷脏⻚时，并不会直接把⻚写到表空间⽂件，⽽是先写⼀份到共享表空间⾥的连续区域⸺也就是doublewritebuffer，再从这⾥分批写回真正的数据⽂件。

这个机制的核⼼价值在于解决崩溃恢复时的数据⻚不⼀致。磁盘写⼊以4K或8K为单位，⽽InnoDB⻚通常是16K。如果在写⼀个16K⻚的过程中断电，可能只写了前8K，导致⻚处于“撕裂”状态。重启后没法靠redolog恢复这种损坏⻚，因为redo记录的是逻辑变更，前提得有个完整的⻚。

有了doublewritebuffer，恢复时会做两件事：1）检查数据⻚⾃带的checksum，判断是否完整2）如果不完整，就去 doublewrite buffer ⾥找这个⻚的副本，⽤它来恢复

虽然听起来像“双写”会带来性能开销，但其实写doublewritebuffer是顺序写，批量进⾏，对性能影响不⼤。反⽽是在没有它的情况下，为了保证⻚完整性，不得不开启 innodb_checksums 并配合每⻚重做，代价更⾼。

典型场景⽐如⼤事务提交后⼤量脏⻚刷新，或者缓冲池压⼒⼤频繁刷⻚时，doublewritebuffer就在后台默默扛住⼀致性⻛险。

## MySQL默认的事务隔离级别是什么？为什么选择这个级别？

MySQL默认的事务隔离级别是可重复读（RepeatableRead）。这个级别能解决脏读和不可重复读问题，⼤多数业务场景下够⽤⼜不会太影响并发性能。

1）脏读是指⼀个事务读到了另⼀个未提交事务的数据，这在任何⽣产环境都是不能接受的。

2）不可重复读是指同⼀个事务内两次查询结果不⼀致，因为期间其他事务修改了数据。可重复读通过MVCC（多版本

并发控制）机制让事务看到⼀致的快照，避免这个问题。

但它不解决幻读问题⸺不过MySQL的InnoDB在这个级别⽤了间隙锁（GapLock）+⾏锁的组合，实际上把幻读也基本遏制住了。⽐起串⾏化那种⼀⼑切的锁表操作，它在数据⼀致性与并发之间取得了不错的平衡。

代码上你不需要显式设置，除⾮要改：

```sql
SELECT @@transaction_isolation;
-- 默认输出 REPEATABLE-READ
```

如果系统对⼀致性要求极⾼，⽐如⾦融核⼼账务，可以升到串⾏化。但⼤部分Web应⽤，像电商库存、⽤户积分这类操作，可重复读完全扛得住，还不会因为过度加锁导致线程堵死。

要不要升级隔离级别，得看业务能不能容忍⼀点点幻读⻛险。其实很多项⽬连这个级别的坑都没遇到过，就是因为底层存储引擎做了额外保护。

什么是数据库的逻辑删除？数据库的物理删除和逻辑删除有什么区别？

数据库⾥删数据，不是所有场景都直接 DELETE 就完事。有时候得留个痕迹，这时候就⽤到逻辑删除。

逻辑删除本质是更新操作。给表加个字段，⽐如 is_deleted 或 del_flag ，删数据时把这字段从0改成1，数据本⾝还留在表⾥。查的时候约定好，默认只查 is_deleted = 0 的记录。像MyBatis-Plus这种框架，直接内置了⾃动过滤逻辑删除数据的能⼒，开发时⼏乎感知不到。

物理删除就是真正的 DELETE 语句，数据从存储引擎层被移除，⾏记录直接消失，空间后续可以复⽤。

两者的差别主要在⼏个地⽅：

1）数据可恢复性：逻辑删除能回溯，误删也能捞回来，审计、合规场景特别需要。物理删除除⾮靠binlog恢复，不然基本没戏。

2）性能影响：⼤批量逻辑删除会导致表数据膨胀，查询变慢，尤其是没有有效索引时。物理删除释放空间更彻底，但⾼并发下可能引发锁竞争和主从延迟。

3）关联数据处理：物理删除常要处理外键约束，可能级联删⼀堆表；逻辑删除通常只要改状态，脏活累活少很多。

4）存储成本：逻辑删除⻓期不清理，磁盘压⼒会越来越⼤，得配合归档机制。

实际项⽬⾥，⽤户账户、订单这种关键数据，基本都⽤逻辑删除。⽇志类、流⽔类数据，过期就删，适合物理删除或定时归档。

MySQL 中 int(11) 的 11 表⽰什么？

MySQL ⾥ int(11) 的 11 压根不是指存储⻓度或取值范围，int 固定占 4 个字节，最⼤存 21 亿左右。

这个11其实是显⽰宽度，只在特定场景下起作⽤，⽐如配合 ZEROFILL 时，不⾜位数会⽤0填充。例如定义为int(11) ZEROFILL，存个 1，查出来就是 00000000001。

但现在这特性基本没⼈⽤，ZEROFILL还有性能隐患，官⽅从8.0.17版本开始已经废弃了这⼀语义。所以现在写int(11) 和 int(5) 在实际运⾏中完全没区别。

建表的时候如果还纠结括号⾥的数字，纯属浪费时间。真正要注意的是数据类型本⾝，⽐如别把⽤户ID⽤int存，万⼀哪天超21亿就搞不定了，直接上bigint才省⼼。

```sql
-- 下⾯这两⾏，效果完全⼀样
id int(11) NOT NULL
id int(5) NOT NULL
```

开发⾥看到 int(11) 别慌，99% 的情况它只是历史遗留的书写习惯，不影响任何⾏为。

## MySQL 中 varchar 和 char 有什么区别？

varchar 和 char 都是⽤来存字符串的，但⽤法和底层处理差别挺⼤。

char是定⻓的，你定义成char(10)，那它就占10个字符的空间，不管实际存的是"a"还是"hello"，都会补空格到10。查询快，适合存⻓度固定的值，⽐如性别、状态码这种1-2位的标识。但浪费空间，尤其是字段定义得⼤⽽实际内容短的时候。

varchar是变⻓的，存多少占多少，最⼤⽀持65535字节（受限于⾏⼤⼩）。它需要额外1-2个字节记录⻓度，所以读写时多⼀点开销。适合⻓度不⼀的场景，⽐如⽤户名、地址这些。但因为⻓度可变，在⾏内存储结构上更灵活，空间利⽤率⾼。

1）char全部按固定⻓度分配存储，尾部空格会被截断（除⾮启⽤PAD_CHAR_TO_FULL_LENGTH模式）2）varchar实际占⽤空间=内容⻓度+⻓度标识字节（内容⼩于255字节⽤1字节，否则2字节）3）两者在检索时，char 的性能略好，因为位置固定；varchar 要先读⻓度再定位内容

举个例⼦：

CREATE TABLE t (a char(10), b varchar(10));   
INSERT INTO t VALUES ('abc', 'abc');

这⾏数据中，a列实际占10字符，b列只占3字符+1字节⻓度信息。

注意⾏⼤⼩限制，⼀张表所有列加起来不能超过约 65KB，所以别随便把⼤⽂本塞进 char 或超⻓ varchar。

## MySQL中的数据排序是怎么实现的？

MySQL 的排序其实有两种路径，⾛不⾛索引决定了性能差很多。

如果 order by 的字段有合适的索引，直接利⽤索引的有序性输出就⾏。索引本⾝就是排好序的 B+ 树，查出来天然有序，压根不需要额外排序。这种是理想情况，⽐如主键或联合索引的最左前缀匹配。

但⼤多数时候还是得排序，这时候就进⼊sortbuffer流程。MySQL会从引擎层读取满⾜条件的⾏，把需要的列（select 的字段或⽤于排序的字段）放进⼀块内存区域叫 sort buffer。当这块内存不够时，⽐如要排上百万条数据，就会分段排序，每段单独快排，写到临时⽂件，最后做归并排序。这个过程叫filesort，虽然名字带file，但其实是磁盘和内存配合的操作。

有个关键参数是sort_buffer_size，调⼤能减少磁盘临时⽂件的使⽤，但每个连接独占这份内存，设太⼤容易吃光内存。

举个例⼦，你查订单列表按创建时间排序，⼜没加索引，那每来⼀个请求都得进filesort，⾼并发下CPU和IO直接拉满。所以慢查询⾥经常看到Usingfilesort就得警惕了。

代码层⾯没法直接控制排序算法，但可以通过索引设计规避。⽐如：

SELECT name, create_time FROM orders ORDER BY create_time;

给 create_time 加索引就能跳过 filesort。

1）索引有序直接返回

2）⽆索引⾛sortbuffer+可能的磁盘临时⽂件

3）max_length_for_sort_data 控制⽤单路还是双路排序，⽼版本有回表问题

## MySQL 中 EXISTS 和 IN 的区别是什么？

EXISTS 和 IN 都⽤来处理⼦查询，但底层玩法完全不同。

1）IN是把⼦查询的结果全捞出来，存成⼀个临时的值列表，然后拿主查询的每⼀⾏去这个列表⾥匹配。⽐如SELECT \* FROM user WHERE dept_id IN (SELECT id FROM dept) ，它会先把所有 dept.id 查出来，再逐个⽐对。如果⼦查询结果很⼤，⽐如上万条，这个临时列表就很占内存，性能容易崩。

2）EXISTS不关⼼具体值，只判断是否存在。它采⽤相关⼦查询的⽅式，对外表每⼀条记录执⾏⼀次⼦查询。只要⼦查询能返回⼀⾏，就认为存在。⽐如 SELECT \* FROM user u WHERE EXISTS (SELECT 1 FROM dept dWHERE d.id = u.dept_id) ，这⾥⼦查询依赖外层user表的字段，相当于“为每个⽤户查⼀下有没有对应的部⻔”。⼀旦命中就停⽌，效率更⾼。

⼀般情况下，外表⼩、内表⼤⽤ EXISTS 更合适，因为驱动⾏数少，关联查询快；外表⼤、内表⼩⽤ IN 更好，因为⼩结果集做哈希查找代价低。

MySQL8.0对两者都有优化，但在复杂场景下⼿动选对依然关键。⽐如在分⻚查询中嵌套条件时，EXISTS往往能避免全表扫描。

什么是分库分表？分库分表有哪些类型（或策略）？

分库分表本质是为了解决单库扛不住数据量和并发压⼒的问题。当⼀张表数据达到千万甚⾄上亿级别，查询变慢、锁竞争激烈，主从复制延迟也会加剧。这时候就得把数据拆开，让多个数据库⼀起⼲活。

## 1）垂直分库

按业务模块拆分，⽐如⽤户服务⽤⼀个库，订单服务⽤另⼀个库。这种拆法最常⻅于微服务架构中，像电商系统⾥把商品、库存、交易拆到不同库，彼此独⽴部署，互不影响。

## 2）垂直分表

把⼀张宽表按字段拆开，⽐如⽤户表的登录信息和扩展资料分开存储。⼀般⽤在表字段特别多、冷热分明的场景，减少 I/O 开销。

## 3）⽔平分表

同⼀张表的数据按某种规则打散到多个结构相同的表⾥，⽐如⽤户表按user_id取模分成16张表。适合写多读少、数据增⻓快的场景，能有效降低单表容量。

## 4）⽔平分库

在⽔平分表基础上再跨数据库实例存储，⽐如把订单数据按 order_id 分到 8 个 MySQL 实例上。这是真正意义上的分布式拆分，能⼤幅提升存储和吞吐能⼒。

分⽚键（ShardingKey）的选择特别关键，它决定了数据是否均匀、查询能否下推。常⻅的有取模、范围、⼀致性哈希等策略。像 ShardingSphere、MyCat 这类中间件就是靠解析 SQL + 路由规则⾃动完成数据寻址的。

需要注意的是，⼀旦分库分表，跨库事务、全局排序、聚合查询就变得复杂，得靠柔性事务或引⼊ES做汇总查询来兜底。

## MySQL 中 VARCHAR(100) 和 VARCHAR(10) 的区别是什么？

字段定义⾥的数字是字符⻓度限制，不是字节占⽤。 VARCHAR(10) 最多存 10 个字符， VARCHAR(100) 最多存100个字符，超⻓会截断或报错，取决于SQL模式。

实际存储空间上，两者都只⽤够⽤的空间。⽐如都存"abc"，在UTF8MB3编码下都是3字节内容+1或2字节⻓度前缀。⻓度前缀根据最⼤定义⻓度决定：⼩于等于 255 ⽤ 1 字节，⼤于 255 ⽤ 2 字节。所以 VARCHAR(10) 和VARCHAR(100) 都⽤1字节前缀，存储开销⼀样。

但别乱设⼤值。虽然MySQL层⾯不浪费空间，但会影响内存分配和临时表⾏为。⽐如排序时，MySQL会按最⼤⻓度预估内存， VARCHAR(100) 可能⽐ VARCHAR(10) 多占10倍内存，容易把数据挤到磁盘临时表，性能就崩了。

另外 ORM 映射、应⽤层校验也会依赖这个⻓度。设成 VARCHAR(10000) 虽然技术上可⾏，但会让其他开发者困惑，也可能触发⼀些框架的低效路径。

所以建议按实际需要定⻓度，给点余量就⾏，⽐如⽤户名⽤ VARCHAR(64) ，短标题⽤ VARCHAR(255) 。别图省事全⽤ VARCHAR(255) 或直接拉满。

## MySQL 中 count(\*)、count(1) 和 count(字段名) 有什么区别？

count(\*) 、 count(1) 和 count(字段名) 看起来都是统计⾏数，但底层处理⽅式其实有差别，⽤错了可能影响性能甚⾄结果。

count(\*) 是标准的⾏计数⽅式，它不关⼼具体列，只统计所有⾏，包括 null 值。MySQL 优化器对它做了专⻔优化，尤其是 InnoDB 引擎下会选择成本最低的索引树来遍历，不⼀定真的全表扫描。

count(1) 其实和 count(\*) ⾮常接近，因为 1 是常量，每⼀⾏都能取到值，所以也是统计所有⾏。在⼤多数情况下，它的执⾏计划和 count(\*) ⼀样，性能⼏乎⽆差别。别被“1”误导，它不是按第⼀列算。

真正有区别的是⼀些⼈写的 count(字段名) 。这个函数只统计该字段⾮空（notnull）的⾏。如果这个字段允许为null ，那结果就可能⽐ count(\*) 少。⽐如 count(email) 会漏掉email为空的⽤户，这在统计总数时容易出错。

1） count(\*) 统计所有⾏，推荐⽤于总⾏数统计

2） count(1) 效果基本等同于 count(\*) ，可互换

3） count(字段名) 只统计该字段⾮空⾏，要⼩⼼语义差异

⼀般情况下，想查总⾏数就⽼⽼实实⽤ count(\*) ，别搞花活。有些 ORM 框架默认⽣成 count(1) ，问题不⼤，但看到 count(id) 还是得确认下 id 是不是主键且⾮空。

## MySQL 中的 Log Buffer 是什么？它有什么作⽤？

MySQL 的 InnoDB 存储引擎在处理事务时，不会每次写操作都直接刷到磁盘的 redo log ⽂件，那样性能会很差。它先写到⼀块内存区域，这块区域就是LogBuffer。

1）当执⾏ INSERT、UPDATE、DELETE 这类事务操作时，InnoDB 会⽣成对应的 redo ⽇志，这些⽇志优先写⼊ LogBuffer。

2）Log Buffer 在内存中，写⼊速度远快于磁盘 IO，能极⼤减少事务提交时的等待时间。

3）后续由后台线程根据策略（⽐如每秒⼀次、事务提交触发等）将缓冲中的⽇志批量刷到磁盘的redolog⽂件，确保崩溃恢复时数据不丢。

这个过程其实和 write-ahead logging（WAL）机制紧密相关，redo log 必须先于对应的数据⻚落盘。Log Buffer 就是WAL 中的关键缓存层。

你可以通过 innodb_log_buffer_size 参数调整它的⼤⼩，⼀般默认 16MB，对于⼤量⼤事务或⾼并发 insert 场景，可以调⼤到64MB或更⾼，避免频繁刷盘。

压根不经过 Log Buffer 直接写磁盘，系统基本就扛不住写压⼒了。脏活累活它承担了⼀⼤半。

## 在MySQL中存储⾦额数据，应该使⽤什么数据类型？

⾦额这种数据，最怕的就是精度丢失，尤其是涉及到加减乘除的时候。你要是⽤float或double，看着能存，但算着算着就差了⼏分钱，线上⼀跑账对不上，背锅是迟早的事。

MySQL⾥处理⾦额，得⽤DECIMAL。它不是近似值，是精确的，存多少就是多少。⽐如 DECIMAL(10,2) ，表⽰总共最多10位数字，⼩数点后占2位，能存像99999999.99这样的值，够⼤多数业务⽤了。你要是做⾦融系统，可能得 DECIMAL(18,4) 或更⾼，看实际需求。

```sql
CREATE TABLE orders (
id BIGINT PRIMARY KEY,
amount DECIMAL(10,2) NOT NULL COMMENT '订单⾦额，单位：元'
);
```

有⼈说⽤int存“分”也⾏，⽐如100元存成10000分。这确实能避免⼩数，但你要在代码⾥反复转换单位，逻辑容易出错，读数据库也不直观。除⾮你整个系统都统⼀这么⼲，不然没必要。

总之，别碰float/double。该⽤DECIMAL的地⽅就得⽤它，简单直接，不给问题留机会。

## MySQL 中 INNER JOIN、LEFT JOIN 和 RIGHT JOIN 的区别是什么？

内连接只返回两边都能匹配上的⾏，左连接会保留左边表的全部数据，右边没有匹配的就补NULL，右连接反过来。

1）INNERJOIN是最严格的，驱动表和被驱动表做关联时，必须满⾜ON条件才会出现在结果⾥。⽐如查订单和⽤户信息，只有⽤户存在且订单归属该⽤户才输出。

2）LEFTJOIN保证左表的每⼀⾏都出现，即使右表没找到匹配项。常⻅于统计场景，像列出所有商品，不管有没有销量记录，都要展⽰出来，⽤ SUM(ifnull(sales,0)) 累加。

3）RIGHT JOIN 和 LEFT JOIN 是镜像关系，实际很少⽤，⼀般统⼀写成 LEFT JOIN 避免混淆。

```sql
-- 内连接：仅返回 user 和 order 能关联上的数据
SELECT u.name, o.amount
FROM user u INNER JOIN order o ON u.id = o.user_id;
-- 左连接：返回所有⽤户，没订单的 amount 为 NULL
SELECT u.name, o.amount
FROM user u LEFT JOIN order o ON u.id = o.user_id;
```

注意点：WHERE 和 ON 的执⾏顺序不同，ON 先过滤⽤于关联的数据，⽽ WHERE 是最终结果的筛选。LEFT JOIN 中如果把右表字段放WHERE⾥可能意外过滤掉NULL⾏，导致变成事实上的内连接。

MySQL 中 LIMIT 100000000, 10 和 LIMIT 10 的执⾏速度是否相同？

MySQL ⾥ LIMIT 100000000, 10 和 LIMIT 10 执⾏速度完全不同，前者慢得多。

原因在于 LIMIT offset, size 的执⾏机制。MySQL 会先扫描前 offset + size ⾏，然后丢弃前 offset ⾏，返回后⾯的size⾏。也就是说， LIMIT 100000000, 10 要真实地跳过⼀亿⾏数据，哪怕这些数据最终不⽤返回。这个过程是逐⾏检索的，尤其是当没有覆盖索引时，每跳过⼀⾏都可能涉及主键回表，代价⾮常⾼。

⽽ LIMIT 10 只需找到前10条记录就结束，扫描量极⼩，⾃然快得多。

这种问题在分⻚查询中特别常⻅。⽐如⽤ OFFSET 做深度分⻚，到后⾯⻚⾯时响应明显变慢。解决⽅案⼀般有两种：

1）使⽤ 游标分⻚（Cursor-based Pagination），⽐如基于上⼀⻚最后⼀条记录的主键或唯⼀排序字段继续查下⼀⻚：

```sql
SELECT * FROM table WHERE id > last_seen_id ORDER BY id LIMIT 10;
```

2）如果必须⽤offset，可以先通过索引覆盖查出主键，再关联原表，减少回表开销：

```sql
SELECT t.* FROM table t
INNER JOIN (SELECT id FROM table ORDER BY id LIMIT 100000000, 10) AS tmp ON t.id =
tmp.id;
```

真正解决这类性能问题的关键是避免全表扫描和⼤量数据跳过，索引下推和最⼩化数据访问才是根本思路。

## MySQL 中 DATETIME 和 TIMESTAMP 类型的区别是什么？

DATETIME和TIMESTAMP都⽤来存时间，但底层设计⽬标不⼀样，⽤错场景容易踩坑。

## 1）存储范围不同

DATETIME 能存从 1000-01-01 到 9999-12-31 的时间，精度到秒。TIMESTAMP 只⽀持 1970-01-01 到 2038-01-19，受32 位时间戳限制，过了 2038 年会溢出。

## 2）时区处理差异⼤

TIMESTAMP 实际存的是 UTC 时间戳，读写时根据当前会话的 time_zone ⾃动转换。插⼊时转成 UTC 存，查询时按本地时区展⽰。DATETIME 不带时区信息，存什么就是什么，不转换。

## 3）存储空间也不同

DATETIME 占 8 字节，TIMESTAMP 只占 4 字节。如果数据量上亿，TIMESTAMP 能省不少空间。

## 4）⾃动初始化和更新⾏为

两者都⽀持 DEFAULT CURRENT_TIMESTAMP 和 ON UPDATE CURRENT_TIMESTAMP ，但 TIMESTAMP 在旧版本中更早⽀持这些特性，某些情况下⼀个表只能有⼀个 TIMESTAMP ⾃动更新。

```sql
CREATE TABLE events (
id INT PRIMARY KEY,
dt DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
ts TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);
```

般建议：需要跨时区保存时间（⽐如⽇志时间、交易发⽣时间），选TIMESTAMP；单纯记录某个时刻且不想被时区⼲扰，⽐如“预约时间”，就⽤DATETIME。别让2038年问题搞不定未来系统。

## 在MySQL中，你使⽤过哪些函数？

MySQL⾥的函数⽤得多了，关键看场景。字符串处理像 CONCAT 拼接、 SUBSTRING 截取，⽇志分析或者⽣成报表时特别常⻅。⽇期函数⼏乎天天⻅，⽐如 DATE_ADD 、 DATEDIFF ，做订单⽣命周期统计或者⽤户活跃度分析都绕不开。

数值计算这块， ROUND 控制⼩数位， IFNULL 处理空值很实⽤，避免后续计算出错。聚合函数像 SUM 、

COUNT 、 AVG 更是家常便饭，配合 GROUP BY 出数据快。有时候还得写 CASE WHEN 做条件判断，⽐如把订单状态码转成可读⽂本。

但要注意，尽量别在 WHERE 条件⾥对字段套函数，⽐如 WHERE YEAR(create_time) = 2024 ，这会让索引失效，全表扫描，性能直接崩。应该写成 WHERE create_time >= '2024-01-01' AND create_time < '2025-01-01' ，让查询能⾛索引。

复杂逻辑建议放在应⽤层，或者⽤视图封装，别⼀股脑塞给数据库算。毕竟数据库的CPU成本⾼，还可能影响主从复制延迟，尤其是⼤表上跑⼀堆函数表达式。

总的来说，函数是⼯具，⽤对地⽅提效，滥⽤就成慢查询根源了。

## 数据库的三⼤范式是什么？

第⼀范式说⽩了就是字段不能再分，每个列都得是原⼦的。⽐如你存个地址"北京市朝阳区"，后⾯要按城市查就不⽅便。要是拆成省、市、区三个字段，才算符合第⼀范式。

第⼆范式建⽴在第⼀范式基础上，要求所有⾮主键字段完全依赖于整个主键。这主要出现在联合主键场景⾥。⽐如说订单明细表，主键是订单ID加商品ID，那数量、单价这些字段就得同时依赖这两个主键。但像客户姓名这种只依赖订单ID的，就得拎出去单独建表，不然就存在部分依赖。

第三范式更进⼀步，⾮主键字段之间不能有依赖关系，都得直接依赖主键。举个例⼦，⽤户表⾥有部⻔ID和部⻔经理两个字段，部⻔经理其实是通过部⻔ID间接确定的，这就产⽣了传递依赖。正确的做法是把部⻔经理信息放到部⻔表⾥，⽤户表只保留部⻔ID作为外键。

<!-- image-->

总的来说，三⼤范式层层递进，⽬的是减少数据冗余、避免更新异常。不过实际项⽬中像TiDB或者⼀些OLAP系统，为了查询性能经常做反范式设计，⽐如预关联宽表。所以范式更像是理论指导，具体还得看业务场景。

## 什么是游标Cursor分⻚？相⽐传统LIMITOFFSET分⻚有什么优势？

游标分⻚不是靠⻚码，⽽是通过上⼀⻚最后⼀个记录的某个唯⼀且有序的字段值（⽐如ID或时间戳）作为“锚点”，来获取下⼀⻚数据。

传统LIMITOFFSET分⻚在深分⻚时性能很差。⽐如 LIMIT 10000, 20 ，数据库得先扫描前1万条数据，再扔掉它们，只返回第10001到10020条。数据量⼀⼤，这种查询会越来越慢，甚⾄拖垮数据库。

游标分⻚直接跳过前⾯的扫描。假设按 ID 升序排列，上⼀⻚最后⼀条的 ID 是 15678，那下⼀⻚就是：

```sql
SELECT * FROM orders
WHERE id > 15678
ORDER BY id
LIMIT 20;
```

这条查询能⾛索引，压根不经过前⾯的数据，响应基本稳定在毫秒级。

不过它也有局限。没法直接跳转到第100⻚，只能“下⼀⻚”这样顺滑滚动。适合⽆限加载场景，⽐如微博、朋友圈这类产品⽤的就是类似机制。Redis的SCAN命令也是游标思想的应⽤。

另外，如果排序字段有重复值，可能需要组合字段做游标，避免漏数据。⽐如 (created_at, id) 联合定位。

## MySQL中的事务隔离级别有哪些？

事务隔离级别是为了解决并发场景下多个事务同时操作数据时产⽣的问题。MySQL⽀持四种标准隔离级别，每种解决的问题和带来的副作⽤都不同。

## 读未提交（Read Uncommitted）

⼀个事务能读到另⼀个事务还没提交的数据。这种情况最容易出问题，⽐如读到了“脏数据”，也就是对⽅事务回滚了，你读到的就是废的。⼀般没⼈⽤这个级别。

## 读已提交（Read Committed）

只能读到已经提交的数据，解决了脏读。但会出现不可重复读，就是同⼀个事务⾥两次读同⼀⾏数据，结果不⼀样，因为中间有别的事务提交了修改。PostgreSQL默认就是这个级别。

## 可重复读（Repeatable Read）

MySQL的默认隔离级别。保证在同⼀个事务中多次读取同⼀数据结果⼀致，解决了不可重复读。通过MVCC（多版本并发控制）实现快照读，普通查询不加锁。但理论上还可能存在幻读问题，不过InnoDB在这个级别通过间隙锁解决了⼤部分幻读场景。

## 串⾏化（Serializable）

最⾼的隔离级别，所有事务排着队执⾏。读会加共享锁，写加排他锁，完全避免并发问题。但性能最差，吞吐降得厉害，只有对数据⼀致性要求极端严格的场景才会考虑。

<!-- image-->

实际业务中，基本都在⽤读已提交或可重复读。选择哪个看场景，⽐如⾦融系统可能倾向可重复读，⽽⾼并发读多写少的系统可能选读已提交更合适。

## MySQL⼀张表最多可以有多少列？

MySQL单表的列数限制不是固定的，它受多个因素影响，最终取决于存储引擎和数据类型的组合。

1）对于 InnoDB 引擎来说，逻辑上⽀持最多 1017 列（MySQL 5.7 及之后版本），如果是 MySQL 8.0.34+，这个上限提升到了 4096 列。但这是理论最⼤值，实际能建多少列还卡在另⼀个硬限制上：⾏⼤⼩（row size）。

2）所有列的⻓度加起来不能超过单⾏最⼤65,535字节。⽐如你定义很多 VARCHAR(65535) ，其实根本存不下，因为⼀⾏压根不经过额外开销就超了。像 CHAR 、 BLOB 、 TEXT 这些类型也都会占⽤这部分空间，尤其是变⻓字段还有额外1-2字节记录⻓度。

3）另外每个索引列也有影响，InnoDB每张表最多⽀持64个⼆级索引，每个索引最多包含16个列，这也会间接约束设计。

举个例⼦：

```sql
CREATE TABLE t (
c1 int,
c2 varchar(100),
⼀堆字段
c1000 varchar(10)
);
```

看着没问题，但如果总字段太多且类型偏⼤，建表时就会报错 Row size too large 。

所以实践中，超过⼏百列就得警惕了。⼀般搞不定业务模型才需要这么多列，通常建议拆成宽表+属性表，或者⽤JSON字段收拢低频属性，别硬刚⼀⻓串nullable字段。

## 在MySQL中建索引时需要注意哪些事项？

索引不是建得越多越好，搞不好反⽽拖慢写⼊性能。每条INSERT、UPDATE都要维护索引结构，尤其是B+树的分裂合并，成本不低。

1）选择区分度⾼的列作为索引键。⽐如⽤户表⽤ user_id ⽐⽤ gender 强多了，后者只有两个值，查起来⼏乎全表扫。

2）联合索引注意最左前缀原则。⽐如你建了 (a, b, c) 的组合索引，查询条件必须从a开始，只查b或c压根不经过这个索引。

3）避免在索引列上做计算或函数操作。像 WHERE YEAR(create_time) = 2023 这种写法，即使create_time 有索引也⽤不上，得改成范围查询。

4）覆盖索引能显著提升性能。如果查询字段都在索引⾥，MySQL 直接从 B+ 树的叶⼦节点取数据，不⽤回表查主键索引，减少 IO。

5）字符串字段别全建索引，太占空间。⽐如 VARCHAR(255) 可以只对前 10 个字符建前缀索引，但得保证前缀区分度够⾼。

6）⼤表加索引要⼩⼼锁表。可以⽤ ALTER TABLE ... ALGORITHM=INPLACE, LOCK=NONE ，或者借助 pt-online-schema-change ⼯具在线操作。

7）定期检查冗余和未使⽤索引。information_schema.statistics 能看索引使⽤情况，⻓时间没被⽤到的可以考虑删掉。

什么是数据全量同步和增量同步？它们各有什么优缺点？

数据同步⼀般分两种模式，全量同步和增量同步，选哪种得看场景。

全量同步就是把源库的所有数据⼀次性拉过来，不管⽬标端有没有。⽐如每天凌晨⽤DataX把MySQL的订单表全量导到数仓⼀次。好处是逻辑简单，不容易出错，适合数据量⼩或⾸次初始化。但问题是数据量⼀⼤就搞不定，⽹络带宽和数据库压⼒都扛不住，像1000万条记录每次扫⼀遍，IO直接打满。

增量同步只传变化的数据，通常是基于binlog、timestamp字段或CDC⼯具。⽐如⽤FlinkCDC监听MySQL的变更⽇志，只把新增或修改的⾏发到Kafka。这种⽅式资源消耗低，延迟也⼩，能实现准实时同步。但复杂度⾼，要处理断点续传、顺序⼀致性、中间环节丢数据等问题，维护成本明显更⾼。

实际项⽬⾥常⻅的是组合打法。第⼀次做全量同步，之后⼀直⾛增量同步。像阿⾥云DTS就是这样设计的。如果中间断了太久，增量追不上，系统会⾃动触发重新全量。

要不要加图？这⾥流程清晰，⽂字⾜够说明。

1）全量：源库 → 全表扫描 → ⽬标库（覆盖） 2）增量：源库 → 捕获变更（binlog） → 消息队列 → ⽬标库（追加/更新）

两者本质是吞吐与延迟的权衡。⼩数据+可靠性优先选全量，⼤数据+实时性要求选增量。

## MySQL索引的最左前缀匹配原则是什么？

当你的SQL查询条件⽤到了联合索引，但不是从第⼀个字段开始，也不是连续使⽤时，能不能命中索引，就得看最左前缀匹配原则。

这条规则的意思是，MySQL会⼀直向右匹配直到遇到范围查询（⽐如>、<、BETWEEN、LIKE）或者没有使⽤的列为⽌，中间不能断。

举个例⼦，你有个联合索引 (a, b, c)，那么下⾯这些查询能⾛索引： 1）只查 a 2）查 a 和 b 3）查 a、b、c

但如果查的是b单独，或者b和c，压根不经过a，那这个联合索引就⽤不上。因为不符合“最左”这个前提。

特别注意范围查询的影响。⽐如 WHERE a = 1 AND b > 2 AND c = 3 ，虽然三个字段都⽤了，但因为 b 是范围，c就没法再利⽤索引了。也就是说，范围查询后⾯的列不会⾛索引。

实际开发中，像 user_id 和 create_time 这种⾼频组合，如果你把 create_time 放前⾯，⽽查询经常是等值查 user_id+范围查时间，那索引顺序错了就搞不定查询性能。

所以建联合索引的时候，顺序很关键：等值查询放前⾯，范围查询放后⾯，并且尽量让⾼频字段靠左。

什么是 CDC（Change Data Capture）？常⻅的 CDC ⼯具有哪些？

CDC 的本质是捕获数据变更事件，⽽不是定期轮询快照。数据库的事务⽇志⽐如 MySQL 的 binlog、PostgreSQL 的WAL天然就是变更流，CDC⼯具就是把这些⽇志实时解析成可消费的消息。

这类⼯具不依赖业务代码侵⼊，能以极低延迟把增删改操作同步到下游，典型场景是保持缓存与数据库⼀致、数据仓库实时⼊仓、微服务间解耦。如果靠定时任务扫表，延迟⾼还容易把数据库搞崩。

## 常⻅开源⽅案有⼏种路线：

1）基于数据库⽇志解析，Debezium 是主流选择，它⽤ Kafka Connect 框架做分布式采集，⽀持 MySQL、PostgreSQL、Oracle 等多种源，能把每⼀⾏变化发到 Kafka Topic ⾥。

2）阿⾥开源的Canal只针对MySQL，模拟slave拉取binlog，适合纯Java技术栈的公司集成，像阿⾥内部早期就⽤它做订单数据同步。

3）商业产品如 Oracle GoldenGate 功能更强，但成本⾼；现代数仓场景也有 Flink CDC 直接嵌⼊计算引擎，⽤ SQL就能写变更管道。

代码层⾯，Debezium的配置核⼼是定义connector的source属性，指定数据库地址、binlog位点、加密⽅式等，启动后⾃动⽣成数据流。

注意点：DDL变更处理要⼩⼼，字段删除可能导致消息格式不兼容；还有断点续传必须依赖可靠的offset存储。

## 什么是批量数据⼊库？相⽐单条插⼊有什么优势？

批量数据⼊库指的是把⼀批数据⼀次性写⼊数据库，⽽不是⼀条⼀条地提交。这个操作在数据导⼊、⽇志处理、ETL场景⾥特别常⻅，⽐如⽤ MyBatis Plus 的 saveBatch ⽅法，或者 JDBC 直接执⾏ addBatch() +executeBatch() 。

单条插⼊每次都要⾛⼀次⽹络往返、事务开销、⽇志刷盘，假设你要插 1 万条数据，就得连着执⾏ 1 万次 prepare、execute、commit。⽽批量⼊库能把这 1 万条打包成 100 个批次，每个批次 100 条，实际执⾏次数直接降到 100 次。

最核⼼的优势是性能提升。⼀般情况下，批量插⼊的吞吐量能⽐单条⾼5\~10倍，甚⾄更多。原因也很直接：⽹络交互少了，数据库的SQL解析压⼒⼩了，事务提交次数也⼤幅降低。

但也不是越⼤越好。如果单批次达到⼏千上万条，可能引发⼤事务问题，内存占⽤飙升，甚⾄导致连接超时或锁表。  
⼀般来说，每批控制在 200\~500 条⽐较稳妥，具体要看数据库配置和硬件能⼒。另外，像 MySQL 在使⽤ rewriteBatchedStatements=true 参数后，会把批量插⼊重写成 INSERT INTO ...  
VALUES (...), (...), (...) 这种多值形式，效率更⾼，这种优化单条压根不经过。

## MySQL的索引类型有哪些？

MySQL的索引类型主要看存储引擎⽀持，最常⽤的是InnoDB，它的索引结构基于B+树。

## 1）主键索引（聚簇索引）

⾏数据和主键⼀起存储在B+树的叶⼦节点，物理顺序和主键顺序⼀致。每张表只能有⼀个，查询效率最⾼，范围查询 也快。

## 2）⼆级索引（普通索引）

⾮主键列上的索引，B+树叶⼦节点存的是主键值。查⾮主键字段会先⾛⼆级索引找到主键，再回表查聚簇索引，这个过程叫回表。

## 3）唯⼀索引

和⼆级索引类似，但要求列值唯⼀，允许⼀个 NULL。创建唯⼀约束时⾃动建这种索引。

## 4）联合索引

多个列组合的索引，遵循最左前缀原则。⽐如 (a, b, c) 能命中 a、(a,b)、(a,b,c)，但不能⽤ b 单独查。

## 5）全⽂索引

⽤于⽂本内容的关键词搜索，⽀持 MATCH AGAINST 语法。MyISAM 和 InnoDB 都⽀持，但使⽤场景不多，⼀般⽤Elasticsearch 或 OpenSearch 替代。

## 6）前缀索引

对字符串前N个字符建索引，节省空间。⽐如index(email(10))，但会影响区分度，可能增加扫描⾏数。

覆盖索引是个重要优化点。如果查询的字段都在索引⾥，压根不经过回表，直接从⼆级索引返回数据，速度很快。⽐如给 (name, age) 建联合索引，select name, age from t where name=? 就能覆盖。

## 多线程并发同步数据时（数据库的数据同步到数仓中）需要注意什么问题？

多线程做数据库到数仓的数据同步，本质是在解决⼀致性和性能的平衡问题。你得先想清楚数据从哪来、怎么拉、怎么写。

1）拉取数据时别直接 SELECT \* FROM table ，⼤表⼀查就卡住，还可能把数据库连接池搞崩。⼀般⽤⾃增ID或时间戳做分⽚，⽐如按 ID 范围切任务，每个线程处理⼀段，这样能并⾏拉数据。如果是 MySQL，可以考虑 WHEREid BETWEEN ? AND ? 配合索引。

2）多个线程往数仓写数据，必须避免重复写或漏写。常⻅做法是每个线程处理的数据块带唯⼀标识，在数仓侧做幂等，⽐如Hive或ClickHouse写⼊前先检查分区是否存在，或者⽤事务型表引擎（如Iceberg）提交时做原⼦替换。

3）共享状态要⼩⼼。⽐如有个全局计数器记录同步进度，多个线程更新它就得加锁，但其实更好的⽅式是让每个线程独⽴汇报进度，由协调者汇总，压根不经过临界区。

4）异常处理不能少。某个线程挂了，任务得能重试，但⼜要防⽌重复同步。通常把任务状态存到外部存储，⽐如ZooKeeper或数据库⾥的任务表，失败后可恢复。

5）别忽视数据库的负载。并发太⼤，源库的CPU、IOPS可能扛不住。⼀般控制并发线程在10\~20个以内，配合限流，像Canal或DataX实际也是这么⼲的。

## MySQL中TEXT类型最⼤可以存储多⻓的⽂本？

MySQL 的 TEXT 类型不是单⼀类型，⽽是⼀组⽤于存储⼤⽂本的字段类型，不同变种容量差别很⼤。

1）TINYTEXT 最⼤ 255 字节，和 VARCHAR(255) 上限⼀样，但存储⽅式不同。

2）TEXT 最⼤ 65,535 字节（约 64KB），实际能存的字符数取决于字符集。⽐如⽤ utf8mb4，⼀个字符占 4 字节，最多存 16383 个字符左右。

3）MEDIUMTEXT ⽀持到 16,777,215 字节（约 16MB），适合存⽂章内容、⽇志⽚段这类中等⻓度⽂本。

4）LONGTEXT 能到 4,294,967,295 字节（约 4GB），基本能满⾜绝⼤多数⼤⽂本场景。

这些类型的数据不存储在⾏内，⽽是把实际内容放在额外的溢出⻚，⾏⾥只存指向它的指针。这样⼀来，虽然能存得下⼤⽂本，但访问时会有⼀次间接寻址，性能⽐VARCHAR差⼀些。

如果字段经常⽤来做WHERE查询或ORDERBY，尽量别⽤TEXT，因为索引受限。⽐如普通索引最多前缀767字节（或 3072 字节，取决于 innodb_large_prefix 配置），全⽂检索可以⽤ FULLTEXT 索引，像 MySQL ⾃带的全⽂索引或者接⼊ Elasticsearch 更合适。

代码上建表时写法很简单：

```sql
CREATE TABLE articles (
id INT PRIMARY KEY,
content LONGTEXT
);
```

般选哪种，得看业务数据量级。存个⽤户简介⽤TEXT绰绰有余，存⼩说章节建议MEDIUMTEXT，搞⽂档归档系统可能就得上 LONGTEXT。

## MySQL 中 AUTO_INCREMENT 列达到最⼤值时会发⽣什么？

当⼀张表的 AUTO_INCREMENT 列达到其数据类型定义的最⼤值时，数据库没法再⽣成新的唯⼀⾃增值，下⼀次插⼊就会直接报错，语句中断。

⽐如你⽤的是 INT 类型，最⼤值是2147483647。⼀旦⾃增到这个数，再执⾏ INSERT ，MySQL就会抛出类似“Duplicate entry '2147483647' for key 'PRIMARY'” 的错误，其实是⾃增溢出，但表现像是主键冲突。

根本原因是，⾃增机制在尝试加1时发⽣了整数溢出，值卡住不变了，导致后续所有插⼊都试图⽤同⼀个ID，⾃然就撞了主键。

1）不同整数类型的上限得⼼⾥有数：

TINYINT 最⼤ 127（有符号）或 255（⽆符号）

SMALLINT 是 32767 / 65535

MEDIUMINT 是 8388607 / 16777215

INT 是 2147483647 / 4294967295

BIGINT 是 9.2e18 / 1.8e19

⼩表⽤ INT ⼀般够⽤，但⾼并发写⼊的场景，⽐如订单、⽇志类系统，⼏年下来可能就逼近极限，这时候就得上BIGINT 。

2）预防这事，其实很简单：设计阶段就评估数据增⻓量。⽇均百万写⼊的话，⼀年就是3.6亿，不到12年就能把有符号 INT 耗尽。所以新项⽬直接⽤ BIGINT UNSIGNED 更省⼼。

3）已经快满了怎么办？可以改列类型，但 ALTER TABLE 在⼤表上是脏活累活，会锁表。可以⽤在线⼯具如 pt-online-schema-change，或者提前分库分表，把压⼒分散掉。

## MySQL⼆级索引有MVCC快照吗？

MySQL的InnoDB引擎⾥，MVCC主要靠聚簇索引中的隐藏字段和undolog来实现。你查主键的时候，InnoDB能通过这些机制判断某条记录对当前事务是否可⻅。

但⼆级索引本⾝不带MVCC信息。它叶⼦节点存的是主键值，不是完整⾏数据。当你⾛⼆级索引查找时，会先定位到对应的主键值，再回表去聚簇索引⾥查那⼀⾏。真正的可⻅性判断，是在回表后的聚簇索引查询阶段才做的。

也就是说，⼆级索引只是⼀个“跳板”。它不保存trx_id、roll_ptr这些MVCC所需的元数据，压根不参与快照读的判定逻辑。查询过程中，虽然⼆级索引⻚也会被加载进 buffer pool，但它不会像聚簇索引那样应⽤ undo log 构建历史版本。

所以你在读⼆级索引时，看到的是索引条⽬的最新状态，但这不代表你能直接看到对应数据⾏的最新版本⸺最终能不能返回这条记录，还得看回表后在聚簇索引中检查MVCC条件的结果。

举个例⼦，你在⼀个已删除但未提交的记录上查⼆级索引，依然能⾛到那个索引项，但回表时发现主键记录已被标记删除且当前事务看不到它，结果就是不返回。

## 什么是数据库的视图？

数据库⾥的视图，说⽩了就是⼀条被命名的SQL查询语句，它不存实际数据，只存逻辑。你查视图的时候，数据库才临时执⾏背后的SQL把结果拼出来。

这种设计主要解决⼏个问题：⼀是简化复杂查询，⽐如多表关联、聚合计算这些脏活累活封装到视图⾥，业务⽅直接SELECT \* FROM v_user_order 就⾏；⼆是做权限隔离，⽐如⽤户表有敏感字段 id_card ，你可以建个视图只暴露 user_name 和 age ，让报表系统只能查这个视图，压根不经过原始表。

还有⼀点是保持接⼝稳定。底层表结构要是改了，⽐如把 user_info 拆成 user_base 和 user_ext ，只要视图的字段输出不变，上层应⽤就不⽤改代码，能平滑过渡。

不过得注意，视图是查的时候才计算的，所以叫“虚表”。频繁查⼤范围数据的视图可能拖慢查询，特别是嵌套好⼏层的视图，执⾏计划会变得很复杂，搞不定的时候就得拆开优化。

有些数据库像 MySQL ⽀持对视图做 CREATE INDEX ，但其实是给基表加索引，本⾝不能独⽴建索引。PostgreSQL有物化视图，可以提前把结果存下来，查得快，但数据不是实时的。

## 什么是数据库的游标？

数据库⾥的游标，你可以把它看作⼀个“查询结果的指针”。执⾏⼀条 SELECT 语句后，数据库返回⼀堆数据，但程序没法⼀⼝⽓全吃进去。这时候就需要游标，⼀点⼀点地从结果集⾥取数据。

1）它本质上是⼀个上下⽂句柄，保存了当前查询的状态，⽐如“现在读到第⼏⾏了”、有没有下⼀⾏。

2）典型的使⽤场景是存储过程或批量处理，⽐如在 MySQL 存储过程中⽤ DECLARE CURSOR 声明，然后 FETCH逐⾏读取，适合处理⼏万甚⾄上百万条记录的后台任务。

3）代码上像这样：

```sql
DECLARE emp_cursor CURSOR FOR SELECT id, name FROM employees;
OPEN emp_cursor;
FETCH NEXT FROM emp_cursor INTO @id, @name;
-- 循环处理
CLOSE emp_cursor;
```

其实⼤多数 Web 应⽤压根不经过游标，JDBC 或 ORM ⽐如 MyBatis 默认是⼀次性拉取结果集，底层已经把数据读进内存了。只有在数据量太⼤、内存扛不住的时候，才会考虑⽤服务器端游标，让数据库分批吐数据。

容易搞混的⼀点是：客户端分⻚不是游标。真正的游标是在数据库服务器上保持连接状态，会占⽤资源，⽤完必须关掉，否则可能拖慢数据库。

## 为什么不推荐在MySQL中直接存储图⽚、⾳频、视频等⼤容量内容？

MySQL这种关系型数据库，设计初衷是处理结构化数据，像整数、字符串、时间这些固定或⼩⻓度的类型。你要是硬塞图⽚、⾳频、视频进去，基本都得⽤BLOB字段，但这会带来⼀堆麻烦。

1） 存储成本翻倍。同样的⽂件，在 MySQL ⾥存⼀遍，备份还得再存⼀遍，占空间不说，备份时间也成倍涨。⼀个  
10MB 的⽂件，每天增量 1000 个，⼀天就是 10GB，磁盘搞不定。

2） 性能直接拖垮。⼤⽂件读写要占⼤量内存和⽹络带宽，MySQL 的 buffer pool 会被污染，缓存命中率暴跌。本来跑得好好的查询，全被这些⼤对象拖慢了。

3）扩展性⼏乎为零。数据库主从同步时，⼤BLOB会卡住复制线程，导致延迟飙升。分库分表更别提，⽂件根本没法拆。

真要存这类内容，主流做法是把⽂件扔到对象存储⾥，⽐如阿⾥云OSS、AWSS3或MinIO。数据库⾥只留个URL或⽂件 ID。访问的时候应⽤先查 DB 拿地址，再去对象存储拿⽂件。这套组合拳在互联⽹公司已经是标配。

<!-- image-->  
这么拆，数据库专注元数据管理，对象存储扛住海量⽂件，各⼲各的，系统才能撑得住。

## 相⽐于 Oracle，MySQL 的优势有哪些？

MySQL和Oracle都是关系型数据库，但定位和设计哲学差得挺远。MySQL起初就是奔着轻量、快、易部署去的，尤其适合互联⽹场景。

1）开源免费是硬道理。MySQL社区版完全免费，像阿⾥、腾讯早期都是靠它省下⼏百万授权费。Oracle⼀套企业版动辄⼏⼗万，还得按核收费，⼩公司压根扛不住。

2）性能侧重点不同。MySQL在读多写少、⾼并发的简单查询场景下响应更快，⽐如商品列表⻚、⽤户评论这些接⼝，QPS 轻松上万。它的 InnoDB 引擎⽀持⾏级锁和 MVCC，已经能覆盖 90% 以上的业务需求。

3） 架构轻，运维成本低。MySQL 单实例资源占⽤⼩，512MB 内存都能跑起来。配合主从复制 + MHA 或 Sentinel，故障切换也够⽤。相⽐之下Oracle是“⼤块头”，依赖专⽤⼯具和DBA精细调优，⼈⼒成本⾼⼀截。
