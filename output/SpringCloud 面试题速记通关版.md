## SpringCloud 有哪些核⼼组件？

SpringCloud不是单⼀框架，⽽是⼀套微服务解决⽅案的集合，它把常⽤的微服务模式都整合成可插拔的组件。

1）服务注册与发现⽤ Eureka、Nacos 或 ZooKeeper。服务启动后往注册中⼼上报⾃⼰，其他服务想调⽤它时，直接从注册中⼼拉取可⽤实例列表，实现动态寻址。

2）服务间调⽤常⽤ OpenFeign 或 RestTemplate 配合 Ribbon。Feign 是声明式 HTTP 客户端，写个接⼝加注解就能发起远程调⽤，Ribbon负责客户端负载均衡，⽐如轮询或随机选实例。

3）熔断限流靠 Hystrix 或 Sentinel。Hystrix 提供熔断、降级和隔离，防⽌⼀个服务雪崩拖垮整个系统。Sentinel 是阿⾥开源的，流量控制更精细，⽀持实时监控和规则动态配置。

4）API ⽹关⼀般⽤ Spring Cloud Gateway 或 Zuul。所有外部请求先⾛⽹关，统⼀做路由、鉴权、限流。Gateway 基于WebFlux，⾮阻塞性能更好。

5）配置中⼼推荐 Nacos 或 Config Server。把 application.yml 放到配置中⼼，服务启动时拉取，运⾏时还能动态刷新，不⽤重启就能改配置。

6）链路追踪整合 Sleuth + Zipkin。Sleuth 给每个请求打上唯⼀ Trace ID，Zipkin 收集⽇志并可视化调⽤链，排查跨服务问题特别有⽤。

这些组件不是必须全⽤，像 Nacos 就能同时搞定注册中⼼和配置中⼼，简化架构。

## Consul 是什么？

Consul 是 HashiCorp 出品的⼀个服务⽹格解决⽅案，主打服务发现、配置管理和服务间安全通信。它不光是个注册中⼼，还能⼲⼀堆脏活累活，⽐如健康检查、多数据中⼼⽀持、ACL权限控制。

1）服务发现：每个服务启动后往Consul注册⾃⼰，消费者通过服务名查到可⽤实例。⽐如订单服务要调库存服务，直接问 Consul 要 inventory-service 的地址列表。

2）健康检查：Consul主动探活，挂掉的服务会⾃动从列表剔除。⽀持HTTP、TCP、脚本等多种探测⽅式，保证流量不会打到残⾎节点。

3）KV 配置存储：可以把配置写进 Consul 的键值对系统，服务监听变更实现动态刷新，类似轻量版的 ZooKeeper。

4）服务⽹格能⼒：通过边⻋代理（Connect）启⽤ mTLS，服务之间⾃动加密通信，还能基于服务⾝份做访问策略控制。

部署模式上，Consul ⽤ Raft 协议选主，数据强⼀致，通常建议 3 或 5 个节点组成集群。相⽐ Eureka，它更重⼀些，但功能也更全；⽐起Nacos，它在多DC场景下更成熟，不过运维复杂度⾼点。

## 什么是服务雪崩？

服务雪崩指的是某个服务出现故障或响应变慢，导致上游服务的请求堆积，线程资源耗尽，最终引发整个系统连锁性崩溃的现象。这种情况在微服务架构中特别常⻅，尤其是当服务调⽤链很⻓的时候。

⽐如你⽤SpringCloud调⽤⼀个订单服务，它⼜去调Redis查数据，结果Redis响应慢了。订单服务的线程⼀直被占着，新请求进来只能等，线程池撑爆，⾃⼰也挂了。上层的⽤户服务调不到订单服务，同样卡住，⼀层层往上倒，最后整个系统瘫痪。

1）核⼼是级联故障，⼀个点的问题扩散成⾯的问题

2）根本原因是同步阻塞调⽤+⽆熔断机制，请求卡住不释放资源

3）典型场景就是⾼并发下数据库慢查询拖垮服务，进⽽影响整个调⽤链

解决思路主要是三点：超时控制、限流、降级和熔断。像Hystrix、Sentinel这类⼯具就是⼲这个的。给每个依赖服务设置最⼤等待时间和最⼤并发数，⼀旦超了就快速失败，不让它把整个线程池拖死。

## HTTP 与 RPC 之间的区别？

HTTP是应⽤层协议，本质是通信规范，⽽RPC是⼀种编程模型，⽬标是让远程服务调⽤像本地⽅法调⽤⼀样简单。

1）通信协议上，HTTP通常基于⽂本或⼆进制格式（如HTTP/1.1、HTTP/2），⾛的是标准端⼝，天然⽀持跨平台和浏览器交互。RPC框架可以⾃定义协议，⽐如Dubbo⽤Netty+⾃定义私有协议，gRPC基于HTTP/2但封装了严格的接⼝契约。

2）调⽤⽅式差异明显。HTTP ⼀般通过 RESTful ⻛格的 URL + ⽅法（GET/POST）交互，数据多⽤ JSON 传输，⼈眼可读。RPC 更关注接⼝抽象，客户端直接调 userService.getUser(1001) ，底层⾃动序列化、⽹络传输、服务寻址，开发者⼏乎感知不到⽹络细节。

3）性能⽅⾯，RPC协议更轻量，压根不经过浏览器那⼀套解析逻辑，序列化也常⽤Protobuf这类⾼效格式，延迟通常⽐HTTP低30%以上。像gRPC在内部微服务之间调⽤就很常⻅，扛住⾼并发没问题。

4）典型场景：对外暴露API给前端或第三⽅，基本都⽤HTTP+REST+JSON。内部服务间调⽤，尤其是对延迟敏感的场景，⽐如订单系统调库存，就更适合⽤ RPC 框架，⽐如 Dubbo 或 gRPC。

负载均衡算法有哪些？

轮询是最常⻅的负载均衡算法，Nginx 默认就⽤这个。服务器按顺序轮流接收请求，实现简单，适合后端机器性能相近的场景。如果某台机器扛不住，得配合健康检查动态摘除。

1）加权轮询给不同机器分配权重，性能强的机器处理更多请求。⽐如三台机器权重 2:1:1，第⼀台每轮处理两次，后⾯各⼀次。Kubernetes 的 kube-proxy 在某些模式下会⽤到类似策略。

2）随机算法直接选⼀台，看似不靠谱，但客户端⾜够多时分布很均匀。gRPC的默认负载均衡就是随机，实现轻量，压根不经过中⼼调度。

3）最少连接数关注实时负载，把新请求发给当前连接数最少的机器。适合⻓连接场景，像WebSocket或数据库连接池，HAProxy⽀持这种策略。

4）源地址哈希根据客户端IP做hash，相同IP始终路由到同⼀台。会话保持的场景有⽤，⽐如没有共享session的⽼系统。缺点是机器扩容时⼤量映射失效。

⼀致性哈希解决普通哈希在节点变动时全量重映射的问题。把节点和请求都映射到⼀个环上，只影响邻近节点。分布式缓存如 Redis Cluster、Cassandra 都⽤了变种。

<!-- image-->  
实际选型看场景。短连接⽆状态服务⽤轮询或随机就够了，有状态或连接密集型考虑最少连接或⼀致性哈希。

## Feign 和 OpenFeign 的区别？

Feign 是 Netflix 开源的声明式 HTTP 客户端，Spring Cloud 将其集成进来，让你⽤接⼝+注解的⽅式发起 HTTP 调⽤，不⽤写⼀堆 RestTemplate 的模板代码。它在早期 Spring Cloud 版本⾥是默认的远程调⽤⽅案。

后来 Netflix 停⽌了 Feign 的维护，社区接⼿并发展出 OpenFeign，其实是同⼀个东西的延续，但功能更强。你现在⽤Spring Cloud 2018 之后的版本，引⼊ spring-cloud-starter-openfeign ，底层⽤的就是 OpenFeign。

1）注解⽀持更全。OpenFeign 原⽣⽀持 Spring MVC 的注解，⽐如 @RequestMapping、@GetMapping，你可以直接把 Controller 接⼝复⽤为客户端接⼝，开发起来顺⼿很多。

2）内置能⼒更丰富。集成了Ribbon实现负载均衡，和Eureka配合天然⽆缝。还⽀持通过配置开启重试机制，配合Spring Retry 可以应对临时故障。

3）扩展性更好。⽀持⾃定义 Encoder、Decoder、Logger，还能插拦截器做请求头注⼊，⽐如传递 JWT token。

代码上⼏乎⽆感，你定义⼀个接⼝加上 @FeignClient 注解就⾏：

```bib
@FeignClient(name = "user-service", path = "/users")
public interface UserClient {
@GetMapping("/{id}")
}
```

本质上，OpenFeign就是Feign的“官⽅增强版”，后续所有新功能都在这上⾯演进。⽼项⽬可能还叫Feign，新项⽬⼀律⽤ OpenFeign，连依赖名都变了，别搞混。

## Feign 和 Dubbo 的区别？

## 通信协议与适⽤场景

Feign 是 Spring Cloud ⽣态⾥的声明式 HTTP 客户端，底层⾛的是 HTTP 协议，⼀般配合 Ribbon 做负载均衡。它适合微服务之间基于 RESTful 接⼝的调⽤，⽐如订单服务调⽤户服务，发个 GET 请求查个信息，简单直接。

Dubbo就不⼀样了，它是阿⾥开源的RPC框架，主打⾼性能服务治理。默认⽤Dubbo协议（基于Netty的TCP⻓连接），序列化也更⾼效，像Hessian2、JSON、Kryo都⽀持。特别适合内部服务间⾼并发、低延迟的调⽤，⽐如交易链路⾥库存扣减、⽀付回调这些关键路径。

## 编程模型与⽣态集成

Feign 的⻛格是“接⼝ + 注解”，写个接⼝，贴上 @GetMapping 、 @RequestParam 就完事了，开发体验和写Controller ⼏乎⼀样，对 Spring Boot 开发者⾮常友好。

Dubbo 则是定义服务接⼝和实现分离，通过 @DubboService 和 @DubboReference 来暴露和引⽤服务。它⾃带注册中⼼（⽀持ZooKeeper、Nacos）、配置中⼼、元数据中⼼，治理能⼒更强，像权重调整、路由规则、熔断降级都更精细。

1）Feign 调⽤链短，适合轻量级、跨语⾔边界不强的场景

2）Dubbo功能重，但能扛住⼤流量，适合核⼼业务模块之间的深度集成

## Feign是如何实现负载均衡的？

Feign 本⾝不实现负载均衡，它只是个声明式的 HTTP 客户端，真正起作⽤的是和它集成的组件。在 Spring Cloud ⽣态⾥，Feign 默认会整合 Ribbon 或 LoadBalancer 来完成这⼀步。

你写⼀个 Feign 接⼝，⽐如调⽤ user-service 的 /get 接⼝，最终请求并不是直接发出去的。Spring Cloud 会在底层把你的接⼝⽅法解析成HTTP请求模板，然后交给动态代理处理。真正发起请求时，会先经过负载均衡拦截。

1）如果项⽬⾥引⼊了 spring-cloud-starter-loadbalancer ，那么 LoadBalancerClient 就会被⾃动装配。Feign底层的 Client 实现会被替换成⽀持负载均衡的版本。

2）这个客户端会去服务注册中⼼（⽐如Nacos、Eureka）拉取 user-service 的可⽤实例列表，再根据默认或配置的策略（如轮询、随机）选⼀个实例。

3）最后才⽤真实的 IP:Port 替换掉原来的 service name，发起 HTTP 调⽤。

代码上你完全不⽤操⼼这些，只要加注解就⾏：

```java
@FeignClient(name = "user-service")
public interface UserClient {
@GetMapping("/get")
String getUser();
}
```

只要 user-service 在注册中⼼有多个实例，Feign调⽤时就会⾃动⾛负载均衡。注意，这个能⼒是靠组合实现的，不是 Feign ⾃⼰写的。如果你压根没引⼊注册中⼼和负载均衡组件，那它就是个普通 HTTP 客户端，搞不定实例选择。

## 什么是 Feign？

Feign 是 Spring Cloud ⽣态⾥⼀个声明式的 HTTP 客户端，它让你像调⽤本地⽅法⼀样发起远程 HTTP 请求。你不需要写具体的⽹络请求代码，只要定义⼀个接⼝，加上注解，框架会⾃动⽣成实现。

它的核⼼其实是动态代理。你写的接⼝在运⾏时会被JDK或CGLIB动态代理，每次调⽤⽅法时，Feign会根据⽅法上的注解解析出对应的HTTP请求路径、参数和请求体，然后交给底层的客户端（⽐如HttpURLConnection、OkHttp）去执⾏。

常⻅的使⽤场景是微服务之间的调⽤。⽐如订单服务要查⽤户信息，直接通过Feign接⼝调⽤⽤户服务的RESTAPI，代码看起来就像本地⽅法调⽤：

@FeignClient(name = "user-service")   
public interface UserClient {   
@GetMapping("/users/{id}")   
User getUserById(@PathVariable("id") Long id);   
}

实际请求过程由 Feign 拦截处理，集成 Ribbon 可做负载均衡，配合 Hystrix 还能⽀持熔断降级。不过现在 OpenFeign已经把 Hystrix 替换为更现代的 resilience4j。

如果你⽤的是 Spring Cloud Alibaba，底层默认还是 OpenFeign，只是注册中⼼换成 Nacos，调⽤逻辑不变。

## 什么是熔断器？为什么需要熔断器？

服务调⽤链路越来越⻓，⼀个接⼝可能依赖三四下游。要是某个下游响应慢或者直接挂了，上游线程池很快就被占满，最后整个系统都不可⽤。熔断器就是⼲这个的，它像个电路保险丝，在异常达到阈值时主动切断请求，避免雪崩。

1）熔断有三种状态：关闭、打开和半开。正常时是关闭状态，⼀旦失败率超过设定值，⽐如10秒内50%请求超时，⽴⻢切到打开状态，所有请求直接失败，不发⽹络请求，压根不经过⽹络。

2）隔⼀段时间后进⼊半开状态，放⼀⼩部分流量过去试探下游是否恢复。如果成功就回到关闭，继续正常流转；要是还失败，再切回打开。

3） 像 Hystrix 和 Sentinel 都实现了这套机制。Hystrix 虽然停更了，但它的设计理念在 Resilience4j ⾥延续着。你可以配置失败⽐例、滑动窗⼝⼤⼩、熔断持续时间等参数，灵活控制保护策略。

代码上基本就是加个注解的事：

```java
@CircuitBreaker(name = "backendA", fallbackMethod = "fallback")
public String callBackend() {
return webClient.get().retrieve().bodyToMono(String.class).block();
}
```

```java
public String fallback(Exception e) {
return "default";
}
```

没有熔断的话，局部故障会迅速扩散成全局问题。有了它，系统⾄少能保住⼀部分核⼼功能可⽤。

## 什么是 Hystrix？

Hystrix是Netflix开源的容错组件，⽤来解决分布式系统中服务调⽤者因依赖服务故障导致的雪崩问题。它的核⼼思路是通过隔离、降级和熔断机制保护系统。

服务调⽤被封装成命令（HystrixCommand），执⾏时会进⼊独⽴线程池或信号量资源池。⼀旦下游响应超时、异常或失败率超过阈值，熔断器就会打开，后续请求直接⾛降级逻辑，不再发起真实调⽤。

降级通常返回预设的兜底数据，⽐如订单服务调⽤⽤户服务失败时，返回⼀个默认⽤户名。这样能快速释放资源，避免线程堆积拖垮整个应⽤。

1）线程池隔离：每个依赖服务分配独⽴线程池，避免单个慢请求耗尽所有线程

2）信号量控制：适⽤于⾮⽹络调⽤场景，限制并发数

3）熔断策略：默认5秒内20次以上请求，错误率超50%就触发熔断，10秒后尝试半开恢复

```java
@HystrixCommand(fallbackMethod = "getDefaultUser")
public String getUserName(Long uid) {
return restTemplate.getForObject("/user/" + uid, String.class);
}
public String getDefaultUser(Long uid) {
return "default_user";
}
```

虽然 Hystrix 已进⼊维护模式，但它的设计理念被⼴泛继承，⽐如 Resilience4j 和 Sentinel 都借鉴了类似的熔断与隔离模型。

## 什么是服务降级？

服务降级不是等系统崩了才去做的事，⽽是提前想好“如果某个依赖出问题，我该怎么办”的兜底策略。本质是在资源有限或依赖不稳定时，牺牲⾮核⼼功能，保证核⼼链路可⽤。

⽐如你调⽤⼀个商品详情接⼝，⾥⾯要查库存、查价格、查推荐。这时候推荐服务挂了，难道整个⻚⾯都打不开？显然不⾏。你可以选择不展⽰推荐列表，但库存和价格必须返回，这就是典型的降级操作。

1）降级通常发⽣在客户端或者⽹关层，⽐如⽤Hystrix、Sentinel这类框架配置规则。当检测到超时、异常或线程堆积时，⾃动⾛fallback逻辑。

2）常⻅的降级⽅式有直接返回默认值、缓存数据、静态资源、简化流程。像淘宝⼤促时可能关闭评论加载，京东秒杀期间不查物流信息，都是为了把流量省下来给下单服务。

3）和熔断的区别在于，熔断是“断开连接避免雪崩”，⼀般是临时性的；⽽降级是“我知道它有问题，但我有备选⽅案”。两者经常配合使⽤。

代码上基本就是加个注解或者配置规则：

```java
@SentinelResource(value = "getRecommend", fallback = "getDefaultRecommend")
public List<Item> getRecommend() {
return remoteCallToRecommendService();
}
return Collections.emptyList(); // 降级返回空列表
}
```

要不要降级、降哪⼀块，得从业务⻆度权衡。核⼼原则就⼀条：保最重要的那个动作能跑通。

## 什么是服务熔断？

服务熔断其实和家⾥电闸跳掉是⼀个道理。系统压⼒太⼤或者下游故障，就先切断请求，避免雪崩。

1）核⼼是保护机制。当某个服务调⽤失败率超过阈值，⽐如连续5次超时或异常，熔断器⽴刻切换到打开状态，后续请求直接失败，不往下游发。

2）给系统⼀个喘息机会。默认等待5秒进⼊半开状态，放少量请求过去试探。如果成功就关闭熔断，恢复正常；失败则继续打开。

3）典型实现像 Hystrix，虽然现在⽤得少了，但思想被⼴泛继承。Sentinel、Resilience4j 都有类似能⼒。⽐如Resilience4j 可以这样配置：

CircuitBreakerConfig config = CircuitBreakerConfig.custom()   
.failureRateThreshold(50) // 失败率超50%触发   
.waitDurationInOpenState(Duration.ofMillis(5000)) // 等5秒尝试恢复   
.build();

4）和限流不⼀样。限流是控制流量⼤⼩，熔断是应对依赖不稳定。经常配合使⽤，⽐如⽹关层⽤ Sentinel 同时做限流和熔断。

搞不定这玩意⼉，线上容易出现连锁故障。⼀个接⼝卡死拖垮整个应⽤，尤其是微服务调⽤链⻓的场景。

## 什么是服务限流？

服务限流不是为了限制⽤户，⽽是为了保护系统不被突发流量打垮。它的本质是在⼊⼝处设置⼀个“流量阀⻔”，只放⾏能处理的请求，超出的部分直接拒绝或排队。

最常⻅的场景就是秒杀活动。⽐如系统每秒最多扛住1000次请求，那就可以设置限流规则为QPS=1000。再往上来的请求，哪怕资源暂时空闲，也先拦住。不然瞬时5000请求进来，数据库直接崩。

实现上⼀般⽤令牌桶或者漏桶算法。像阿⾥开源的Sentinel、Google的GuavaRateLimiter都是基于这些原理。代码层⾯可以很简单：

// Guava ⽰例，每秒⽣成 10 个令牌   
RateLimiter limiter = RateLimiter.create(10.0);   
if (limiter.tryAcquire()) {   
handleRequest();   
} else {   
rejectRequest();   
}

实际架构中，限流通常放在⽹关层做，⽐如⽤ Nginx 或 Spring Cloud Gateway 配合 Redis 实现分布式限流。这样不⽤每个服务都重复实现。

要注意的是，限流和熔断不⼀样。熔断是依赖出问题了临时切断，防⽌雪崩；限流是主动控制⼊⼝流量，保证系统在安全⽔位运⾏。

图中⽹关是核⼼拦截点，所有请求必须先过它这⼀关。

## Sentinel 是怎么实现限流的？

Sentinel 的限流不是靠拦截器硬拦，⽽是基于统计模型做决策。它在每个资源上挂⼀个实时的流量哨兵，盯着 QPS 或线程数，⼀旦超过设定阈值，后续请求直接拒绝。

这套机制的核⼼是滑动时间窗⼝。不像固定窗⼝那样⼀⼑切，Sentinel把1秒拆成多个⼩格⼦，⽐如20个slot，每个50ms刷⼀次。这样能更精准地反映流量分布，避免突发流量被误杀。

控制⾏为⽀持多种策略：1）直接拒绝：最常⻅，超了就throwBlockException2）WarmUp：慢启动，适⽤于系统刚上线怕被突增流量打垮，⽐如从 30% 速率慢慢拉到 100% 3）匀速排队：像队列⼀样让请求等⼀等，适合削峰填⾕，⽐如每秒放⾏10个，多了就排队

配置也很简单，代码⾥加个注解就⾏：

```java
@SentinelResource(value = "doSomething", blockHandler = "handleBlock")
public String doSomething() {
return "hello";
}
```

真正⼲活的是 FlowSlot ，它是责任链⾥的⼀环，每次请求都会经过它。它会去查这个资源有没有配流控规则，有就按规则算要不要block。

实际项⽬中，我们常把Sentinel和Gateway结合，在⽹关层统⼀限流，保护后端服务。像订单服务、⽀付接⼝这种核⼼链路，基本都设了QPS限制，防⽌被刷。

## Sentinel 与 Hystrix 的区别是什么？

Sentinel和Hystrix都是服务容错组件，但设计思路和能⼒范围差别挺⼤。Hystrix更像是给单个⽅法做“保险丝”，主流⽤法是基于注解或命令模式包裹远程调⽤，⼀旦超时或出错就⾛降级逻辑。它核⼼是熔断降级，在SpringCloudNetflix体系⾥⽤得⽐较多。

Sentinel是阿⾥开源的流量治理⼯具，不只做熔断，还覆盖了限流、系统⾃适应保护、热点参数防护这些。⽐如你可以对某个URL按QPS限流，或者限制某类⽤户请求频率，这些Hystrix压根搞不定。

使⽤⽅式上也有差异。Hystrix依赖线程池隔离或信号量隔离，线程池⽅案有开销，信号量⼜不能⽀持超时控制。Sentinel默认⽤信号量模式，通过滑动时间窗⼝统计实时指标，资源损耗⼩，规则还能动态配置，配合SentinelDashboard 调整策略特别⽅便。

还有⼀个关键点：Hystrix 已经进⼊维护模式，不再迭代。⽽ Sentinel 在持续更新，和 Spring Cloud Alibaba ⽣态深度集成，也⽀持 Dubbo、gRPC 等多种框架。

举个场景：你有个商品详情接⼝，突然被爬⾍打爆了。⽤Hystrix很难应对，因为它不擅⻓限流。但Sentinel可以直接按⼊⼝来源限流，把爬⾍请求挡掉，正常⽤户照常访问。

<!-- image-->

所以简单说，Hystrix是“熔断专家”，Sentinel是“全链路流量卫⼠”。新项⽬建议直接上Sentinel。

## Sentinel是怎么实现集群限流的？

Sentinel集群限流的关键是把流量控制的决策从单机移到中⼼化的“集群维度”。你得先有个TokenServer，它负责统⼀计算和发放令牌，其他服务实例作为TokenClient向它申请许可。

1）通常⽤⼀台或⼏台独⽴部署的 Sentinel Dashboard 或专⽤服务来充当 Token Server。客户端启动时会注册⾃⼰，Server维护所有客户端的⼼跳和状态。

2）请求进来时，Client不再直接判断能不能放⾏，⽽是向Server发起⼀次轻量级的远程调⽤，问“我这个资源现在能通过吗”。Server根据当前集群总QPS配额、已⽤量、流控规则做统⼀决策，返回允许或拒绝。

3）如果⽹络出问题或者Server挂了，可以配置降级为本地限流，避免整个服务被拖垮。这其实是“⾼可⽤”和“⼀致性”之间的权衡。

代码上，只需要在客户端配置：

```javascript
FlowRule rule = new FlowRule("myResource")
.setCount(100) // 集群总阈值
.setGrade(RuleConstant.FLOW_GRADE_CLUSTER)
.setClusterMode(true);
```

然后指定 clusterConfig，告诉它是 client 还是 server，以及连接信息。背后通信默认⽤ Netty + TCP，延迟压根不经过 HTTP 层。

<!-- image-->

这种模式适合秒杀、热点商品这些需要精确控总量的场景。但要注意⽹络开销，⾼频调⽤的服务得评估好性能损耗。

什么是服务⽹格？

服务⽹格本质是处理服务间通信的基础设施层，专⻔管请求怎么在微服务之间安全可靠地传。它把熔断、限流、监控这些⽹络相关的脏活累活从业务代码⾥剥离出来，交给独⽴的代理组件去⼲。

1）每个服务实例旁边都会部署⼀个轻量级⽹络代理，叫sidecar。这个sidecar挡在服务前⾯，所有进出流量都得经 过它。⽐如 Istio ⽤的是 Envoy，多个 sidecar 组成⼀个 mesh ⽹络。

2）控制平⾯负责统⼀下发路由规则、安全策略。数据平⾯就是那些sidecar，按规则转发流量。业务服务压根不关⼼对⽅IP，也不⽤⾃⼰实现重试逻辑，全由sidecar搞定。

3）典型场景像⾦丝雀发布，控制平⾯改条规则，只放5%流量到新版本，sidecar⾃动分流。故障注⼊、链路追踪也都是配置级别操作，不⽤动代码。

适合中⼤型微服务架构，服务数量上 50+ 后运维复杂度飙升，靠 SDK 很难统⼀治理。但⼩项⽬别上，多⼀跳延迟，运维成本也⾼。

<!-- image-->

sidecar模式让通信逻辑与业务彻底解耦，这才是服务⽹格的核⼼价值。

## 什么是灰度发布、⾦丝雀部署以及蓝绿部署？

灰度发布、⾦丝雀部署和蓝绿部署都是控制流量逐步切换的发布策略，核⼼⽬标是降低上线⻛险。

灰度发布是个⼤概念，指先让⼀部分⽤户使⽤新版本，反馈没问题再全量推。⽐如你在⽤某个App，突然被选中体验“内测版”，其实就是进⼊了灰度名单。这种策略常⻅于互联⽹产品，像微信、淘宝发版都⾛灰度，靠⽤户ID或地域分流，后端⼀般⽤Nginx或Spring Cloud Gateway做路由。

⾦丝雀部署是灰度的⼀种具体实现，名字来⾃矿⼯带⾦丝雀下矿的传统。它更偏向基础设施层⾯操作，⽐如在Kubernetes⾥，你先起⼀个新版本Pod，把1%的流量导过去，观察⽇志和监控指标。没问题就逐步增加⽐例，直到全切。这过程可以⽤Istio这样的服务⽹格精细控制。

蓝绿部署则是准备两套完全⼀样的⽣产环境，蓝⾊是当前线上，绿⾊是新版本。发布时直接把流量从蓝切到绿，回滚也是⼀键切回来。好处是切换快、回滚快，但成本⾼，毕竟要维持两套环境。AWSElasticBeanstalk和阿⾥云EDAS都⽀持这种模式。

对⽐来看，蓝绿最稳但花钱多，⾦丝雀最灵活但控制复杂，灰度适合⽤户维度的渐进验证。

## 什么是微服务⽹关？为什么需要服务⽹关？

微服务⽹关本质是所有外部请求进⼊系统的统⼀⼊⼝。它不处理具体业务逻辑，⽽是负责把请求安全、⾼效地路由到后端不同的微服务上。

## 1）请求路由

系统拆分成⼏⼗个微服务后，每个都有独⽴地址和端⼝，客户端不可能记住所有接⼝位置。⽹关通过配置规则，⽐如/user/\*\*转发到⽤户服务，/order/\*\*转到订单服务，实现统⼀接⼊。

## 2）协议转换

前端通常⽤HTTP，内部服务可能⽤gRPC或Thrift提⾼性能。⽹关做协议适配，让前后端各⽤最合适的通信⽅式。

## 3）横切关注点集中处理

鉴权、限流、⽇志、监控这些通⽤功能如果在每个服务⾥重复实现，维护成本极⾼。⽹关把这些脏活累活揽下来，⽐如⽤ JWT 校验⾝份，⽤ Redis + Lua 实现分布式限流。

## 4）安全防护

直接暴露内部服务容易被攻击。⽹关可以屏蔽真实服务信息，加WAF防护，控制访问频率，避免单个服务被打垮影响全局。

像SpringCloudGateway、Kong、Envoy都是典型实现。没有⽹关的微服务架构，就像没设⻔卫的⼤楼，谁都能随便进出，管理⼀⽚混乱。

## Spring Cloud 可以选择哪些 API ⽹关？

Spring Cloud ⽣态⾥主流的 API ⽹关选择其实就两个，Spring Cloud Gateway 和 Zuul。

1）Spring Cloud Gateway 是 Spring 官⽅⾃⼰搞的⽹关，基于 WebFlux，底层⽤的是 Netty，性能⽐ Zuul 强不少。它⽀持响应式编程模型，路由、断⾔、过滤器这些功能都挺全，像路由匹配可以⽤ Path、Header、Query 参数等条件。现在新项⽬基本都推荐⽤它。

```lua
return builder.routes()
.route("path_route", r -> r.path("/user/**")
.uri("http://localhost:8081"))
.build();
}
```

2）Zuul 是 Netflix 那⼀套的⽼将，基于 Servlet 2.x，阻塞 I/O，吞吐量有限。虽然 Zuul 2.x 改成了异步模型，但集成到 Spring Cloud ⾥并不顺畅，社区推动⼒也不够。现在基本处于维护状态，不建议新项⽬选型。

⽹关的核⼼职责是统⼀⼊⼝，做路由转发、鉴权、限流这些事。这类脏活累活⼀般都会交给专⻔的组件来做。⽐如你可以结合 Sentinel 做限流降级，或者⽤ Spring Cloud Gateway 配合 Nacos 实现动态路由。

要不要上 API ⽹关，得看你的微服务规模。如果就三五个服务，直接⽤ Nginx 反向代理也⾏。但服务⼀多，上百个实例，就得靠⽹关来统⼀治理了。

## 什么是 Spring Cloud Zuul？

SpringCloudZuul是Spring⽣态⾥⼀个⽹关组件，主要⼲的事就是统⼀⼊⼝、路由转发和过滤拦截。虽然现在官⽅不维护了，但⽼项⽬⾥还挺常⻅。

它的核⼼其实是基于Servlet实现的同步阻塞⽹关，所有请求进来都会经过⼀系列ZuulFilter。你可以⾃定义PRE类型的filter做⾝份校验，ROUTING阶段决定往哪转发，POST处理响应头，ERROR捕获异常。

典型场景⽐如你有 user-service 和 order-service，Zuul 可以配置路径前缀 /user/\*\* 转发到⽤户服务， /order/\*\* 转发到订单服务。还能做限流、灰度发布，甚⾄结合 Eureka 动态发现服务实例。

代码上主要是加 @EnableZuulProxy 注解，然后配置 routes：

```yaml
zuul:
routes:
```

```css
user: /user/**
order: /order/**
```

不过要注意，Zuul1.x是同步模型，每个请求占⼀个线程，⾼并发下容易把线程池搞满。后来有了Zuul2.x想上异步，但Netflix压根不推，⼤家转投SpringCloudGateway了。现在新项⽬基本都⽤后者，底层是Reactor，能扛住10w+ 并发连接。

所以总结⼀句：Zuul 是个⽼派⽹关，理解它有助于维护旧系统，但新项⽬直接上 Spring Cloud Gateway 更靠谱。

## 什么是 Spring Cloud Gateway？

Spring Cloud Gateway 是 Spring 官⽅基于 Spring 5、Project Reactor 和 WebFlux 构建的响应式 API ⽹关，⽤来替代早期的Zuul。它运⾏在⾮阻塞I/O模型上，能⽤少量线程处理⾼并发请求，资源消耗远低于传统Servlet栈的⽹关。

它的核⼼机制是路由（Route）+断⾔（Predicate）+过滤器（Filter）。请求进来后，先通过Predicate判断是否匹配某个 Route，如果匹配就交给对应路由处理，过程中再经过⼀系列 GatewayFilter 和 GlobalFilter 做加⼯或控制。

⽐如你想把 /user/\*\* 转发到⽤户服务，配置就像这样：

@Bean   
public RouteLocator customRouteLocator(RouteLocatorBuilder builder) {   
return builder.routes()   
.route("user_route", r -> r.path("/user/\*\*")   
.uri("http://user-service:8080"))   
.build();   
}

实际项⽬⾥，你通常会结合Nacos或Eureka做服务发现，⽤过滤器实现鉴权、限流、⽇志埋点，也可以集成Sentinel 实现熔断降级。像鉴权这种通⽤逻辑，写个 GlobalFilter 拦⼀下 token 就⾏。

要注意的是，它是纯响应式的，如果你的下游服务还是 Spring MVC 那套，整合时得注意线程模型差异，别把阻塞操作混进去，不然整个⽹关的吞吐就垮了。

## 你项⽬⾥为什么选择Gateway作为⽹关？

项⽬选型⽹关，不是为了凑热闹，⽽是业务发展到⼀定阶段，服务拆得太多，API调⽤乱成⼀锅粥了，必须有个统⼀⼊⼝来兜住。

1）最直接的痛点是路由混乱。以前前端调后端接⼝，IP+端⼝到处写，服务⼀迁移就断。Gateway 提供动态路由，结 合Nacos或Eureka，服务上线下线⾃动感知，请求压根不经过⼈⼯⼲预。

2）跨切⾯需求集中处理。⽐如鉴权、限流、⽇志打标，要是每个微服务都⾃⼰实现⼀套，后期改个规则得改⼗多个服务。⽤Gateway做拦截，⼀个过滤器搞定，省掉⼤量重复代码。

3）性能和扩展性也得看。Zuul 1 是阻塞 I/O，⾼并发下容易搞不定。Gateway 基于 WebFlux，默认就是响应式⾮阻塞，单机扛⼏千QPS没问题，横向扩缩也⽅便。

4）集成⽣态友好。和 Spring Cloud Config 配合做动态配置，加个限流规则不⽤发版；配合 Sentinel 做熔断降级，出问题⾃动切流量；甚⾄能对接 OAuth2 做统⼀认证。

<!-- image-->  
说⽩了，Gateway⼲的就是API管理的脏活累活，让业务服务专注业务逻辑。当然，如果项⽬就两三个服务，⽤Nginx 反向代理也够了，没必要上 Gateway。

说说什么是 API ⽹关？它有什么作⽤？

API⽹关本质是所有外部请求进⼊系统的统⼀⼊⼝，有点像⼩区的⻔卫。所有流量都得先经过它，再决定往哪⾛。

它的核⼼价值不是转发，⽽是把⼀堆通⽤的、和业务⽆关的脏活累活给拦下来。⽐如你⽤ Spring Cloud Gateway 或者Kong，其实都是在配置这些能⼒。

1）鉴权校验。接⼝不是谁都能调的，⽹关层可以检查JWTtoken，没带或者过期了直接401拒掉，压根不经过后端服务。2）限流熔断。防⽌突发流量把系统打崩，按IP或⽤户维度限制QPS，超过阈值就返回503，保护下游。3）⽇志监控。统⼀记录请求响应时间、状态码，上报到ELK或Prometheus，排查问题不⽤挨个服务翻⽇志。4）协议转换。前端调REST，但内部微服务可能⾛gRPC，⽹关做⼀层翻译，让前端少操⼼。5）路由转发。根据path路由到不同服务，⽐如 /user/\*\* 转发到user-service，路径规则集中管理，后端改了也不⽤前端跟着变。

拿电商系统举例，下单请求进来，⽹关先看是不是登录⽤户，再判断当前流量有没有超限，然后记⼀笔 traceId ⽅便链路追踪，最后才放⾏到订单服务。要是没有⽹关，每个服务都得⾃⼰实现这⼀套，重复代码多，策略还不⼀致。

## 什么是令牌桶算法？⼯作原理是什么？使⽤它有哪些优点和注意事项？

令牌桶算法是⼀种流量整形和限流控制机制，⽤来平滑突发流量，保证系统在可承受范围内处理请求。

系统会以恒定速率往⼀个固定容量的桶⾥放⼊令牌，⽐如每秒放10个。请求要被执⾏，必须先从桶⾥拿到⼀个令牌。桶⾥没令牌，请求就得等着，或者直接被拒绝。桶本⾝有容量上限，⽐如最多存50个令牌，满了就不再放，多余的丢弃。

这种机制能应对短时间内的流量⾼峰。⽐如瞬间来了30个请求，只要桶⾥有⾜够令牌，就能全部放⾏，不像漏桶那样强制匀速处理。这也是它和漏桶算法的关键区别⸺令牌桶允许⼀定程度的突发流量。

优点很明显。⼀是实现简单，⼆是⽀持突发流量，⽤户体验更⾃然。像Guava的 RateLimiter 就是基于令牌桶，Nginx 的 limit_req 模块也能配置成令牌桶模式来保护后端服务。

不过要注意，单机令牌桶只管⾃⼰这台机器。如果部署了多个实例，得配合分布式协调，⽐如⽤ Redis + Lua 脚本实现全局限流，否则整体流量可能超出预期。

## 什么是分布式事务的防悬挂，空回滚?

分布式事务⾥，防悬挂和空回滚是保证事务⼀致性的关键机制，尤其在TCC（Try-Confirm-Cancel）这类柔性事务中必须处理。

1）空回滚是指：没有执⾏Try操作，但因为异常或超时，事务协调器直接调⽤了Cancel接⼝。⽐如事务发起⽅宕机前没发出Try请求，恢复后却触发全局回滚，资源⽅的Cancel就会被调⽤。这时候如果没有幂等控制，可能把正常的资源状态搞乱。解决办法是在 Cancel ⾥判断是否真的执⾏过 Try，通常靠⼀个事务状态记录来识别。

2）防悬挂是应对更复杂的时序问题。⽐如Try请求被延迟，先收到了Cancel，后⾯迟到的Try⼜被执⾏。这会导致资源预留成功，但事务已经回滚，数据不⼀致。防悬挂的做法⼀般是：⼀旦收到Cancel，就记录⼀个“已取消”标记，后续所有相同事务ID的Try都直接拒绝，不让它再预留资源。

这两个机制⼀般要配合使⽤。拿Seata的TCC模式来说，它的事务上下⽂⾥会带XID和分⽀事务ID，资源⽅需要本地维护事务状态表，通过数据库⾏锁或 Redis 来做幂等和防写⼊。

核⼼就是靠状态记录+幂等控制，把⽹络异常下的边缘情况兜住。

## 什么是 Seata？

Seata是阿⾥开源的分布式事务解决⽅案，⽬标是让分布式事务变得像本地事务⼀样简单。它不依赖数据库的XA协议，⽽是⾃⼰实现了⼀套⾼性能的事务协调机制。

它的核⼼是 TC（Transaction Coordinator）、TM（Transaction Manager）、RM（Resource Manager）三部分。TC是独⽴部署的服务，负责维护全局事务状态；TM开启或终⽌全局事务；RM负责分⽀事务的注册和状态汇报。

典型流程是：TM向TC申请开启全局事务，拿到全局事务ID；服务调⽤上下游时透传这个ID；各个RM在执⾏本地操作时，先写 undo_log 记录反向 SQL，再提交本地事务；如果全部成功，TC 提交全局事务，否则触发回滚，通过

undo_log 做补偿。

适合微服务架构下跨数据库、跨服务的场景，⽐如订单、库存、账户三个系统协同完成⼀个业务。Spring CloudAlibaba 集成后，加个 @GlobalTransactional 注解就能⽤。

常⻅模式有 AT 模式（⾃动补偿）、TCC 模式（⼿动定义两阶段逻辑）、Saga 模式（⻓事务编排）。AT 模式最常⽤，对业务侵⼊最⼩。

## 什么是配置中⼼？有哪些常⻅的配置中⼼？

配置中⼼本质是把应⽤的配置从代码⾥剥离出来，集中管理。服务启动时动态拉取配置，改配置不⽤重新发包，运维效率提升特别明显。

1）最核⼼的是实时⽣效。⽐如⽤Nacos修改⼀个开关，下游服务能⽴刻感知并调整⾏为，不像以前改个参数得重启⼏⼗个实例。

2）配置隔离靠命名空间和分组。开发、测试、⽣产环境各⽤各的配置，不会串。⼀个Nacos实例能撑起上千应⽤的配置管理，扛住⽇常变更完全没问题。

3）常⻅⽅案⾥，Spring Cloud Config 适合纯 Spring Boot 技术栈，但功能相对基础。Apollo 是携程开源的，配置界⾯友好，灰度发布⽀持好，⼤中型项⽬⽤得多。Nacos来⾃阿⾥，除了配置还⽀持服务发现，微服务体系⾥能⼀箭双雕，现在新项⽬基本⾸选它。

4）别⼩看这层能⼒。电商⼤促时调个限流阈值，如果靠改代码发布，半⼩时都搞不定。配置中⼼能让这个操作压根不经过研发，运营点两下就⽣效。
